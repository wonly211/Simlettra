# 澄笺项目协作

## 开始工作

1. 定位仓库根目录并读取 `AGENTS.md`。
2. 从 `AGENTS.md` 的“当前项目状态”判断所处阶段，不跨过尚未接受的决定。
3. 按任务读取最少的当前文档：
   - 产品行为：读取 `文档/需求/需求基线.md` 和相关需求清单。
   - 架构与技术路线：读取 `文档/架构/架构约束与质量属性.md`、相关平台核验和架构决策记录。
   - 实现与测试：读取当前需求、状态为“已接受”的架构决策记录、相关代码和测试。
   - 旧系统迁移：读取迁移需求和 `文档/需求/旧系统能力参考.md`，再检查旧仓库证据。
4. 用户在当前任务中的明确要求优先；发生需求变化时先更新当前文档，再调整架构或实现。

## 区分事实状态

- 只把“已确认”的需求和“已接受”的架构决策作为承诺。
- 把“提议中”方案写成备选或推荐，不写成已经决定。
- 不因旧代码存在而继承旧行为、权限、数据结构或技术债务。
- 所有项目文档及可自由命名的文档目录、文件名使用简体中文。

## 检查旧系统

- 把 `E:\SynologyDrive\github\Simletter` 视为只读参考仓库。
- 以提交 `9d016831ff2d862e38c08d9376a58327bc8933df` 为证据基准，优先使用 `git show`、`git grep` 和 `git ls-tree`。
- 未经用户明确要求，不安装依赖、不生成产物、不格式化、不提交也不修改旧仓库。
- 记录入口、数据写入、权限检查、失败行为和测试证据；把观察与新系统建议分开。

## 处理架构任务

1. 先从需求基线提炼约束、质量目标和风险。
2. 使用 Cloudflare 或第三方服务的当前能力时，核验官方资料并记录核验日期。
3. 提出少量可比较方案，用日常语言说明用户会感受到的差别、维护成本和风险。
4. 对部署单元、模块边界、数据存储、认证授权、公共契约或迁移方式建立架构决策记录。
5. 决策未接受前不建立正式工程骨架；验证性原型放在独立位置并明确标记。

## 处理实现任务

- 按业务模块组织代码，通过公开应用服务协作。
- 使用版本化 D1 迁移，不在普通请求中自动建表或隐式升级。
- 对收信、发信、删除和多资源写入设计幂等、补偿、重放与对账。
- 所有资源访问在服务端检查身份、所有权和组织成员资格。
- 不记录或提交密码、密钥、会话令牌、完整正文、附件内容和真实用户数据。
- 按可演示的纵向功能切片实现，并同步测试、文档与迁移。

## 验证与交付

- 文档变更检查状态、编号、内部链接、日期、简体中文和 UTF-8 编码。
- 代码变更运行与风险相称的单元、集成、浏览器端到端、类型和构建检查。
- 迁移和恢复使用数据副本演练，提供数量、对象引用和失败对账。
- 交付时说明完成内容、验证证据、仍未接受的决定和剩余风险。
