# 初步风险与待确认问题

## 文档状态

- 状态：进行中
- 建立日期：2026-08-15
- 说明：本页用于告诉非专业项目所有者“容易踩什么坑”和“还需要问什么”。风险评级与结论将在逐题访谈和深度核查后调整。

## 一、最容易忽略的坑

### 1. 产品信任边界如果理解错，现有架构可能整体不适用

当前设计明显倾向“一套部署服务一个相互认识的个人、家庭或小团队”，并由唯一系统管理员承担可信责任。如果实际目标是由一套系统服务多组互不信任的公众用户，租户隔离、管理员权限、滥用治理、合规、计费、服务等级和故障影响范围都需要重新设计。

### 2. “本地功能很多”不等于“邮箱已经能上线”

当前项目有大量本地自动化和功能文档，但首发发布门槛仍有 23 项阻断项。真实 Email Routing、Queue、Cron、接近 20 MB 邮件、Resend、SMTP2GO、备份恢复、旧系统迁移、浏览器矩阵和真人部署等尚未完整闭环。最大风险是继续增加功能，却迟迟没有证明最核心的真实收发链路成立。

### 3. 三个硬目标可能互相冲突

“Workers Free”“接近 20 MB 邮件”“完整可靠解析与异步处理”同时成立仍以真实环境验证为上线门槛。任何一个失败都可能要求改变邮件大小、运行套餐、解析策略或产品承诺，不能只靠继续写本地代码解决。

### 4. 同时支持 R2 和 KV 会长期扩大测试与运维成本

两种对象存储模式会影响容量、配额、对象一致性、备份恢复、迁移、部署、故障处理和验收矩阵。若没有明确的真实用户价值，双模式可能让每次修改都承担接近双倍的验证面。

### 5. 功能范围已经接近完整邮件平台，维护能力可能跟不上

项目同时包含收信、发信、搜索、组织、通知、转发、导出、备份恢复、旧系统迁移、生命周期清理、资源配额、健康状态和双存储部署。对于单人维护项目，风险通常不是“能否写出来”，而是上线后能否持续修复安全问题、平台变化、投递问题和数据故障。

### 6. 关键代码正在形成集中式大文件

当前单个 Vue 组件约 10,755 行，HTTP 路由文件约 4,206 行，样式文件约 3,998 行。即使测试通过，这种集中度也会增加修改冲突、状态耦合、审查困难和回归概率。是否需要拆分应依据实际耦合和测试边界进一步核查，不能只按行数机械重构。

### 7. 数据恢复方案正确性要求很高，但真实恢复尚未证明

项目明确承认 D1、对象存储和搜索之间没有整次原子恢复，失败后需要废弃目标资源并从空白目标重来。这是合理的保守设计，但也意味着发布前必须真实演练资源创建、对象回读、六项检查、绑定切换和失败处置，否则“有备份”仍可能等于“无法及时恢复”。

### 8. 自动部署与数据库迁移之间存在操作窗口

GitHub 自动部署遇到未应用迁移会停止，管理员需要先处理数据库再重新部署。若版本标识、迁移顺序、旧 Worker 兼容性或操作文档有任何漂移，可能导致停机或代码与数据库版本不匹配。

### 9. 邮件安全不只是不泄露密码

还需要持续处理 HTML/XSS、远程图片、恶意附件名、MIME 解析资源消耗、重复投递、重复发信、Provider 回调伪造、开放重定向、SSRF、日志正文泄露、备份密钥丢失和管理员账号恢复等风险。当前已有不少保护，但真实平台日志与外部边界仍未总审计。

### 10. 发信“接口调用成功”不代表邮件真正可用

真实可用性还受域名 DNS、SPF、DKIM、DMARC、Provider 账号状态、退信、投诉、速率限制和信誉影响。项目必须明确哪些由 Simlettra 自动判断，哪些由管理员配置和承担，否则用户会把投递失败误认为程序缺陷。

### 11. 文档数量多也会产生版本漂移

初步扫描已经看到部分运维文字仍写到迁移 `0022`，而当前正式迁移已经到 `0025`；公开部署记录也保留“待 Cloudflare 重新部署”的阶段性结论。后续需要建立“当前状态唯一入口”，避免非专业管理员照着过期步骤操作。

### 12. Git 与发布来源还不够稳固

本地开发仓库当前只看到一个基线提交，公开部署仓库有另一套提交历史，但正式标签和 Release 尚未建立。发生回归时，能否准确取得“上一可用版本、对应迁移、对应构建产物和对应文档”仍需证明。

### 13. 免费额度是产品上限，不只是成本说明

一旦 D1、KV、R2、Queue 或请求额度接近上限，系统需要保守停止新增数据并继续允许阅读、导出和删除。若平台指标不可用或延迟，管理员看到的“剩余额度”可能只是本地估算，产品提示和停止策略必须避免产生虚假安全感。

### 14. 唯一管理员是简化，也是单点风险

唯一管理员降低了权限模型复杂度，但密钥、账号、域名、Provider、恢复和成员管理都集中于一人。需要明确管理员失联、账号丢失、密钥丢失和恶意操作时，产品承诺到什么程度。

### 15. 旧系统迁移可能拖住新系统发布

如果首发必须迁移真实旧数据，旧邮件缺少原始 MIME、弱密码不能迁移、对象可能缺失、状态语义不同都会影响上线计划。如果真实用户并不需要旧系统迁移，把它保留为首发阻断项会付出很高成本。

## 三、当前最需要防止的偏差

在访谈完成前，先设置三条临时保护线：

1. 暂不增加新的产品功能，把注意力放在真实收发、恢复和部署证据上。
2. 暂不把“本地通过”“已经部署”或“代码存在”改写为“可以正式使用”。
3. 暂不为大文件做无目标拆分；先建立模块职责、变化频率、测试边界和用户在途修改的证据。

这些保护线是本轮工作建议，不是已经接受的新需求。

## 四、已确认的梳理基准

### 基准 01：自托管可信群体

2026-08-15，项目所有者确认：每个个人、家庭或小团队自行部署一套 Simlettra，实例内成员属于同一个信任群体，产品长期定位于此。

这意味着本轮梳理暂不要求引入公众 SaaS 所需的跨租户隔离、平台运营后台、租户计费、平台客服角色或防范实例唯一管理员的额外密钥隐藏机制。用户之间的个人邮件权限、组织成员权限和必要的服务端授权仍然必须保持，不能因为属于同一信任群体而取消。

### 基准 02：允许审查和取代既有决定

2026-08-15，项目所有者同意：当可靠证据表明某项已确认需求或已接受架构决定不适合当前产品定位时，本轮可以提出通过新需求变更或新 ADR 正式取代旧决定的建议。

梳理本身不自动改变当前基线。每项重大产品或架构变更仍需单独说明影响并取得项目所有者确认。

### 基准 03：免费且可靠优先于 20 MB

2026-08-15，项目所有者确认：Workers Free 与可靠性属于产品定位，优先级高于接近 20 MB 的邮件大小目标。

当前 20 MB 要求在真实 Workers Free 验证完成前仍保持原状。如果验证失败，纠偏方向应是依据稳定实测边界降低首发邮件大小上限，并通过正式需求变更和 ADR 取代旧结论；不得接受随机失败、静默丢失或半封邮件可见。

### 基准 04：正式产品只保留 D1 + R2

2026-08-15，项目所有者确认：正式移除 `D1 + KV`，首发和长期产品只保留 `D1 + R2`。

这是对当前需求与架构基线的重大调整，后续需要先建立正式需求变更和取代 ADR，再实施以下工作：

1. 取消 KV 部署入口、资源自动创建、配置模板和公开部署说明；
2. 删除 KV 对象存储适配、KV 一致性等待和双模式条件分支；
3. 把逻辑存储默认额度统一为 R2 模式对应值，明确已有 KV 测试实例不属于正式升级支持范围；
4. 收缩备份恢复、旧系统迁移、导出、清理、资源用量、构建和测试矩阵；
5. 检查 ADR `0004`、`0009`、`0029`、`0030`、`0032`、`0040`、`0041`、`0050` 至 `0052` 及相关需求、数据模型和运维文档的影响；
6. 决定现有 KV 代码是一次移除，还是先标记弃用并在一个可回退切片中删除。

当前代码和正式文档尚未执行上述变更，不能把本条访谈结论误写成已经完成实现。

### 基准 05：推荐规模与验证规模分离

2026-08-15，项目所有者确认：不对单实例承诺固定的无条件容量上限。项目继续以 50 名用户、100,000 封邮件和代表性并发读取作为发布验证规模；实际可用规模由邮件大小、附件比例、使用频率以及 Cloudflare Free 的资源边界共同决定。

后续文档应分别表达：

1. **验证规模**：项目实际执行过测试的规模和测试条件；
2. **推荐规模**：适合个人、家庭和小团队的日常使用范围；
3. **资源停止条件**：接近免费资源边界时阻止继续增长，但继续允许阅读、导出、备份和删除；
4. **非承诺事项**：不把 50 名用户或 100,000 封邮件写成任何内容分布下都保证可用的硬容量。

### 基准 06：首发采用手动离线加密备份

2026-08-15，项目所有者确认：首发采用管理员手动生成并保存的本地加密备份，外部自动备份留待后续评估。

首发仍必须补齐以下产品和运维闭环：

1. 明确显示最近一次成功备份时间；
2. 区分“在线备份已生成”和“管理员已经下载离线加密容器”，不能把前者等同于灾难备份完成；
3. 明确提示长期没有离线备份的风险；
4. 提供非专业管理员能够执行的备份、保管、校验和空白资源恢复演练；
5. 不承诺自动跨账号灾难恢复，也不新增外部存储凭据和协议。

### 基准 07：先受控试运行，再正式首发

2026-08-15，项目所有者确认采用两阶段交付：

1. **受控试运行**：先完成一套真实 `D1 + R2` 实例的核心闭环，供项目所有者和少量可信用户使用；
2. **正式首发**：受控试运行稳定后，再完成面向其他自托管部署者的发布、兼容、文档和完整验收。

后续需要把当前统一发布门槛拆成两层。受控试运行不能省略真实收信、可靠读信、核心发信、权限、安全、手动离线备份、恢复演练、资源停止和基本运维；可以根据后续确认，把非核心外部集成、完整浏览器矩阵、非程序员独立部署和公开分发收口安排到正式首发阶段。

### 基准 08：受控试运行从空白数据开始

2026-08-15，项目所有者确认：第一套 R2 受控试运行实例全新开始，不迁移旧 Simletter 数据。

因此真实旧数据迁移不再是受控试运行的前置条件。近期可以避免新旧数据合并、切换窗口、旧对象缺失、旧弱密码和旧邮件结构差异影响核心收发验证。旧迁移能力是否继续作为正式产品功能保留，仍需单独确认。

### 基准 09：冻结旧系统迁移能力

2026-08-15，项目所有者确认：冻结现有旧 Simletter 迁移实现，等受控试运行稳定后再决定正式保留、降级或移除。

冻结期间：

1. 不把真实旧数据迁移作为受控试运行阻断项；
2. 不继续增加迁移功能或扩大兼容范围；
3. 不删除现有迁移代码、正式迁移、自动化和文档；
4. 若 R2 单模式纠偏影响到迁移代码，只做保证工程一致性的必要调整，不恢复 KV 长期承诺；
5. 正式首发前重新决定它是否属于公开产品能力。

### 基准 10：不承诺固定数据恢复点

2026-08-15，项目所有者确认：账号级灾难发生时，以管理员最近一次成功保存的离线加密备份为恢复点，不承诺最多丢失 24 小时或 7 天等固定时间。

产品必须持续明确提示：

1. 最近一次在线备份生成时间；
2. 系统能否确认制品已被管理员下载，若不能确认则如实说明；
3. 最近一次可确认的恢复演练时间；
4. 最近备份之后的数据在账号级灾难中可能无法恢复；
5. 手动备份是管理员责任，首发不提供自动外部复制。

### 基准 11：长期支持双 Provider 与故障切换

2026-08-15，项目所有者确认：Resend 与 SMTP2GO 都属于长期正式支持范围，并保留域名级默认、备用路线及受控故障切换。

因此后续不能通过删除其中一家来简化正式产品。梳理需要重点验证：

1. 两家 Provider 当前真实 API、大小限制、鉴权和事件协议；
2. 只有明确未接受时才切换，结果未知时停止自动动作；
3. 逐收件人幂等、重复事件、乱序事件和回调伪造防护；
4. 管理员配置、测试、停用和替换凭据的非专业用户体验；
5. Provider 规则变化后的维护责任和兼容策略。

两家是否都必须在受控试运行开始前完成真实验收，仍需单独确认。

### 基准 12：试运行先验证一家 Provider

2026-08-15，项目所有者确认：受控试运行开始前，先选择一家 Provider 完成真实发信、回调和失败处理；另一家及真实故障切换在正式首发前完成。

试运行期间必须明确当前启用和已验证的 Provider，不能把尚未真实验收的备用路线显示为可依赖能力。正式首发仍需完成 Resend、SMTP2GO 以及明确未接受、结果未知、重复、乱序和故障切换场景。
