## 问题 01：部署与信任边界

### 当前证据

当前需求和实现倾向以下模型：

- 每套 Simlettra 独立部署为一个 Cloudflare Worker 项目；
- 每套系统只有一名可信系统管理员；
- 服务对象是个人、家庭或相互认识的小团队；
- 管理员能够管理运行密钥、域名、Provider 凭据、用户和恢复操作；
- 不存在面向多组互不信任客户的租户隔离、计费、客服和平台运营角色。

### 待确认问题

Simlettra 首发最终要采用哪一种部署与信任模型？

1. 每个使用者或小团队自己部署一套，单套实例内的管理员与成员属于同一个信任群体；
2. 由你集中部署一套，给多组互不认识、互不信任的公众用户共同使用；
3. 首发采用第一种，但未来明确要演进到第二种。

### 状态

已确认。

### 项目所有者回答

每个个人、家庭或小团队自己部署一套，实例内成员属于同一个信任群体，产品定位于此。

### 确认结论

1. Simlettra 是单实例、单可信群体的自托管产品，不是集中式公众多租户 SaaS。
2. 当前单 Worker、实例级唯一系统管理员和实例级 Cloudflare 资源的总体方向与产品定位一致。
3. 本轮不以公众 SaaS 的租户计费、平台运营角色或跨客户故障隔离要求评价现有架构。
4. 实例内部仍需保留个人邮件、组织邮件和普通成员之间的服务端授权边界。

### 影响范围

- 需求定位与首发目标；
- 管理员信任模型；
- 部署单元和资源归属；
- 安全审查边界；
- 后续运维和发布方式。

## 问题 02：本次纠偏能否调整既有决定

### 当前背景

项目已经形成 161 项有效需求和 53 份架构决策记录，并完成大量实现。后续深度核查可能发现某些已接受决定虽然能够实现，但与自托管小团队定位相比成本过高、风险过大，或者真实 Cloudflare 证据不足。

如果不能调整既有决定，本轮只能检查“代码是否忠实实现现有基线”；如果允许调整，本轮还可以比较“现有基线本身是否值得继续坚持”。两种范围会产生不同的纠偏结果。

### 待确认问题

当可靠证据表明某项已确认需求或已接受架构决定不适合当前产品定位时，本轮梳理是否可以建议用新的需求变更或 ADR 正式取代它？

### 状态

已确认。

### 项目所有者回答

同意。

### 确认结论

1. 本轮不局限于检查实现是否符合现有基线，也可以检查现有基线是否仍适合产品定位。
2. 有可靠证据时，可以提出新的需求变更或 ADR 取代既有决定。
3. 梳理文档中的建议不自动生效；重大变更必须逐项取得项目所有者确认。

## 问题 03：Free、20 MB 与可靠性冲突时的优先级

### 当前背景

当前基线同时要求：

1. Workers Free 是首发核心运行基线；
2. 支持接近 20,000,000 原始字节的邮件；
3. 邮件需要可靠保存、解析、重试并避免半封可见或静默丢失。

本地原型不能证明这三项在真实 Workers Free Queue consumer 中可以同时稳定成立。真实验证失败时，产品必须明确调整目标，继续优化代码未必能突破平台运行上限。

### 待确认问题

如果真实验证最终证明三项目标不能同时满足，哪两项应优先保留？

1. 保留 Free 和可靠性，降低首发最大邮件大小；
2. 保留接近 20 MB 和可靠性，允许改用付费运行基线；
3. 坚持 Free 和接近 20 MB，并接受部分大邮件可能无法稳定处理；
4. 暂不预选，验证失败后根据实测数据重新比较方案。

### 初步建议

不建议选择第 3 项。邮箱系统不能把不可预测的数据处理失败包装成正式支持。

在尚无真实失败证据时，建议选择第 4 项：先保持当前验证门槛；一旦失败，再以实测 CPU、内存、重试和样本边界比较第 1 项与第 2 项。

### 状态

已确认。

### 项目所有者回答

Free 和可靠性，产品定位于此。

### 确认结论

1. Workers Free 与可靠处理是产品定位中的优先约束。
2. 接近 20 MB 的支持目标继续接受真实环境验证，但不是不可调整的硬目标。
3. 如果验证失败，应根据真实稳定边界降低邮件大小上限，并正式更新需求与架构决定。
4. 不接受为了保留名义上的 20 MB 而让部分大邮件随机失败、静默丢失或产生不完整可见状态。

### 影响范围

- 需求 `6.02`、相关首发验收条件及需求变更；
- ADR `0030` 及 MIME 解析架构；
- 收信入口、Queue 解析、外发最终 MIME 和附件限制；
- 部署说明、错误提示和大邮件验收样本。

## 问题 04：是否长期保留 KV 与 R2 双存储模式

### 当前背景

当前工程同时支持 `D1 + R2` 和 `D1 + KV`：

- 两套部署配置；
- 两套默认逻辑配额；
- 对象读写、一致性等待、容量统计、导出、备份、恢复、迁移和清理均需要覆盖两种模式；
- R2 是当前默认模式，KV 是可选模式。

双模式能给部署者更多选择，但会持续扩大每次功能修改、故障修复和发布验收的工作量。对于定位为个人、家庭和小团队的免费自托管产品，需要确认这种选择是否真的值得长期维护。

### 待确认问题

首发和长期产品是否必须同时正式支持 `D1 + R2` 与 `D1 + KV`？

1. 必须长期同时支持两种模式；
2. 首发只正式支持默认的 `D1 + R2`，KV 延后到有真实需要时再评估；
3. 首发保留两种模式，但真实验收后若 KV 明显增加风险或没有实际价值，允许正式移除。

### 初步建议

建议选择第 3 项。已有双模式实现不必现在直接删除，但应让真实部署、恢复和维护证据决定 KV 是否值得成为长期正式承诺。

### 状态

已确认。

### 项目所有者回答

正式移除 `D1 + KV`，仅保留 `D1 + R2`。

### 确认结论

1. `D1 + R2` 成为唯一正式存储模式。
2. `D1 + KV` 不再是首发验收、长期兼容或升级支持范围。
3. 后续通过正式需求变更和取代 ADR 修改当前基线，再以独立纵向切片移除 KV 实现与文档。
4. 删除过程中必须保留 R2 现有行为和测试证据，不能顺带改变邮件对象、备份、迁移或配额语义。

### 主要影响

- 产品需求和默认逻辑配额；
- 对象存储抽象与 Worker 绑定；
- Cloudflare 资源自动创建与公开部署；
- 备份恢复、旧系统迁移、导出和清理；
- 测试、构建、验收和运维矩阵；
- 多份已接受 ADR 的适用范围。

## 问题 05：单实例正式规模目标

### 当前背景

当前产品定位是个人、家庭和小团队自托管；现有本地性能验收使用 50 名用户、100,000 封邮件和 10 个独立读取线程。规模目标不是宣传数字，它决定 D1 查询、搜索索引、后台任务、页面分页、资源停止线和未来是否需要重新拆分部署单元。

### 待确认问题

一套正式 Simlettra 实例应承诺支持到哪个规模？

1. 最多约 10 名用户、100,000 封邮件，重点服务个人与家庭；
2. 最多约 50 名用户、100,000 封邮件，保持当前小团队验收目标；
3. 需要支持超过 50 名用户或明显超过 100,000 封邮件；
4. 不按硬上限承诺，只明确推荐规模，并在接近 Cloudflare Free 资源边界时保守停止增长。

### 初步建议

建议选择第 4 项，同时把“50 名用户、100,000 封邮件”保留为发布前验证规模而不是无条件容量承诺。Cloudflare Free 的实际可用容量还会受邮件大小、附件比例、访问频率和平台额度共同影响。

### 状态

已确认。

### 项目所有者回答

选择第 4 项。

### 确认结论

1. 不承诺固定的单实例硬容量上限。
2. 50 名用户、100,000 封邮件继续作为发布前验证规模，而不是无条件容量承诺。
3. 产品文档提供推荐规模，并说明容量受邮件大小、附件比例、访问频率和 Cloudflare Free 额度共同影响。
4. 接近资源边界时保守停止新增数据，继续保障阅读、导出、备份和删除。

## 问题 06：备份是否需要自动离开当前 Cloudflare 账号

### 当前背景

现有方案允许管理员在线生成 D1 与 R2 的可校验备份，再由本地工具打包为 AES-256-GCM 加密容器。它能应对数据库或对象损坏，但前提是管理员主动生成、下载并妥善保存备份。

如果备份只留在同一个 Cloudflare 账号或同一组资源中，账号丢失、误删资源或账号级故障可能同时影响业务数据与在线备份。要自动把备份发送到另一个位置，则需要新增外部存储协议、凭据、定时任务、保留策略、失败告警和恢复兼容测试。

### 待确认问题

首发对灾难备份应承诺到什么程度？

1. 维持当前方案，由管理员定期手动生成并下载加密备份；
2. 自动定期备份，但仍保存在同一 Cloudflare 账号中；
3. 自动把加密备份发送到管理员配置的外部存储；
4. 首发采用手动本地加密备份并提供明确提醒、状态和演练流程，外部自动备份作为后续版本评估。

### 初步建议

建议选择第 4 项。第 2 项不能充分覆盖账号级灾难；第 3 项会明显扩大首发架构、凭据和兼容面。首发至少需要让非专业管理员清楚知道“尚无离线备份”、最近一次备份时间以及如何真实恢复。

### 状态

已确认。

### 项目所有者回答

首发采用手动加密备份，并清楚提醒最近备份时间、未备份风险和恢复演练方法；外部自动备份以后再评估。

### 确认结论

1. 首发不建设自动跨账号或外部存储备份。
2. 管理员主动下载并保存的本地加密容器是首发灾难备份方式。
3. 网页和运维文档需要明确最近备份时间、离线备份是否完成、长期未备份风险和恢复演练方法。
4. 在线 R2 备份制品不能被描述为已经覆盖 Cloudflare 账号级灾难。

### 后续仍需量化

- 推荐备份频率；
- 可接受的数据恢复点；
- 恢复完成时间目标；
- 备份密码或密钥丢失后的责任边界。

## 问题 07：下一个“可用”里程碑如何定义

### 当前背景

当前首发发布门槛把真实 Cloudflare 双模式、收发信、接近 20 MB、两个发信 Provider、五种通知、自动转发、备份恢复、旧系统迁移、浏览器矩阵、安全检查和非程序员部署等放在同一批关闭。即使功能代码已经很多，这种门槛仍可能让项目长期处于“什么都有，但没有一个被正式称为可用”的状态。

现在已经决定移除 KV，项目还可以进一步把“内部受控试运行”和“面向其他自托管者的正式首发”分成两个里程碑。这不会降低最终正式发布门槛，但会改变近期工作的优先级。

### 待确认问题

接下来的第一个项目目标应是哪一种？

1. 所有现有首发功能和外部集成全部验收后，才允许任何真实使用；
2. 先完成一套 R2 真实实例的核心闭环，供你和少量可信用户受控试运行；稳定后再完成面向其他部署者的正式首发；
3. 直接面向其他非专业用户发布公开测试版，边使用边补验收；
4. 只作为个人项目继续开发，暂不定义可用或发布里程碑。

### 初步建议

建议选择第 2 项。受控试运行仍必须先满足数据安全底线、真实收信、读信、核心发信、手动备份和可恢复性，但可以把五种通知、双 Provider 完整切换、旧系统迁移和完整浏览器矩阵等安排到正式首发阶段。

### 状态

已确认。

### 项目所有者回答

先完成一套 R2 真实实例的核心闭环，供项目所有者和少量可信用户受控试运行；稳定后再完成面向其他部署者的正式首发。

### 确认结论

1. 项目采用“受控试运行”和“正式首发”两个里程碑。
2. 近期优先级从继续增加功能改为关闭一套真实 R2 实例的核心使用闭环。
3. 受控试运行仍需满足数据安全和恢复底线，不能被称为无保护的线上测试。
4. 当前 23 项发布阻断项需要重新分类，不能全部继续阻塞受控试运行，也不能从正式首发门槛中静默删除。

### 近期规划影响

- 先完成真实初始化、Email Routing、Queue、核心收发和 R2 对象路径；
- 先确认稳定邮件大小边界，不再优先追求名义上的 20 MB；
- 先完成手动离线加密备份和真实空白资源恢复；
- 先建立试运行期间的故障记录、停止条件和数据退出方案；
- 公开部署、完整外部集成、浏览器矩阵和非程序员验收进入后续正式首发阶段评估。

## 问题 08：受控试运行是否必须带入旧系统数据

### 当前背景

项目已经实现旧 Simletter 数据迁移工具，但真实旧数据副本和远程资源迁移仍未演练。是否必须把旧账号、地址和历史邮件带入第一套试运行实例，会直接决定试运行是“全新开始”还是“迁移切换”，也影响实例初始化顺序、失败回退和时间安排。

### 待确认问题

第一套 R2 受控试运行实例应如何处理旧 Simletter 数据？

1. 全新开始，受控试运行不迁移旧数据；
2. 试运行先全新开始，旧数据迁移在独立资源演练，正式首发或以后再决定是否导入；
3. 受控试运行前必须完成真实旧数据迁移，旧数据是进入试运行的前置条件；
4. 只迁移账号、域名和地址，不迁移历史邮件。

### 状态

已确认。

### 项目所有者回答

全新开始，不迁移旧数据。

### 确认结论

1. 第一套 R2 受控试运行实例从空白数据初始化。
2. 真实旧 Simletter 数据迁移不属于受控试运行前置条件。
3. 不在已经产生新数据的试运行实例中临时设计新旧数据合并流程。
4. 旧系统迁移功能的长期产品归属仍需另行确认。

### 近期规划影响

- 受控试运行可以先完成初始化、真实收发、备份恢复和资源验证；
- 旧数据副本、迁移切换和迁移失败回退不进入近期关键路径；
- 当前已经完成的迁移代码和测试暂不删除，等待下一项决定。

## 问题 09：旧系统迁移能力是否继续作为正式产品功能

### 当前背景

虽然试运行不需要旧数据，项目已经为旧 Simletter 建立正式迁移 `0019`、迁移工具、KV/R2 双模式自检、失败场景和大量文档。继续保留意味着以后仍要维护旧格式读取、来源映射、对象迁移、对账和版本兼容；正式移除则能缩小发布和维护范围，但以后不能承诺直接导入旧系统。

### 待确认问题

旧 Simletter 数据迁移接下来应如何定位？

1. 继续作为正式产品功能，但不阻塞受控试运行；正式首发前再完成真实迁移验收；
2. 降级为仅供项目所有者按需使用的内部工具，不作为公开产品承诺；
3. 正式移除旧系统迁移功能、迁移账本和公开文档，不再维护；
4. 暂时冻结现有实现，等受控试运行稳定后再决定是否保留。

### 初步建议

建议选择第 4 项。它已经完成大量实现，现在立即删除收益有限；但在没有真实迁移需求时，也不值得继续占用受控试运行的时间。稳定后可根据是否存在实际迁移用户，再选择正式保留或移除。

### 状态

已确认。

### 项目所有者回答

冻结现有实现，等受控试运行稳定后再决定。

### 确认结论

1. 旧系统迁移不阻塞受控试运行。
2. 当前不继续建设，也不立即删除已经完成的迁移实现。
3. R2 单模式纠偏涉及迁移模块时，只进行必要的一致性调整。
4. 受控试运行稳定后，根据真实迁移需求重新决定正式保留、内部化或移除。

## 问题 10：手动备份可接受的数据恢复点

### 当前背景

手动离线备份只能恢复到最近一次管理员实际下载并保管的备份。如果 Cloudflare 账号、D1 和 R2 同时不可恢复，最近备份之后收到和发送的邮件可能丢失。必须先明确可接受的数据丢失窗口，才能设计提醒频率和判断手动方案是否现实。

### 待确认问题

发生最严重的账号级灾难时，首发最多可以接受丢失多久的新数据？

1. 最多 24 小时，需要管理员至少每天完成一次离线备份；

## 问题 11：是否长期正式支持两家域外发信 Provider

### 当前背景

当前产品正式支持 Resend 与 SMTP2GO，并包含域名级默认与备用路线、逐收件人状态、不同回调鉴权、幂等和“结果未知不重发”等逻辑。两家服务可以提供选择和有限故障切换，但也要求持续维护两套 API、事件协议、账号规则和真实验收环境。

受控试运行只需要先证明一条真实域外发信链路。正式产品是否长期承诺两家 Provider，会影响发信状态机、配置界面、文档和发布门槛。

### 待确认问题

Resend 与 SMTP2GO 接下来应如何定位？

1. 长期正式支持两家，并保留默认与备用故障切换；
2. 只选择一家作为正式 Provider，移除另一家和故障切换；
3. 受控试运行先验证一家，冻结另一家；稳定后再决定是否保留双 Provider；
4. 两家代码都保留，但只把其中一家列为正式支持，另一家不作兼容承诺。

### 初步建议

建议选择第 3 项。先用真实可取得的 Provider 完成发信闭环，避免两家外部服务同时阻塞试运行；稳定后依据故障切换价值和维护成本决定是否继续双支持。

### 状态

已确认。

### 项目所有者回答

长期正式支持两家，并保留故障切换。

### 确认结论

1. Resend 与 SMTP2GO 都是正式产品能力。
2. 域名级默认与备用路线及安全故障切换继续保留。
3. 不能以缩减维护范围为由删除任一家 Provider。
4. 两家真实 API、回调、失败、结果未知、重复和乱序场景都必须在正式首发前形成证据。

## 问题 12：双 Provider 是否都阻塞受控试运行

### 当前背景

### 待确认问题

受控试运行开始前，域外发信需要达到哪一层？

建议选择第 2 项，并在试运行界面与记录中明确当前只启用哪一家，不显示未经真实验证的备用路线为可用状态。
