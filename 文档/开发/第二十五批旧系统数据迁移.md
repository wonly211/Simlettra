# 第二十五批旧系统数据迁移

## 状态

本地闭环完成。

## 目标

使用旧系统数据副本，把已确认范围内的用户、域名、个人地址、邮件信息、正文、附件和星标迁移到当前 Simlettra。迁移工具只读取旧数据，可以重复执行，并提供检查点、失败报告和分类对账；正式迁移必须引用同一来源快照和规则版本的成功演练。

## 事实来源

- 旧系统只读仓库：`E:\SynologyDrive\github\Simletter`
- 旧系统参考提交：`9d016831ff2d862e38c08d9376a58327bc8933df`
- 当前需求：`11.01` 至 `11.06`
- 当前数据决定：数据-123 至数据-128
- 当前架构决定：ADR `0033`

## 已确认的旧系统结构

1. 旧 D1 的迁移来源主要是 `user`、`account`、`email`、`attachments` 和 `star` 表。
2. `user.email` 是旧用户主地址；同一用户的其他 `account.email` 是个人别名。域名从有效用户和地址中归纳，不迁移旧角色权限。
3. 邮件元数据保存在 `email`；正文对象键保存在 `email.body_key`，对象内容是包含 `html` 与 `text` 的 JSON。
4. 附件元数据保存在 `attachments`，对象键通常位于 `attachments/`；同一对象键可能被多条附件记录引用。
5. 正文对象键通常位于 `message-bodies/`。旧部署可以使用 KV 或 R2，但业务字段与对象键规则相同。
6. 旧系统不可靠保留原始 MIME。迁移邮件统一按 `structured_rebuilt` 标记，不伪装为完整原始邮件。
7. 旧密码使用单次 `SHA-256(salt + password)`，不符合当前慢速密码哈希基线。所有旧用户都记录为 `reset_required`，不把旧密码摘要迁入当前登录记录。
8. `email.type = 0` 表示收件，`email.type = 1` 表示已发送；`unread = 0` 表示未读，`unread = 1` 表示已读；`is_del = 1` 表示旧逻辑删除。

## 迁移范围

| 旧数据 | 当前目标 | 处理规则 |
| --- | --- | --- |
| `user` | 用户、主地址、默认地址偏好、密码迁移结果 | 有效且格式合法的用户进入迁移；密码必须重设；禁用状态保留 |
| 地址中的域名 | 邮件域名 | 统一执行当前 IDNA、Punycode 和小写规范化；重复域名只建立一次 |
| `account` | 主地址或个人别名、地址占用、显示名称和排序偏好 | 主地址由 `user.email` 判断；已删除地址不占用当前地址 |
| `email` | 物理邮件、投递、邮箱条目、个人状态、迁移来源质量 | 保留可表达的收发信息、时间、邮件关系和旧删除状态；结构化正文单独迁移 |
| 正文对象 | 当前正文对象与对象登记 | 读取 JSON，校验大小与摘要后写入当前 KV/R2；缺失或损坏进入失败报告 |
| `attachments` 与对象 | 当前附件对象与对象登记 | 保留名称、类型、大小、处置方式和内容编号；对象回读校验后提交 |
| `star` | 当前用户星标状态 | 只为仍有权访问的迁移邮箱条目建立星标 |

## 明确不自动迁移

旧角色权限、注册密钥、复杂设置、Telegram 通知、外部转发、Resend 配置、本地草稿、旧登录会话和运行时缓存均不自动迁移。旧全域收信规则和未分配来信不在首发自动迁移范围内；遇到相关数据时进入跳过统计和报告，不静默改变归属。

## 迁移安全边界

1. 迁移输入必须是数据副本或由只读命令生成的快照；工具不更新、删除或格式化旧 D1、KV、R2。
2. 来源快照摘要覆盖旧 D1 数据和对象清单；来源发生变化后必须重新演练。
3. 正式迁移只允许写入已经初始化并应用当前正式迁移的目标系统。
4. 来源映射不可修改。相同快照重复执行时复用已有结果；相同旧编号的内容摘要变化时停止并报告冲突。
5. 邮件及对象必须在当前目标结构中满足完整性条件后才建立可见邮箱条目。
6. 迁移失败不能删除或覆盖已有目标数据；失败项保留有限错误、来源编号和可重试状态，不记录正文、附件内容或凭据。

## 本地快照契约

迁移分为“读取旧系统”和“写入新系统”两段，二者不在同一命令中进行。`snapshot` 只使用 Wrangler 的查询与对象读取命令访问旧 D1、KV 或 R2，把以下内容写入本地快照目录：

1. `迁移清单.json`：记录旧系统版本、参考提交、存储模式、迁移规则版本、各实体数量、每个分卷与对象的大小和 SHA-256。
2. `表/`：按主键顺序保存 `user`、`account`、`email`、`attachments` 和 `star` 的 NDJSON 分卷。
3. `对象/`：只保存被有效正文或附件记录引用的对象，不扫描或复制运行时缓存及无引用对象。
4. `快照报告.json`：列出缺失表、无效字段、重复地址、缺失对象和明确跳过项。

来源快照摘要由固定来源元数据和全部排序后的分卷、对象摘要共同计算，不包含创建时间和本地路径。同一份旧数据重复生成快照时得到相同摘要。

## 迁移账本契约

正式迁移 `0019-旧系统数据迁移.sql` 建立以下七类事实：

| 表 | 作用 |
| --- | --- |
| `migration_runs` | 保存演练或正式执行、来源摘要、规则版本、目标版本、状态和演练证据 |
| `migration_checkpoints` | 按用户、域名、地址、邮件、正文、附件和星标保存游标与数量 |
| `migration_source_mappings` | 保存旧稳定编号、内容摘要和确定的新编号，写入后不可修改 |
| `migration_failures` | 保存有限错误码、摘要、重试次数和解决状态 |
| `migration_reconciliations` | 保存七类数据的预计、成功、跳过、失败和最终对账结果 |
| `migrated_message_sources` | 明确迁移邮件是原始 MIME 还是结构化重建 |
| `migration_user_password_results` | 明确旧密码处理结果，不保存旧密码、盐或摘要 |

正式目标不会执行一次会写入数据的“演练”。演练在独立临时目标完成后生成 `迁移演练报告.json`；正式执行验证报告摘要、来源快照、旧版本、参考提交、规则版本和目标迁移版本完全一致，再在正式 D1 中登记一条外部演练证据，并让正式运行引用它。来源或规则变化后旧报告立即失效。

## 五阶段执行顺序

1. **预检**：验证快照、目标迁移版本、唯一管理员、地址冲突、预计对象字节和演练报告。
2. **身份**：迁移域名、用户、主地址、别名、地址占用和用户默认策略；来源映射与业务数据在同一 D1 批次提交。
3. **内容**：按邮件准备结构化正文和附件对象，写入目标 KV/R2 后回读核对大小与 SHA-256。
4. **可见提交**：对象全部核对后，在同一 D1 批次写入物理邮件、邮件头、投递、邮箱条目、个人状态、完整性和来源质量，再登记逻辑存储用量。
5. **收口**：重建邮件关系与搜索，完成七类对账；所有对账匹配且没有待处理失败时才能把运行标记为成功。

D1 和对象存储不能组成跨资源原子事务。对象写入成功而 D1 提交失败时，重复执行使用同一确定性对象键并重新回读；D1 提交成功后重复执行通过不可变来源映射复用结果。不能确认结果时停止，不自动生成第二份邮件。

## 稳定映射与冲突规则

1. 目标编号和对象键由来源系统、快照摘要、实体类型、旧稳定编号和内容摘要确定，不使用每次运行随机值。
2. 旧主地址与当前唯一管理员主地址相同时，旧用户映射到现有管理员，保留当前管理员密码和身份；旧角色表不参与判断。
3. 其他有效旧用户建立为普通用户。旧 `status = 1` 映射为禁用；旧 `is_del = 1` 用户及其从属数据跳过，不让已删除账号重新出现。
4. 迁移用户写入不可登录的随机当前格式占位凭据，`must_change = 1` 且没有临时密码有效期。管理员必须使用现有密码重置功能生成一次性临时密码后，用户才能登录。
5. 旧 `is_del = 1` 邮件没有可靠删除时间，不能转换成当前 30 天垃圾箱，因此跳过并计入报告，不把用户已经删除的邮件重新显示。
6. 已删除个人别名可以作为退休地址与已结束绑定迁移，以便保留仍可迁移邮件的实际投递地址，但不建立当前地址占用和可用发件身份。
7. 相同规范地址已经被不同目标主体占用、旧对象缺失或摘要不一致、同一来源编号内容变化时，该项失败且不覆盖现有目标数据。

## 工具命令契约

```powershell
node tools/旧系统数据迁移.mjs snapshot --source-config 旧系统wrangler配置 --source-database SIMLETTRA_DB --source-storage-mode r2 --source-bucket 旧存储桶 --output 旧系统快照
node tools/旧系统数据迁移.mjs validate --snapshot 旧系统快照
node tools/旧系统数据迁移.mjs rehearse --snapshot 旧系统快照 --target-config wrangler.jsonc --target-database DB --target-storage-mode r2 --target-bucket simlettra-mail --report 迁移演练报告.json
node tools/旧系统数据迁移.mjs apply --snapshot 旧系统快照 --rehearsal-report 迁移演练报告.json --target-config wrangler.jsonc --target-database DB --target-storage-mode r2 --target-bucket simlettra-mail --confirm MIGRATE_LEGACY_COPY
```

KV 来源使用 `--source-binding`，KV 目标使用 `--target-binding`。旧来源和新目标的存储模式彼此独立，可以在 KV 与 R2 之间迁移。远程读写必须显式增加 `--source-remote` 或 `--target-remote`；默认只操作 Wrangler 的本地持久化资源。

## 当前进展

正式迁移 `0019-旧系统数据迁移.sql`、迁移工具和双模式自检已经完成。合成旧数据包含 2 名用户、3 个地址、3 封邮件、1 个附件、1 个星标和 4 个旧对象；KV 与 R2 目标均通过快照稳定性、演练、正式迁移、重复执行、搜索、会话、七类对账、对象校验和外键检查。每种模式还验证了 6 类拒绝场景。

当前结论只证明本地工具链和迁移契约闭环，不等同于真实用户旧数据副本演练，也不等同于真实 Cloudflare Free 远程 D1、KV 或 R2 的规模、权限和中断恢复验证。正式上线前必须使用脱敏的数据副本在独立远程演练目标执行完整流程。
