- 完成日期：2026-08-12

- 对应决策：[0027 以独立操作协调通知、外部邮箱验证与来信转发](../架构决策记录/0027-以独立操作协调通知外部邮箱验证与来信转发.md)

## 本批目标

用户可以为自己的个人邮箱和当前有权查看的组织邮箱建立外部通知订阅。邮件完整可见后，系统通过独立后台任务把发件人、收件人、主题和完整正文推送到 ntfy、Gotify、WxPusher、Telegram 或 Bark；通知失败不能影响原邮件。

## 验收条件

1. 用户只能查看、创建、暂停、恢复和删除自己的通知订阅，不能读取或操作他人的订阅。
2. 每个订阅可以覆盖全部个人地址、指定个人地址和当前有权查看的组织地址；保存和执行时都重新检查权限。
3. Gotify 应用令牌、Bark 设备密钥、ntfy 访问令牌、WxPusher AppToken 和 Telegram Bot Token 使用 `CONFIG_KEY` 加密后写入 D1，不进入 Queue、普通日志或网页响应。
4. 外部来信和系统内直投邮件都只在完整可见后创建通知操作；同一实际投递与同一订阅最多建立一个权威操作。
5. 通知内容包含发件人、收件人、抄送、实际投递地址、主题和完整正文，不发送附件；HTML 正文只提取安全可见文本。
6. ntfy 超过 4,096 字节、Telegram 超过 4,096 个字符、WxPusher 超过 40,000 个字符时明确失败，不截断正文，也不调用外部服务。
7. Gotify 和 Bark 没有统一固定正文上限，发送完整内容并以目标服务的明确响应为准；目标返回容量错误时保存可见失败结果。
8. 明确未接受且可重试的响应最多自动尝试三次；请求发出后没有响应或响应无法判断时标记“结果未知”，不盲目重复推送。
9. 用户被禁用、订阅暂停或删除、个人地址失效、退出组织、组织停用、邮件损坏或永久隐藏后，尚未提交的通知被取消。
10. 网页可建立五种通道的订阅、选择邮件来源、暂停或删除订阅，并查看最近通知的成功、失败、取消或结果未知状态。

## 实现边界

### 本批包含

- 五种首发通知通道的用户级设置和加密凭据。
- 个人地址及组织地址的订阅范围。
- D1 权威通知操作、尝试历史与 Queue 执行。
- 通知状态页面和通道边界测试。

### 本批不包含

- 浏览器系统通知；需求 `10.01` 已明确不进入首发。
- 外部邮箱验证与自动转发；这两项使用相同的独立操作原则，但属于后续纵向切片。
- 通知模板、正文摘要模式、附件推送和管理员代管个人订阅。
- 五家服务真实账号或自建实例的远程联调；本批先完成官方契约和高保真边界测试。

## 官方接口核验

核验日期：2026-08-12。

1. [ntfy 官方发送文档](https://docs.ntfy.sh/publish/)支持向服务根地址提交 JSON，并使用 `topic`、`title` 和 `message`；访问令牌使用 Bearer 鉴权。官方默认单条消息正文最多 4,096 字节，更长内容会被当作附件，因此 Simlettra 在调用前拒绝超限内容，避免违反“不发送附件”。
2. [Gotify 官方推送文档](https://gotify.net/docs/pushmsg)使用 `POST /message` 和 `X-Gotify-Key` 应用令牌，正文使用 `message` 字段。Gotify 是可自行部署的服务，官方没有规定所有实例统一的正文上限。
3. [WxPusher 官方文档](https://wxpusher.zjiecode.com/docs/)使用 `POST https://wxpusher.zjiecode.com/api/send/message`，请求包含 `appToken`、`content`、`summary`、`contentType` 和 `uids`，顶层及逐接收者 `code` 为 `1000` 表示成功；`content` 最多 40,000 个字符，`summary` 最多 100 个字符。
4. [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage)使用 `POST https://api.telegram.org/bot<token>/sendMessage`，`sendMessage.text` 最多 4,096 个字符。Simlettra 使用纯文本且不启用外部内容解析。
5. [Bark 官方教程](https://github.com/Finb/Bark/blob/master/docs/en-us/tutorial.md)支持向 `/push` 提交包含 `device_key`、`title` 和 `body` 的 JSON，也支持自行部署 Bark Server；官方没有规定所有实例统一的正文上限。

## 风险控制

1. 通知操作只保存来源投递、订阅、内容版本、字节数和 SHA-256，不保存正文副本。
2. 通知任务执行时从当前完整邮件对象重新生成正文，并核对操作中冻结的大小和摘要。
3. 自建服务地址只接受不含账号、查询串和片段的 HTTPS 地址，令牌始终放在请求头或 JSON 正文而不是网址中。
4. 外部响应只保存状态码、服务返回编号和简短错误类别，不保存请求正文、完整响应、凭据或服务令牌。
5. 网络异常发生在请求已经发出之后时按“结果未知”收口；只有能够明确判断未接受的限流响应才进入自动重试。

## 完成结果

1. 正式迁移 `0013-外部通知网关.sql` 已建立通知订阅、订阅范围、加密凭据、权威通知操作和尝试历史五张表，并加入权限、身份和状态流转约束。
2. 用户可以在网页建立 ntfy、Gotify、WxPusher、Telegram 和 Bark 订阅，选择全部个人邮箱、指定个人地址或当前组织地址，并暂停、恢复或删除自己的订阅。
3. 外部来信和系统内直投都在邮件完整可见事务中建立防重通知操作与 D1 权威后台任务；通知失败、取消或结果未知不改变原邮件。
4. 通知任务执行前重新检查用户、订阅、地址、组织成员和邮件完整性，重新读取正文对象并核对大小与 SHA-256；正文和附件不进入 D1 操作、Queue 或日志。
5. 五种通道请求格式和成功响应已经按官方接口分别实现；已知正文上限在请求前检查，Gotify 与 Bark 以目标服务的明确响应为准，任何通道都不截断正文。
6. 通知凭据使用独立配置主密钥和 AES-GCM 加密保存，网页响应、审计和普通日志不返回凭据。
