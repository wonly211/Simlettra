# 第四十五批部署配置静态安全审查

## 文档状态

- 状态：当前，已完成本地静态审查
- 完成日期：2026-08-14
- 对应需求：`2.03`、`2.04`、`2.06`、`12.10`、`12.13`
- 对应验收：验收-01、验收-19、验收-28
- 工程变化：加强生产构建、部署前配置检查和统一质量门槛；没有改变产品行为、部署单元、数据结构或依赖

> 后续更新：需求变更 `0011` 与 ADR `0049` 已把 Cloudflare 连接 GitHub 设为正式发布默认入口，并允许唯一管理员在控制台查看 `INIT_KEY` 与 `CONFIG_KEY`。本记录中“普通 vars 只能包含 `STORAGE_MODE`”仅指仓库和生成部署配置不能携带运行密钥；管理员在 Cloudflare 控制台设置的文本变量由 `keep_vars: true` 保留。

## 目标

在不创建或修改真实 Cloudflare 资源的前提下，确认 R2 与 KV 两种部署配置具备相同的必要绑定、Queue、Cron 和网页回退规则，并阻止模板占位编号、本机绝对路径或普通变量中的敏感配置进入正式部署路径。

本批只证明本地配置和产物结构正确，不证明真实资源存在、权限充分、套餐为 Free，也不代替远程部署和人工安全签署。

## 完成内容

1. 安全构建在密钥扫描前清除 Cloudflare Vite 插件写入产物配置的 `configPath` 和 `userConfigPath`，避免把本机项目绝对路径带入最终部署配置。
2. 新增 `tools/部署配置自检.mjs`，检查 Worker 入口、兼容日期、`STORAGE_MODE`、D1、KV/R2 互斥绑定、Queue producer 与 consumer、每小时 Cron、单页应用回退和 `/api/*` Worker 优先规则。
3. 本地模板验收允许源配置保留全零资源编号；真正的 `pnpm deploy:r2` 与 `pnpm deploy:kv` 在调用 Wrangler 前使用严格模式，发现全零 D1 或 KV 编号就立即停止。
4. `pnpm test:deployment-config` 已加入 `pnpm check`，会分别安全构建 R2 与 KV 产物并检查结构。部署命令仍会在完整质量门槛后重新构建目标模式，再执行严格检查。
5. 仓库和生成部署配置中的 `vars` 只允许非敏感的 `STORAGE_MODE`；`INIT_KEY` 与 `CONFIG_KEY` 由唯一管理员在 Cloudflare 控制台以可查看文本变量管理，第三方动态凭据由管理员在网页中管理并加密保存到 D1。

## 仍需真实验收

1. 部署者创建真实 D1、KV 或 R2、Queue，并正确替换资源名称和编号。
2. 分别确认两套目标账号使用 Cloudflare Free，绑定权限、Email Routing、Queue consumer 和 Cron 在远程环境生效。
3. 使用管理员可见的真实运行时变量完成初始化、管理员恢复、配置加密和轮换演练。
4. 按[发布前安全人工检查表](../验收/发布前安全人工检查表.md)复核远程配置、日志和控制台权限，并保留脱敏签署记录。

因此，验收-01、验收-19和验收-28继续保持原状态，本批不改变当前“不发布”判断。
