# 澄笺 | Simlettra 第四十六批多地址收信归并与补交付

## 文档状态

- 阶段：首发本地验收缺口收口
- 状态：已完成
- 完成日期：2026-08-14
- 依据：需求 `5.04`、`5.05`、`5.12`、`12.05`、`12.09`，ADR `0016`、`0023`、`0047`
- 数据变化：没有新增迁移；复用 `receive_operation_routes`、`message_deliveries`、`mailbox_entries` 和 `background_tasks`

## 发现的问题

原实现把实际投递地址放进收信有界指纹。Cloudflare 为同一原始邮件的两个本地地址分别调用 Worker 时，会建立两个收信操作、两封物理邮件和两份对象内容。这与需求 `5.05` 及 ADR `0016` 不一致，也使验收-06的“同封多本地地址”一直没有专项证据。

## 完成内容

1. 物理邮件有界指纹改为“一小时窗口、信封发件人和原始 MIME 摘要”，实际收件地址成为同一收信操作下的独立冻结路由。
2. 最终可见事务读取并提交全部已接受路由；同一用户的多个地址共用一个个人邮箱条目，不同用户或组织分别建立邮箱条目。
3. 每条路由仍有独立实际投递事实、通知匹配、个人转发匹配和完成状态；不同邮箱所有者各自计入一次逻辑内容用量。
4. 物理邮件已经可见时，新路由建立 `receive_route_commit` D1 任务，由 Queue 读取已校验原始 MIME 并补交付，不在 Email Worker 中同步解析大邮件。
5. 同一地址的重复事件不会新增路由。首次解析或补交付的 Queue 发送失败后，重投会再次唤醒既有任务，Cron 仍可补投。
6. 解析失败或对象损坏时会释放所有已登记邮箱所有者的逻辑预留，不再只处理第一条路由。

## 自动化证据

`incoming-mail.test.ts` 现有 15 项测试全部通过，其中三项专项回归确认：

1. 首次 Queue 发送失败后，同一地址重投会重新唤醒原解析任务；
2. 解析前命中同一用户的主地址和别名，只建立一个收信操作、一封物理邮件、一个邮箱条目和两条实际投递；
3. 物理邮件可见后命中另一名用户，即使补交付 Queue 首次发送失败，重投仍能完成补交付，最终只有一封物理邮件且两名用户分别可见。

## 当前边界

1. 本批修正本地实现与既有需求、数据模型的冲突，不改变验收-06的“部分通过”状态，因为真实 Cloudflare Free 尚未投递同封多地址邮件。
2. 一小时内信封发件人和原始 MIME 字节完全相同的不同地址事件会共享物理邮件；窗口外相同字节仍形成新邮件。
3. 真实 Email Routing 的多地址事件顺序、并发、原始字节一致性、Queue 重试和接近 20 MB 成本仍是发布门槛。
4. 没有新增浏览器界面，因此本批不重复视觉验收。
