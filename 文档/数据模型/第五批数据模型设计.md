## 设计范围

本设计把数据-80 至数据-98 转换成 D1 中的服务配置、域名发信路线、发送路线快照、通知、外部邮箱验证和个人来信转发模型。

它同时落实三项新结论：

1. `init_key` 与 `CONFIG_KEY` 分离。`init_key` 只用于初始化与管理员恢复；`CONFIG_KEY` 只用于加密 D1 中的动态服务凭据。唯一系统管理员可以在 Cloudflare 控制台查看两者，项目不以隐藏管理员自己的密钥为安全目标。
2. 单一 Provider 快照改为域名级优先路线。每名站外收件人根据冻结路线选择最靠前且兼容的服务；只有能证明前一家未接受时，才可切换备用服务。
3. 首发 Provider 类型只允许 Resend 和 SMTP2GO；Cloudflare Email Sending 不进入配置、路线、快照、尝试或事件表。

迁移草案仍位于“迁移草案”目录，不是生产 `migrations/` 历史。由于前四批也尚未进入生产，`0005` 在空白验证数据库中重建第三批临时的单 Provider 发信表，使第五批验证的是最终候选结构；建立正式工程骨架时必须把这段草案重组为连续、可升级的 Wrangler 迁移。

## 新增与重建的表

| 表 | 所属模块 | 保存内容 | 权威性 |
| --- | --- | --- | --- |
| `outbound_provider_configs` | 域外发信网关 | 版本化 Provider 配置、公开选项、加密凭据、加密主密钥版本和启停状态 | 服务配置权威来源 |
| `domain_outbound_routes` | 域外发信网关 | 每个域名的一版发信路线及其当前状态 | 域名发信策略权威来源 |
| `domain_outbound_route_entries` | 域外发信网关 | 路线中的优先顺序与 Provider 配置版本 | 路线顺序权威来源 |
| `outbound_route_snapshots` | 域外发信网关 | 发送、转发或验证投递接受时冻结的路线版本 | 执行路线事实 |
| `outbound_route_snapshot_entries` | 域外发信网关 | 冻结后每个候选服务的顺序、类型和大小上限 | 执行候选事实 |
| `outbound_submission_attempts` | 域外发信网关 | 所有使用 Provider 的外部提交尝试、结果和有限错误 | 外部副作用账本 |
| `outbound_submission_attempt_recipients` | 域外发信网关 | 一次普通发送尝试包含哪些逻辑收件人及切换原因 | 逐收件人尝试关系 |
| `outbound_provider_events` | 域外发信网关 | 已验证回调的最小不可变事件与匹配结果 | Provider 事件账本 |
| `send_recipient_route_progress` | 草稿与发信 | 每名站外收件人的冻结路线、下一个候选位置和最后结果 | 自动切换进度权威来源 |
| `notification_subscriptions` | 通知 | 用户通知订阅、通道和启停状态 | 订阅权威来源 |
| `notification_subscription_scopes` | 通知 | 全部个人地址、指定个人地址或指定组织地址的来源范围 | 通知范围权威来源 |
| `notification_subscription_secrets` | 通知 | 加密后的通知端点凭据 | 通知凭据权威来源 |
| `notification_operations` | 通知 | 某次邮件投递与某个订阅的唯一通知操作 | 通知防重账本 |
| `notification_attempts` | 通知 | 每次通知提交的状态、时间和有限错误 | 通知执行历史 |
| `external_email_targets` | 转发 | 用户拥有的外部目标邮箱及验证状态 | 外部目标权威来源 |
| `external_email_verifications` | 转发 | 一次性验证码哈希、有效期、失败次数与验证投递状态 | 验证事实 |
| `mail_forwarding_rules` | 转发 | 用户个人来信转发规则与版本 | 转发规则权威来源 |
| `mail_forwarding_rule_addresses` | 转发 | 指定个人地址范围的规则关系 | 转发范围权威来源 |
| `mail_forward_operations` | 转发 | 来源邮件、实际投递、规则、目标和冻结内容摘要 | 转发防重账本 |
| `mail_forward_attempts` | 转发 | 每次站外转发提交、Provider 和切换原因 | 转发执行历史 |

为消除单 Provider 假设，`0005` 重建第三批的 `send_operations`、`send_idempotency_keys`、`send_recipients` 和 `send_recipient_status_history`。它们保留草稿、幂等、站内投递、已发送条目、逐收件人状态和最终 MIME 的既有边界，但不再把单一 `provider_type`、配置引用和最小 Provider 上限作为整封邮件的唯一事实。

## 服务配置与加密凭据

`outbound_provider_configs` 是不可变版本行。管理员更改连接参数或密钥时，不直接覆盖旧行，而是为同一个 `configuration_key` 创建递增版本。每行保存：

1. `provider_type`：只允许 Resend 或 SMTP2GO；
2. 用于连接和能力判断的非敏感参数摘要；
3. `AES-GCM-256` 密文、12 字节随机值、加密主密钥版本和凭据更新时间；
4. `active`、`disabled` 或 `retired` 状态。

动态凭据明文仅在当前系统管理员通过服务端授权后、当前请求的必要期间出现。D1、审计、任务和普通日志只保存密文或安全摘要。`CONFIG_KEY` 不进入 D1 或 GitHub；它不能由 `init_key` 派生，也不能反过来用于管理员恢复。唯一系统管理员可以在 Cloudflare 控制台直接查看和管理两把运行时变量。

## 域名发信路线与冻结快照

`domain_outbound_routes` 是域名路线版本，`domain_outbound_route_entries` 是其从零开始的服务顺序。一个域名同一时刻只有一条 `active` 路线；修改路线建立新版本并把旧版标记为 `superseded`。

一旦用户发送邮件、系统转发邮件或系统投递外部邮箱验证码，就创建 `outbound_route_snapshots` 及其条目。快照复制：

1. 当时路线版本和完整条目顺序；
2. 每家服务配置版本和 Provider 类型；
3. 当前收件条件下可接受的最终负载上限；
4. 用于核对的不含密钥摘要。

后续管理员增加、删除或排序服务，不修改旧快照。管理员停用某个配置时，旧快照仍可解释历史；尚未提交的收件人只能跳过已停用服务并寻找该快照内的下一家兼容服务。

## 普通发送与自动切换

每个 `send_recipients` 仍是一个最终去重后的收件人。站外收件人对应一条 `send_recipient_route_progress`，保存冻结路线、当前候选位置、最后选中配置、最后尝试和有限切换原因。

`outbound_submission_attempts` 在网络调用前建立，并引用一条冻结路线条目。多名能使用同一服务的收件人可以关联到同一次尝试；`outbound_submission_attempt_recipients` 对每名收件人保存这是首次、同 Provider 安全重试、幂等重试还是备用切换，以及备用切换原因。

自动切换规则为：

1. 每名收件人在发送接受时，必须有至少一家候选服务接受完整最终 MIME 与收件条件；否则整次发送不接受。
2. 首先使用路线中优先且兼容的服务。默认服务的当前有效大小上限不兼容时，可以直接选择后续兼容服务。
3. 只有 Provider 明确未接受，且错误属于服务不可用、服务限制不兼容、服务端临时拒绝或配置停用时，才推进到下一个候选服务。
4. 请求已经发出但响应丢失、连接中断或其他无法判断的结果，收件人进入 `unknown`，不创建备用尝试。
5. 地址错误、全局大小超限、发件权限失效等本地确定性错误直接失败，不切换。

`outbound_provider_events` 仍按“Provider 类型加 Provider 事件编号”唯一。事件只能关联到 Provider 类型一致的尝试和收件人；终态不被旧事件覆盖。

## 通知

通知订阅属于一个用户。`notification_subscription_scopes` 区分三种范围：

1. 该用户全部个人地址；
2. 指定个人地址；
3. 指定组织共享地址。

组织范围并不赋予新权限；任务执行前必须重新检查当前成员关系。`notification_subscription_secrets` 保存加密端点配置。通知操作以“实际投递加订阅”唯一，并记录邮件对象集合版本、负载字节数和摘要，而不是复制正文。通知尝试只保存状态和安全错误。正文超过具体通道上限时，必须明确失败，不能静默截断。

## 外部邮箱验证与来信转发

外部目标邮箱由 `external_email_targets` 保存，按“用户加规范邮箱”唯一。它只能从 `pending` 变为 `verified`、`expired`、`disabled` 或 `deleted`。`external_email_verifications` 保存验证码哈希、过期时间、失败次数、验证使用时间和投递路线快照；原始验证码不进入 D1、URL 或日志。

转发规则只允许 `all_personal` 和 `selected_personal_addresses` 两类范围。规则引用已验证目标邮箱并带版本号。指定范围时，`mail_forwarding_rule_addresses` 只保存该用户个人地址的稳定编号；组织地址不能写入该表。

`mail_forward_operations` 以“物理邮件、实际投递、规则版本和目标邮箱”唯一，冻结原邮件内容摘要、目标地址、规则版本、转发跳数和发信路线快照。转发尝试记录所选 Provider、路线顺序、结果和切换原因。邮件本身写入稳定转发标记；发现本系统标记、跳数超限或目标属于系统管理域名时，操作被拒绝，不能形成循环。

## 状态和权限边界

1. 订阅、目标、规则、Provider 配置可以被停用或删除；执行前重新检查当前状态，未提交操作可取消。
2. 已提交到外部服务的通知、验证邮件或转发不能撤回，但后续重试必须停止。
3. 通知和转发在来源邮件具有 `ready` 完整性状态后才建立操作；失败不会影响物理邮件、实际投递或邮箱条目。
4. 用户只能管理自己的通知、目标、规则和结果。系统管理员管理 Provider 配置并查看服务健康汇总，但不通过运维表读取正文、通知端点明文或外部邮箱验证码。
5. 系统管理员可以查看和维护 Provider 明文凭据，这是已确认的配置管理能力；它不改变个人邮件正文与单封个人邮件删除的现有边界。

## 关键唯一与一致性约束

1. 同一逻辑 Provider 配置的版本号唯一；同一密文必须带有效算法、12 字节随机值和主密钥版本。
2. 每个域名同一时刻最多一条启用路线；路线内优先顺序唯一且至少有一个条目。
3. 同一执行对象只拥有一份路线快照；路线快照条目顺序唯一。
4. 同一发送操作内最终收件人去重键唯一；每名站外收件人最多一条路线进度。
5. 同一 Provider 事件只能保存一次；Provider 事件、尝试和收件人必须属于同一 Provider 类型和发送操作。
6. 同一通知订阅和实际投递只有一个通知操作；同一操作内尝试序号唯一。
7. 同一用户和规范外部邮箱只有一份当前目标；验证码只保存摘要且一旦成功不能再次使用。
8. 同一转发规则、实际投递、目标和规则版本只有一个转发操作；同一转发操作内尝试序号唯一。

## 验证要求

1. 从第一批到第五批顺序执行迁移草案，验证 D1/SQLite 结构可建立且外键检查为零。
2. 验证配置凭据不能插入明文形状、随机值长度和主密钥版本必须正确，`init_key` 不出现在任何凭据字段。
3. 验证路线顺序、当前路线唯一、冻结快照不可改写和路线修改不影响旧快照。
4. 验证数据库拒绝 Cloudflare Email Sending 类型；一个 10 MiB 最终 MIME 默认选择 Resend，没有兼容候选时不能接受发送。
5. 验证明确未接受时可登记备用切换，结果未知时不能登记备用切换。
6. 验证通知操作防重、组织退出后的执行取消、通知正文不在操作表中复制。
7. 验证验证码哈希、有效期、失败次数、一次性完成和普通用户目标唯一性。
8. 验证个人范围限制、转发防重、转发环路拒绝、转发不占用普通发送操作和外部失败不删除原邮件。

本地 SQLite 验证通过后，仍需要在真实 Cloudflare D1、Worker、Queue 以及 Resend、SMTP2GO 测试账号中验证 Web Crypto、密钥轮换、备用服务、回调、容量、网络中断和多地区并发行为。
