## 检查范围

本轮重点检查了 Worker 入口、网页工程、数据库初始化、认证授权、邮件收发、正文与附件存储、全域收信、发信回调、部署脚本和现有测试。

旧系统行为只用于提供证据，不自动成为新系统需求或架构。

## 旧系统整体形态

旧系统由两个工程组成：

1. `mail-vue`：Vue 3、Vite、Pinia、Element Plus 组成的单页网页应用。
2. `mail-worker`：Hono、Drizzle ORM、D1、KV/R2 组成的 Worker 后端。

构建时先生成网页静态资源，再由同一个 Worker 提供网页、接口、附件、收信和定时任务。这说明“单 Worker 提供完整应用”已经有可运行经验，但旧工程内部仍存在较强耦合。

## 值得保留的经验

1. **单部署产物**：网页资源和 Worker 一起部署，符合新需求的单 Worker 边界。
2. **元数据与对象分离**：D1 保存邮件可查询信息，正文和附件放入 KV 或 R2，方向正确。
3. **存储适配层**：`r2-service.js` 已经尝试用同一接口覆盖 KV 与 R2。
4. **邮件先隐藏再完成**：收信时先使用 `SAVING` 状态，完成后再改为可见状态，体现了避免半封邮件的意识。
5. **部署模式测试**：旧测试覆盖 D1+KV、D1+R2 资源绑定和部署脚本，对新部署工具有参考价值。
6. **对象引用清理**：正文和附件删除前检查是否仍被其他邮件引用，说明旧系统已经遇到共享对象生命周期问题。
7. **品牌资源可独立评估**：旧网页中的印章、字形和视觉资源可以在新界面设计阶段单独决定是否复用，不需要继承旧组件。

## 必须重做的问题

### 数据结构与升级

1. 数据表通过初始化请求中的 `CREATE TABLE IF NOT EXISTS` 建立，并夹杂旧数据格式化逻辑，没有独立的版本化迁移链。
2. 大量状态使用整数和单表字段表达，邮件实体同时承担物理邮件、用户副本、文件夹状态和发信状态，无法自然支持组织成员各自的已读、星标和垃圾箱状态。
3. 收件人、抄送和密送以 JSON 文本保存在邮件行中，不利于按收件人组合搜索和精确权限判断。
4. 没有独立的域名、组织、组织成员、会话、审计、异步任务和数据保留模型。

### 收信可靠性

1. 收信会把完整原始邮件读入内存后再解析，缺少明确大小检查和阶段性资源预算。
2. 附件写入失败后只记录错误，随后仍将邮件标记为接收完成，可能出现正文可见但附件丢失。
3. 没有针对重复投递建立数据库唯一约束或稳定去重编号。
4. 定时任务会把遗留 `SAVING` 邮件直接改成可见状态，没有先检查正文和附件对象是否齐全。

### 发信可靠性

1. 旧流程先调用外部发信服务，之后才保存已发送邮件。若外部已经接受而 D1 写入失败，系统会缺少发送记录，重试还可能重复发送。
2. 站内与站外收件人主要按“是否全部站内”分支处理，不能完整表达一次混合发送的逐收件人结果。
3. Resend 回调入口未验证签名或来源，任何请求都可能尝试修改发信状态。
4. 没有通用的发信操作编号、尝试记录、结果未知状态和供应商能力声明。

### 认证与权限

1. 密码使用“随机盐加 SHA-256”快速哈希，不符合新需求要求的慢速密码哈希。
2. JWT 由项目自行实现，令牌保存在浏览器 `localStorage`，扩大脚本注入后的令牌泄露风险。
3. 权限通过 HTTP 路径前缀和硬编码数组匹配，业务规则与路由强耦合。
4. 管理员或拥有“全部邮件查看”权限的角色可以读取普通用户邮件正文，与当前需求基线冲突。
5. 旧系统提供多角色、多权限体系，而新需求只保留一个系统管理员和普通用户，不应迁移旧权限模型。

### 前端与草稿

1. 草稿主要保存在浏览器 IndexedDB 中，无法满足服务端保存和跨设备继续编辑要求。
2. 页面、状态仓库和接口模块按旧功能逐步增长，缺少围绕新业务模块的清晰边界。
3. 登录状态依赖前端是否存在令牌，不能代替服务端会话和资源权限检查。

## 对新架构的直接启示

1. 保留“单 Worker + D1 + 对象存储”的大方向，但完全重建数据模型和状态流程。
2. 物理邮件、投递目标、邮箱视图和成员个人状态必须分开建模。
3. 跨 D1 与对象存储的操作必须使用状态机、幂等编号和修复任务，不能依赖顺序调用恰好成功。
4. 外部发信之前先建立持久化发送操作，外部结果与内部已发送视图分别记录。
5. 身份认证改为慢速密码哈希、随机会话令牌和受保护 Cookie。
6. 旧密码哈希安全性不足，不应直接迁移；迁移用户需要重设密码。
7. 旧系统测试可以帮助发现部署和对象生命周期场景，但新系统需要围绕当前需求重新编写测试。

## 结论

旧系统证明了 Cloudflare 单 Worker 邮箱应用的基本可行性，也暴露了“页面驱动接口、单表邮件模型和顺序式多资源写入”在功能扩大后的维护成本。新系统应保留平台经验，放弃旧数据模型、旧权限体系和关键写入流程，不进行逐文件翻译。
