# 澄笺 | Simlettra 架构约束与质量属性

## 文档状态

- 状态：当前
- 建立日期：2026-08-09
- 依据：`需求基线-0001`
- 用途：约束候选架构和技术路线，不直接指定代码实现

## 不可改变的架构约束

以下约束已经由需求基线确定，架构方案只能满足，不能绕开：

1. 整套系统只部署一个 Cloudflare Worker 脚本。
2. 网页、接口、收信、定时任务和外部回调都由同一个 Worker 承接。
3. 只提供 `D1 + KV` 和 `D1 + R2` 两种邮件存储模式。
4. 不建设完整邮件服务器，收信依靠 Cloudflare Email Routing，站外发信依靠可替换的发信服务。
5. 首发同时支持电脑和手机浏览器，不开发原生应用。
6. 系统需要支持多个域名、个人地址、别名和组织共享地址。
7. 邮件正文、附件和备份属于敏感数据；系统管理员不能通过产品界面读取普通用户个人邮件正文。
8. 旧系统迁移、完整备份、完整恢复和版本回退必须能够真实执行。
9. 目标规模为 50 名已启用用户、10 人同时操作和累计 100,000 封测试邮件。
10. 在目标规模和正常网络下，常用列表及邮件详情通常应在 2 秒内可操作。
11. 首发核心闭环必须以 Workers Free 为默认运行基线；Paid 只能作为可选增强，不能成为隐藏前提。

## 质量优先级

架构发生取舍时，按以下顺序判断：

1. **邮件不丢失**：可恢复故障不能造成已经接受的邮件静默消失。
2. **权限不越界**：任何邮件、地址、组织和管理操作都必须由服务端检查权限。
3. **重试不重复**：收信和 Simlettra 控制的发信重试必须幂等。
4. **能够恢复**：数据、对象、索引和任务状态必须能够备份、对账、恢复或重建。
5. **容易维护**：个人维护者能够理解模块边界、故障位置和升级影响。
6. **日常够快**：常用流程达到已确认的性能目标，不追求没有使用价值的极限吞吐量。
7. **成本可预期**：默认配置避免无边界轮询、扫描和重复写入，能够解释 Cloudflare 用量来源。
8. **功能丰富度**：只有前七项得到保证后，才扩展非核心功能。

## 必须满足的可靠性规则

1. D1 中只有状态为“可见”的邮件才能出现在用户列表中。
2. 正文或任一必要附件缺失时，邮件不得进入“可见”状态。
3. 每个跨 D1 与 KV/R2 的写入流程都必须具有稳定操作编号、明确状态和补偿或重放办法。
4. 外部通知、转发和投递状态失败不能回滚或删除原始邮件。
5. 队列、回调和定时任务均按“可能重复执行”设计。
6. 永久删除先从用户视图中消失，再通过可追踪任务清理数据库、对象、索引和缓存。
7. 搜索索引属于可重建数据，原始邮件和权威元数据不能依赖搜索索引恢复。

## 必须满足的安全规则

1. 密码使用成熟的慢速密码哈希，并为每个密码使用独立随机盐。
2. 会话使用不可预测的随机令牌；浏览器只保存受保护的会话 Cookie，不在 `localStorage` 保存长期登录令牌。
3. 数据访问先判断用户身份，再判断具体资源所有权或组织成员资格。
4. 管理员身份不能自动绕过个人邮件正文权限。
5. 初始化、管理员恢复、永久删除、备份恢复和管理员转让具有额外确认与频率限制。
6. HTML 邮件在隔离环境中清理后显示，远程资源默认不加载。
7. 日志只记录操作编号、资源编号、状态、耗时和错误类别，不记录正文、附件内容、密码、令牌或密钥。

## 必须满足的可维护性规则

1. 代码按业务模块组织，不按页面或 HTTP 路径堆放业务规则。
2. 单 Worker 只代表一个部署单元，不代表把所有代码写进一个文件。
3. 每个模块通过公开应用服务协作，不直接调用其他模块的内部数据访问代码。
4. 数据库只通过版本化迁移改变，不在普通请求中自动建表或隐式升级。
5. KV 与 R2 使用同一对象存储接口，业务模块不能判断具体绑定类型。
6. 发信和通知服务使用统一网关接口，新增供应商不修改邮件核心规则。
7. 重要状态变化具有审计记录，并能够从操作编号追踪完整过程。

## 仍需架构验证的风险

1. 20 MB 邮件解析在真实 Workers Free Queue consumer 中的 CPU、128 MB 内存和并发代价。
2. D1 免费额度与 100,000 封邮件的正文搜索索引能否同时满足。
3. KV 单值限制、每日写入额度和最终一致性对邮件对象的影响。
4. Resend 与 SMTP2GO 的套餐、邮件大小、回调和结果未知边界。
5. 中文正文搜索需要采用何种 FTS5 分词或分块策略。

这些风险需要官方资料和验证性原型支持，不得凭印象宣称已经解决。
