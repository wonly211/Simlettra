# 0001 采用单 Worker 模块化单体

## 状态

已接受

- 接受日期：2026-08-10

## 背景

需求基线已经确定单 Worker 集中部署，但单一部署单元仍可以采用混乱的大文件结构，也可以在内部建立清晰模块。系统需要同时处理网页、接口、收信、队列、定时任务和外部事件，并由个人长期维护。

## 决定

只部署一个 Simlettra Worker 脚本。脚本同时导出 `fetch`、`email`、`queue` 和 `scheduled` 入口，内部按系统、身份、地址、组织、收信、邮箱、发信、通知、数据生命周期和运维模块组织。

模块之间通过公开应用服务和稳定契约协作，不直接调用其他模块的内部存储代码。

## 备选方案

1. 多 Worker 拆分：隔离更强，但违反已接受需求并增加部署、配置和排错成本。
2. 单 Worker 单层脚本：初期文件少，但权限、状态和故障处理会快速耦合。
3. 全栈框架主导所有入口：页面整合方便，但邮件和后台处理过度依赖框架生命周期。

## 后果

### 正面

1. 保持一次部署和统一配置。
2. 业务边界清楚，能够独立测试。
3. 同一进程内协作简单，不引入内部网络调用。

### 负面

1. 必须主动维护模块边界，不能把“单体”当作随意互相调用。
2. Worker 包体、冷启动和依赖数量需要持续控制。
3. 任一入口的严重初始化错误可能影响整个应用。

## 验证方式

1. 每个业务模块具有独立单元测试和公开应用服务。
2. 构建产物只有一个 Worker 脚本。
3. `fetch`、`email`、`queue` 和 `scheduled` 具有独立边界集成测试。
4. 依赖规则测试阻止模块直接导入其他模块的内部目录。
