# 0003 使用 Cloudflare Queues 唤醒异步任务

## 状态

已接受

- 接受日期：2026-08-10

> 后续影响：[0028 首发域外发信只支持 Resend 和 SMTP2GO](0028-首发域外发信只支持Resend和SMTP2GO.md) 已移除 Cloudflare Email Sending 的 Queue 投递事件。Queue 仍用于邮件解析、站外发信任务唤醒、通知、转发、对象清理和对账，因此本记录的核心决定继续有效。

## 背景

邮件解析、站外发信、通知、转发、对象清理和供应商事件不适合全部阻塞网页请求或收信入口。仅靠定时扫描会增加延迟和 D1 读取，Cloudflare Email Sending 的投递事件本身也通过 Queue 提供。

## 决定

1. 两种部署模式共同创建一个 Cloudflare Queue。
2. 同一个 Simlettra Worker 既写入队列，也消费队列，不增加第二个 Worker。
3. Queue 消息只包含任务编号和必要版本信息，不包含邮件正文或密钥。
4. D1 任务表保存权威状态、尝试次数、下一次执行时间和最后错误。
5. Queue 只负责尽快唤醒任务；定时任务扫描 D1 并重新投递遗漏或到期任务。
6. 所有消费者按至少一次投递设计并保持幂等。

## 备选方案

1. 只使用 D1 任务表和定时扫描：资源少，但延迟较高、扫描成本更大，并不能直接接收 Cloudflare 发信事件。
2. 在请求中同步完成全部工作：实现直观，但外部延迟和部分失败会影响收信或网页请求。
3. 使用多个专用 Worker 消费不同队列：隔离更强，但违反单 Worker 部署要求。

## 后果

### 正面

1. 收信入口可以在可靠保存原始邮件和任务后尽快结束。
2. 外部发信、通知和清理可以独立重试。
3. Cloudflare Email Sending 事件能够进入统一状态模型。
4. Queue 暂时不可用或消息过期时，D1 任务仍可由定时修复。

### 负面

1. 部署多一个 Queue 资源，初始化和备份说明需要解释其作用。
2. 至少一次投递要求所有任务具有稳定操作编号和条件更新。
3. Free 计划的每日 Queue 操作额度需要纳入用量监控。

## 验证方式

1. 同一 Queue 消息重复消费不会重复收信、发信或通知。
2. Queue 投递失败后，定时任务能够从 D1 重新投递。
3. 消费中途异常时，任务保留可理解状态和下一次尝试时间。
4. Queue 消息和日志不包含正文、附件内容、密码、令牌或密钥。
