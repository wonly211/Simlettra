# 0007 采用中文双字词元和邮箱范围词元建立搜索索引

## 状态

已接受

- 接受日期：2026-08-10

## 背景

需求要求按正文关键词搜索，目标规模为 100,000 封邮件，同时 D1 免费计划单数据库只有 500 MB。D1 FTS5 默认 `unicode61` 不能可靠匹配没有空格的中文子串，`trigram` 又不能匹配常见的两个汉字关键词。

2026-08-10 的本地验证表明：应用生成双字词元可以正确匹配两个及以上连续汉字；同时建立单字词元会把原型 D1 从 266.50 MiB 增加到 443.78 MiB。全局搜索常见词会读取 307,946 行，加入稳定邮箱范围词元后降到 13,946 行。

验证证据见[中文搜索与 D1 规模验证结果](../验证/中文搜索与D1规模验证结果.md)。

## 决定

1. 中文正文规范化后按连续文字生成相邻双字词元，例如“预算调整”生成“预算、算调、调整”。
2. 首发中文正文全文搜索至少输入两个汉字，不为单个汉字建立全量正文索引。
3. 拉丁文字、数字和邮件地址继续按明确规范化规则生成词元，具体规则在搜索契约中测试。
4. 正文按固定上限分块，每个分块映射回物理邮件。
5. FTS5 使用内容空表，只保存可重建索引，不把正文原文复制到 D1。
6. 每个搜索分块加入稳定的个人邮箱或组织邮箱范围编号。组织使用组织编号，不按成员复制索引。
7. 范围词元只用于减少候选行；返回结果前仍必须检查个人邮箱所有权或当前组织成员资格。
8. 设计阶段以 300 MiB 为容量预警线、400 MiB 为高风险线；正式发布前在真实 Cloudflare D1 上复核。

## 备选方案

1. 直接使用 `unicode61`：容量较低，但中文子串搜索不正确。
2. 使用 `trigram`：可以匹配三个及以上字符，但不能满足常见的双字中文词。
3. 同时建立单字和双字词元：支持单汉字，但 100,000 封合成邮件已达到 443.78 MiB，余量不足。
4. 使用 `LIKE` 扫描正文：无需 FTS 设计，但正文位于 KV/R2，无法在 D1 中高效扫描，且成本不可控。
5. 引入外部搜索服务：搜索能力更强，但增加部署、费用、数据边界和维护复杂度，不符合首发的自部署重点。

## 后果

### 正面

1. 常见的两个及以上连续汉字可以正确搜索。
2. 相比单字加双字索引节省约 177.28 MiB 的本地 D1 空间。
3. 邮箱范围词元显著降低高频词搜索的读取行数。
4. 组织成员变化不需要重建正文索引，只需在查询时重新检查成员资格。
5. 搜索索引仍可从 KV/R2 正文对象重建。

### 负面

1. 首发不能只输入一个汉字搜索正文。
2. 应用需要维护确定性的规范化、分块、词元生成和查询表达式规则。
3. 合成数据可能低估真实邮件语言多样性带来的索引体积。
4. 真实 Cloudflare D1 性能和计费读取行数仍需远程复核。

## 验证方式

1. 词元生成器使用简体中文、繁体中文、英文、数字、邮件地址、标点和混合文本单元测试。
2. 100,000 封邮件下，列表和范围搜索满足性能与读取行预算。
3. 删除 FTS 表后可以从对象正文和权威元数据完整重建，并通过数量对账。
4. 用户退出组织后，即使范围词元仍含组织编号，也不能通过服务端权限检查读取组织邮件。
5. 在受控 Cloudflare D1 上重复正确性、耗时、读取行数和容量验证。
