# 0008 限制 MIME 解析资源并保留原始邮件

## 状态

已接受

- 接受日期：2026-08-10

> 后续影响：用户于 2026-08-11 明确 Simlettra 以 Cloudflare 免费资源为设计初衷。Queue consumer 的 CPU 边界与本记录采用的 Workers Free HTTP CPU 边界不同，因此重新评估了完整 20 MB 是否必须使用 Workers Paid；随后接受的 ADR `0030` 已作出取代决定。本记录保留原决定正文作为历史，不再代表当前完整结论。

> 后续取代：[0030 以真实 Free 环境验证作为 20 MB 邮件解析上线门槛](0030-以真实Free环境验证作为20MB邮件解析上线门槛.md) 于 2026-08-11 接受，取代本记录第 10 项“直接以 Workers Paid 为生产基线”的结论。20,000,000 字节定义、原始 MIME 先保存、Queue 异步解析、结构限制、失败保留原件和不可信输入边界继续有效。

## 背景

需求基线要求接收总大小不超过 20 MB 的邮件，并要求可恢复故障不能造成半封邮件或附件丢失。已接受架构规定收信入口先保存原始 MIME，再由 Queue consumer 异步解析。

2026-08-10 的本地原型证明 `postal-mime 2.7.6` 能正确解析接近上限的附件、正文和大量部件，也能执行邮件头、MIME 嵌套和 RFC822 展开限制。最高一组本地解析第 95 百分位为 271 毫秒，明显高于 Workers Free 的 10 毫秒 CPU 上限；Node.js 近似内存还显示 20 MB 纯文本是高风险场景。真实 Worker 的 128 MB 内存余量尚未证明。

验证证据见[接近 20 MB 邮件解析验证结果](../验证/接近20MB邮件解析验证结果.md)。

## 决定

采用以下方案：

1. 产品中的 `20 MB` 指原始 RFC 822 邮件最多 20,000,000 字节，不按 20 MiB 解释。
2. 收信入口使用 `rawSize` 在解析前执行大小检查；超过上限时明确拒收，不写入半成品。
3. 原始 MIME 先以不可变字节对象保存，D1 建立“已接受、待解析”状态，然后由 Queue consumer 解析。
4. 通过项目自有 MIME 解析适配器使用 `postal-mime`；锁定依赖版本和配置，使以后替换解析器不影响收信业务模块。
5. Queue consumer 从 KV/R2 取得完整 `ArrayBuffer` 并直接交给解析器。禁止把原始邮件先转换或拼接为 JavaScript 字符串，也不把直接传入 `ReadableStream` 宣称为低内存解析。
6. 首发解析边界为：每个已解析消息的邮件头最多 256 KiB、MIME 最深 64 层、内嵌 `message/rfc822` 最多展开 5 层、解析后附件最多 1,000 个。
7. 超过邮件头或 MIME 深度限制时，邮件保持不可见并进入确定性“解析失败”状态；超过 RFC822 展开深度的剩余子邮件作为带标记附件保留。
8. 格式异常、附件名、HTML、外部链接和解析结果始终视为不可信输入。容错解析成功不等于邮件格式安全或有效。
9. 临时对象读取或平台故障可以按同一任务编号重试；确定性格式错误和超过结构限制不无限重试。原始 MIME 保留到数据生命周期策略明确允许清理。
10. 对完整 20 MB 支持的生产部署基线采用 Workers Paid。发布前仍必须在真实 Cloudflare Worker 中通过 CPU、128 MB 内存、并发和 Queue 重试验证；Paid 不提高单 isolate 内存上限。

## 备选方案

1. 在收信入口同步完成解析：可少一个中间状态，但解析耗时或异常会扩大收信入口失败面，不采用。
2. 把 `ReadableStream` 直接交给 `postal-mime`：接口可用，但当前实现仍收集并复制全部分块，没有形成真正流式解析，不作为推荐路径。
3. 先把原始邮件解码为字符串：实现直观，但会增加内存副本并可能破坏二进制内容，禁止采用。
4. 自行编写 MIME 解析器：能够定制流式行为，但协议复杂、安全风险和维护成本过高，不作为首发方案。
5. 把产品上限降到更小：能降低资源压力，但会改变已确认需求，不能由架构阶段自行决定。
6. 只支持 Workers Free：成本低，但不能对接近 20 MB 的解析可靠性作出可信承诺。

## 后果

### 正面

1. 用户看到的 20 MB 含义明确，不会因 MB 与 MiB 混用产生边界差异。
2. 原始邮件始终存在，可以重新解析、迁移、导出和对账。
3. 解析失败不会产生半封可见邮件，也不会因无限重试持续消耗资源。
4. 已验证的安全边界能够阻止超大邮件头和过深嵌套。
5. 解析器被适配器隔离，后续可在不改业务规则的情况下替换。

### 负面

1. 完整首发能力不承诺在 Workers Free 上稳定运行。
2. `postal-mime` 仍是全量内存解析，20 MB 纯文本可能逼近或超过真实 Worker 内存余量。
3. 1,000 个附件的数量限制是在解析后确认，原始大小限制仍是解析前最重要的资源边界。
4. 格式异常但被容错接受的邮件需要继续依靠 HTML 清理、附件安全下载和风险提示。
5. 部署和升级文档必须持续核验 Cloudflare 与解析库限制。

## 验证方式

1. 标准邮件、大附件、多附件、大正文和 1,000 个附件的数量、正文、关系、大小与哈希符合生成清单。
2. 超过 256 KiB 邮件头和 64 层 MIME 嵌套被确定性拒绝。
3. 超过 5 层 RFC822 嵌套的剩余内容被标记为附件。
4. 重复 Queue 消费不会重复生成邮件、附件对象或邮箱条目。
5. 在真实 Cloudflare Workers Paid 环境复核接近 20 MB 纯文本和附件邮件的 CPU、内存、并发与重试。
6. 解析器升级时重跑固定样本和恶意结构回归测试，结果变化必须审查。
