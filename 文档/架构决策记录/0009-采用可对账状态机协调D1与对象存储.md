# 0009 采用可对账状态机协调 D1 与对象存储

## 状态

已接受

- 接受日期：2026-08-10

## 背景

D1 与 KV/R2 之间没有跨资源事务。邮件接收、修复和永久删除任一步都可能在数据库或对象存储已经成功后中断。若只按固定顺序调用接口而没有权威状态和重放规则，会产生半封可见邮件、重复对象、无法判断是否完成的删除或静默数据损坏。

R2 提供强一致性，KV 是最终一致且同一键有写入频率限制。两种存储必须保持相同产品功能，但不能假定具有相同的可见时序。

2026-08-10 的本地原型在两种模式下完成 31 个故障场景，证明候选状态机能够回滚可见提交、幂等补写对象、换键修复衍生内容、对账孤立对象并继续永久删除。KV 全球一致性仍需远程验证。

验证证据见[KV 与 R2 故障恢复验证结果](../验证/KV与R2故障恢复验证结果.md)。

## 决定

采用以下方案：

1. 每封物理邮件的原始 MIME、正文、HTML、附件和内嵌资源使用属于该邮件的唯一不可变对象键，键包含稳定邮件编号、对象角色和代数。
2. 首发不在不同物理邮件之间共享内容对象或使用跨邮件引用计数去重。重复投递通过邮件和接收操作幂等处理，不通过共享对象处理。
3. 写对象前先在 D1 `object_registry` 建立写入意图，记录角色、代数、预期大小、SHA-256 和状态。对象写入后再把登记改为“存在”。
4. 接收状态依次为：接收意图、原始对象存在、解析中、衍生对象存在、等待一致性、可见。Queue 和定时任务只根据 D1 状态继续下一步。
5. 全部活动对象通过大小与 SHA-256 校验后，使用一个 D1 `batch()` 同时建立邮件关系、投递、邮箱条目并把任务改为完成；对象写完但 D1 未提交时邮件仍不可见。
6. R2 模式在对象校验后可以立即进入最终可见事务。KV 模式先进入“等待一致性”，至少在后续任务中重新校验；仍读不到时继续隐藏、延迟重试并显示运维告警，不覆盖同一键。
7. 所有对象键只通过服务端 D1 授权后的接口访问，不把内部键暴露为长期公开链接。KV 缓存中的旧值不能绕过删除或成员权限。
8. 已可见邮件缺少或损坏衍生对象时，D1 立即撤销邮箱可见条目并进入“修复中”；从原始 MIME 生成更高代数的新对象键，校验后重新提交可见。
9. 原始 MIME 缺失或损坏时，邮件进入“损坏”状态并触发不含正文的告警；只能从经过验证的备份恢复或人工处理，不能伪造恢复成功。
10. 永久删除先在 D1 事务中撤销所有访问并标记待删除，再由幂等任务清理对象、正文、附件、搜索和缓存。全部对象及内容引用对账为零后，才把操作标记为完成。
11. D1 保留最小防重操作记录、任务结果和必要审计事件，不保留已永久删除邮件的主题、地址、正文、附件名或对象键。
12. 定时修复同时覆盖未完成任务和对象完整性对账。孤立对象至少经过 24 小时保护期并在两次独立对账中持续孤立后才删除；缺失或损坏对象立即进入修复或告警流程。

## 备选方案

1. 对象写完后直接把邮件设为可见：步骤少，但对象缺失或 D1 部分提交时会出现半封邮件，不采用。
2. 依赖 Queue 消息作为任务真相：实现简单，但消息重复、丢失或过期后无法可靠判断工作状态，不采用。
3. 使用内容哈希在不同邮件之间共享对象：节省重复附件空间，但需要并发引用计数和复杂删除保护，首发收益不足以覆盖风险。
4. 修复损坏对象时覆盖原键：对象数较少，但 KV 可能继续返回旧缓存，也会触发同一键写入限制，不采用。
5. 永久删除先删对象、最后撤销 D1 访问：后台中断时用户可能看到缺失内容，不采用。
6. KV 与 R2 使用不同业务流程：可以分别优化，但测试、迁移和故障语义会分裂，不采用。
7. 只支持 R2：一致性更清楚，但违反已经接受的 D1+KV 兼容部署要求。

## 后果

### 正面

1. 接收、修复和删除每一步都可以从 D1 判断下一步，不依赖调用方记住执行到哪里。
2. 重复 Queue 消息、调用超时和进程中断不会创建重复邮件或对象引用。
3. 用户不会看到已知缺少正文或附件的邮件。
4. 对象大小、哈希、孤立和缺失状态可以被统一对账。
5. 永久删除立即撤销访问，同时允许后台安全完成物理清理。
6. KV 与 R2 共用相同业务契约，差异集中在对象适配器和一致性等待策略。

### 负面

1. 每个对象都增加一条 D1 登记，任务和状态数量随邮件及附件数量增长。
2. 不进行跨邮件内容去重，会使用更多 KV/R2 空间。
3. KV 模式的新邮件可能比 R2 更晚出现，传播异常时会长时间停留在“等待一致性”。
4. 缺失衍生对象修复期间邮件会暂时从普通邮箱视图撤下。
5. 定期对象列举和 D1 对账会消耗额度，需要按规模分批执行。
6. 原始 MIME 本身损坏时仍需要备份，状态机只能发现问题，不能创造不存在的数据。

## 验证方式

1. 在每个 D1 和对象存储边界注入故障，故障期间邮箱条目始终为 0。
2. 最终可见 D1 批次中任一语句失败时全部回滚。
3. 同一接收、修复或删除任务重复执行至少三次，邮件、邮箱条目、对象登记和对象键数量保持不变。
4. 衍生对象缺失或哈希不符时使用更高代数新键恢复，原始 MIME 缺失时明确转为损坏状态。
5. 永久删除在每个中断点重试后，内容引用和实际对象均为 0。
6. 在真实 Cloudflare 多地区环境验证 KV 的创建、负查询缓存和删除传播；异常时不能提前设为可见。
7. 在目标规模下测量增量修复和全量对账的 D1 读取与对象列举成本。
