# 0010 采用供应商感知的域外发信状态机

## 状态

已接受

- 提议日期：2026-08-10
- 接受日期：2026-08-10

> 后续取代：[0028 首发域外发信只支持 Resend 和 SMTP2GO](0028-首发域外发信只支持Resend和SMTP2GO.md) 于 2026-08-11 接受，取代本记录中 Cloudflare Email Sending 适配器、5 MiB 特例、Queue 发信事件和“三家 Provider”范围。最终 MIME 计量、逐收件人状态、Resend、SMTP2GO、安全重试、回调鉴权和结果未知不自动重发的其余结论继续有效。

## 背景

需求 `7.07` 规定 Simlettra 单封邮件总大小默认不超过 20 MB，发信服务限制更小时采用更小值；需求 `10.06` 要求首发支持 Cloudflare Email Sending、Resend 和 SMTP2GO；需求 `7.11` 要求重试不能产生重复邮件。

三家服务的限制、幂等能力和事件入口并不相同。Cloudflare 向普通外部地址发信的上限只有 5 MiB，Resend 有 24 小时幂等键，Cloudflare 与 SMTP2GO 当前均未提供已核实的发送幂等键。如果把三家服务伪装成完全相同的调用，会出现超限邮件晚失败、响应丢失后重复发信或伪造回调修改投递状态的风险。

2026-08-10 的本地原型完成九组自动验证，证明候选大小检查、重试规则、事件鉴权、状态映射、防重和乱序保护能够共用一个网关契约。证据见[三种域外发信服务验证结果](../验证/三种域外发信服务验证结果.md)。

## 决定

采用以下方案：

1. 为 Cloudflare Email Sending、Resend 和 SMTP2GO 分别建立适配器；每个适配器公开能力、负载测量、提交和事件转换接口，不把供应商差异散落到业务模块。
2. Simlettra 自身上限固定为 `20,000,000` 个最终邮件字节。实际发信上限取 Simlettra、供应商和当前收件人条件三者中的较小值。
3. Cloudflare 普通外部地址按 `5,242,880` 字节限制；全部收件人均为 Email Routing 已验证目标时，供应商上限为 25 MiB，但仍受 Simlettra 的 `20,000,000` 字节限制。
4. Resend 按 40 MB 供应商上限、SMTP2GO API 按 50 MB 供应商上限，因此两者当前有效上限均为 `20,000,000` 字节。
5. 邮件头、地址、主题、正文、HTML、MIME 边界、内嵌资源、附件和 Base64 膨胀全部计入；Queue consumer 在供应商调用前根据最终 MIME 或等价完整提交负载再次检查。
6. 每次用户发送建立唯一发信操作，每个站外收件人建立独立投递记录。统一状态为等待提交、提交中、已提交、延迟、已送达、退信、失败和结果未知。
7. 能证明供应商尚未接受时允许以同一操作编号重试。Resend 在 24 小时内使用稳定 `Idempotency-Key`；同一键不得对应不同邮件内容或收件人。
8. Cloudflare Email Sending 与 SMTP2GO 发生“可能已接受但响应丢失”时进入结果未知，不自动重发；后续事件可以消解状态，仍无法确定时由用户或管理员决定是否创建新的发送操作。
9. Cloudflare 事件只从 Queue consumer 接收；Resend 使用原始请求体和 Svix 请求头验签；SMTP2GO 使用专用 HTTPS Basic Auth 凭据，并回传稳定的 Simlettra 操作编号。
10. 所有事件按供应商事件编号去重。终态不被较早的已提交或延迟事件覆盖；垃圾投诉保存为独立风险标记，打开和点击不作为可靠已读状态。
11. 供应商限制是适配器能力配置的一部分。升级时复核官方资料；限制变化不得要求修改发信核心业务规则。

## 备选方案

1. 三家服务统一按 5 MiB 限制：最简单，但无端减少 Resend、SMTP2GO 和 Cloudflare 已验证目标可用容量，不采用。
2. 三家服务统一按 20 MB 限制：用户体验表面一致，但 Cloudflare 普通外部邮件会被供应商拒绝，违反发送前可判断要求，不采用。
3. 所有网络超时都自动重试：可能提高表面成功率，但缺少幂等键时会向同一收件人发送多封，不采用。
4. 所有网络超时都不重试：避免重复，但浪费 Resend 已提供的幂等能力，也会让明确未提交的连接失败需要人工处理，不采用。
5. 只保存整封邮件一个状态：表结构较少，但无法表达多个收件人的不同结果，不采用。
6. 三家事件都使用一个自定义共享密钥 HTTP 接口：实现统一，但放弃 Cloudflare Queue 和 Resend Svix 已提供的边界，不采用。

## 后果

### 正面

1. 用户在发送前就能知道当前域名和收件条件的实际大小限制。
2. Cloudflare 的 5 MiB 特殊限制不会被误当成 20 MB。
3. Resend 可以在响应丢失时安全恢复，Cloudflare 与 SMTP2GO 不会因盲目重试制造重复邮件。
4. 多收件人邮件能分别显示送达、延迟、退信和失败。
5. 三家服务使用各自最可信的事件入口，同时向业务层提供同一状态模型。
6. 供应商以后调整能力时，改动集中在适配器和契约测试。

### 负面

1. Cloudflare Email Sending 向普通外部地址发信时，用户只能使用约 5 MiB 的完整邮件容量。
2. 最终 MIME 可能比用户选择的附件原文件大，界面只能提前估算，仍必须在服务端最终检查。
3. Cloudflare 与 SMTP2GO 的“结果未知”可能需要等待事件或人工判断，不能承诺所有发送立即得到确定结果。
4. 每个收件人独立状态会增加 D1 行数和事件处理逻辑。
5. SMTP2GO 的 Basic Auth 不等同于事件级签名，需要额外的 HTTPS、强凭据、限速和防重保护。
6. 真实账号契约测试和供应商能力复核会成为发布与升级流程的一部分。

## 验证方式

1. 对四种有效限制分别提交等于上限和大于上限一个字节的合成 MIME；前者成功，后者在本地拒绝且供应商接受次数为零。
2. 三家服务在明确未接受的连接故障后重试，最终只产生一次供应商接受。
3. Resend 接受后响应丢失时使用同一幂等键重复三次，只产生一个供应商发送编号。
4. Cloudflare 与 SMTP2GO 接受后响应丢失时，重复执行不得创建第二次发送。
5. 对三家主要事件执行状态映射，验证每个收件人独立更新。
6. 重复事件、乱序事件和投诉事件不得造成重复迁移或终态倒退。
7. 无效 Resend 签名、过期时间戳、无效 SMTP2GO Basic Auth 和公共 HTTP Cloudflare 伪造事件必须被拒绝。
8. 发布前使用三家测试账号各执行一次真实大小边界、提交响应和事件回调契约测试。
