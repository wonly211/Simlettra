# 0012 采用 Drizzle 查询层和 Wrangler 迁移账本

## 状态

已接受

- 提议日期：2026-08-10
- 接受日期：2026-08-10
- 部分取代：远程生产迁移的具体执行通道已由 [ADR 0048](0048-远程迁移使用D1文件导入并沿用Wrangler账本.md) 取代；本记录的正式 SQL、唯一账本和只增不改原则继续有效。

## 背景

D1 是 Simlettra 的权威状态来源，需要承载权限、地址唯一性、邮件元数据、成员状态、任务、审计和搜索索引。系统必须使用版本化迁移，不能继承旧系统在普通请求中执行 `CREATE TABLE IF NOT EXISTS` 的方式。

全部手写 D1 SQL 能完整使用平台能力，但会增加字段、类型和组合查询的人工同步成本。完整 ORM 可以提高开发便利性，却可能隐藏 FTS5、PRAGMA、D1 `batch()`、Sessions 和结果用量指标，并增加 Worker 包体与运行时兼容边界。

2026-08-10 的本地原型完成 11 组自动验证。Drizzle 与原生 D1 的组合列表结果一致，生成迁移、手写 FTS5 迁移和 Wrangler 账本可以共存；Prisma 也能查询，但 D1 adapter 仍为 Preview，代表性 Worker gzip 包体约为 Drizzle 的 32.25 倍。证据见[D1 数据库工具与迁移验证结果](../验证/D1数据库工具与迁移验证结果.md)。

## 决定

采用以下方案：

1. 使用 Drizzle ORM 作为普通 D1 表的 TypeScript 结构描述和默认查询构造器。
2. Drizzle 只存在于各业务模块的内部存储适配器，业务服务不得接收 Drizzle 表、查询对象或返回类型。
3. Drizzle Kit 只生成普通表结构变更的 SQL 草案。每份草案必须人工审查后才成为正式迁移。
4. `migrations/` 中按编号排列、只增不改的 SQL 文件是数据库变更历史的权威记录；生产只使用 `wrangler d1 migrations apply` 应用。
5. 禁止在生产使用 `drizzle-kit push`、Prisma Migrate、运行时自动建表或其他并行迁移账本。
6. FTS5、PRAGMA、数据回填、表重建和 Drizzle 不适合表达的 SQLite 能力使用手写 SQL 迁移，并与生成迁移共用同一编号序列。
7. 普通增删改查优先使用 Drizzle；FTS5、D1 Sessions、结果 `meta`、批量分块和平台特有能力使用参数化原生 D1。
8. 所有动态数据使用绑定参数。动态表名、列名和排序字段只能来自代码中的固定白名单。
9. 邮箱列表使用稳定键集分页，不把深 `OFFSET` 作为主要翻页方式。
10. 受 D1 每条查询最多 100 个绑定参数限制，大批量操作默认按最多 90 个业务参数分块。
11. 每次迁移在数据副本演练，检查外键、索引、表列、数量、对象引用和关键状态；生产迁移前记录 Time Travel 书签并确认本地备份成功。
12. 单个迁移失败时停止发布并依赖 D1 原子回滚。已成功迁移后优先使用兼容应用或修复性前向迁移；需要恢复数据时使用 Time Travel 或本地备份。
13. 已应用迁移不得改写、删除、重排或复用编号，任何修复都新增迁移。

## 备选方案

1. 全部使用原生 D1：依赖最少，但普通表查询缺少结构关联类型，组合条件与字段变更更容易依赖人工同步，不采用为默认方式。
2. 使用 Prisma：D1 查询可以运行，但 adapter 仍为 Preview，代表性 Worker gzip 包体约 1,242.30 KiB，并需要 `nodejs_compat` 和生成客户端，首发不采用。
3. 使用 Kysely：查询 API 清晰，但核心项目没有内置 D1 dialect，需要额外第三方适配边界，首发不采用。
4. 完全由 Drizzle 接管迁移：普通表方便，但 FTS5、PRAGMA、回填和 D1 运维仍需要原生 SQL，会形成不透明的双轨流程，不采用。
5. 只手写迁移、Drizzle 仅查询：可以运行，但 TypeScript 表结构与正式 SQL 更容易漂移；采用“Drizzle 生成草案、人工审查、Wrangler 唯一应用”更容易持续检查。
6. 使用 `OFFSET` 分页：实现简单，但深页读取成本随偏移增长，不采用为主要列表方案。

## 后果

### 正面

1. 普通表、字段和组合查询具有 TypeScript 类型检查，SQL 仍保持可见和可审查。
2. 只有 Wrangler 维护生产迁移账本，避免不同工具对“哪些迁移已应用”产生分歧。
3. FTS5、D1 Sessions、用量指标和批量操作不受 ORM 能力上限限制。
4. Drizzle Worker 包体较小，不需要为数据库工具打开 `nodejs_compat`。
5. 键集分页和 90 参数分块直接反映 D1 的成本与限制。
6. 数据访问工具被限制在模块内部，不会把数据库结构扩散成跨模块公共契约。

### 负面

1. 项目需要同时理解 Drizzle 查询和少量原生 D1 SQL。
2. Drizzle 生成迁移不能未经审查直接发布，自动化程度低于 `push` 模式。
3. 特殊 SQL 与 Drizzle 表结构可能发生漂移，必须用迁移重演和结构契约测试发现。
4. 更新 Drizzle 或 Wrangler 时需要重新生成样例迁移并执行回归验证。
5. 修复性前向迁移和兼容应用要求发布流程明确区分代码回退与数据回退。

## 验证方式

1. 从空库依次应用 Drizzle 生成迁移和手写 FTS5 迁移，迁移账本顺序正确。
2. 重复应用时不再次执行已经记录的迁移。
3. 已有数据经过新增字段迁移后得到正确默认值，外键检查为零。
4. Drizzle 与原生 D1 对相同组合查询返回一致结果。
5. 用户范围、地址范围、状态筛选和键集分页不得越权或重复。
6. Drizzle `batch()` 中任一语句失败时，所有语句均回滚。
7. 205 个批量编号按 90、90、25 分块并全部成功。
8. 故意失败的迁移不留下部分表和迁移记录。
9. Drizzle 与 Prisma 候选均完成类型检查和 Worker 干运行打包，并记录包体。
10. 发布前在真实 D1 重复迁移演练、失败回滚、Sessions 和 Time Travel 验证。
