# 0022 以统一对象登记和完整性状态管理邮件内容

## 状态

已接受

- 提议日期：2026-08-10
- 接受日期：2026-08-10

## 背景

Simlettra 的原始 MIME、纯文本正文、HTML、普通附件、内嵌资源、草稿附件和最终发信 MIME 都保存在 KV 或 R2。D1 与对象存储之间没有跨资源事务，KV 还可能在新对象写入后短暂读不到。如果只在邮件表中保存几个对象键，系统无法判断每个部件的写入意图、实际大小、哈希、当前代数、损坏状态和清理进度。

已接受 ADR `0002`、`0008` 与 `0009` 已经确定对象不可变、D1 保存登记、全部必要对象校验后才可见、衍生对象换代修复以及 KV/R2 共用业务契约。本决定把这些原则落实为统一数据模型，并承接[第四批数据模型确认清单](../数据模型/第四批数据模型确认清单.md)中的数据-58 至数据-66、数据-78 和数据-79。

## 决定

1. 所有 KV/R2 邮件对象使用一张统一对象登记表；每个逻辑部件的每个代数各有一行，不按存储后端或对象角色拆成多套业务表。
2. 对象角色至少区分原始 MIME、纯文本正文、HTML、普通附件、内嵌资源、草稿附件和最终发信 MIME。逻辑部件编号与显示顺序独立于对象键。
3. 对象键由服务端生成，只包含不泄露业务含义的稳定内部引用、角色和代数；邮箱地址、主题和附件原名不得进入键。
4. D1 登记保存预期与实际字节数、SHA-256、媒体类型、不可信文件名、内容处置、`Content-ID`、生产者版本、后端类型、后端校验标识和生命周期时间。
5. 对象状态依次表达写入意图、已写入、等待 KV 一致性、已验证、当前使用、被替代、缺失、损坏、待删除和已删除。状态与代数只能按允许的方向前进。
6. 消息对象可以在物理邮件最终行建立前使用预留的邮件引用登记；最终提交时只能一次性附着到同名物理邮件，不能改指其他邮件。
7. 每封可见邮件建立独立完整性状态。访问查询必须同时验证邮箱权限和完整性状态为“就绪”；搜索索引是否完成不影响读信权限。
8. 收信邮件必须有当前原始 MIME，发信邮件必须有当前最终 MIME。旧系统迁移邮件可以明确标记为“只有结构化内容”，不得伪装成保留了原始 MIME。
9. 草稿附件对象属于具体草稿附件记录。发送前将其复制或固化成物理邮件专属对象；已发送邮件不继续依赖可被清理的草稿对象。
10. 对象校验使用实际字节长度与 SHA-256；后端 ETag 或版本只作诊断信息，不能替代内容完整性判断。
11. 已可见邮件的当前对象缺失或损坏时，先把完整性状态改为“修复中”或“损坏”，使普通邮箱查询立即隐藏内容；衍生对象从可信原始 MIME 生成更高代数，验证后原子切换并恢复就绪。
12. 原始 MIME 或最终发信 MIME 本身损坏时，不允许从衍生对象伪造原始内容；只能使用经过验证的备份恢复或进入明确的人工处理流程。
13. 发送操作必须引用冻结的最终 MIME 对象，并使对象字节数与 SHA-256 和发送操作、供应商尝试保存的负载快照一致。

## 备选方案

1. 在 `messages` 中直接保存若干 KV/R2 键：字段少，但无法表达多个附件、对象代数、修复和部分失败，不采用。
2. KV 与 R2 各建一套登记表：能针对后端定制，但会形成两套业务状态和迁移风险，不采用。
3. 使用内容哈希作为全局对象键并跨邮件共享：可以节省重复附件空间，但需要引用计数和并发删除保护，首发不采用。
4. 修复时覆盖原对象键：对象数更少，但 KV 旧值传播和同键写入限制会让修复结果不可靠，不采用。
5. 对象缺失时继续显示其余正文：表面可用性更高，但用户可能误以为邮件完整，违反半封邮件不可见的可靠性要求，不采用。
6. 只保存供应商提交结果，不保留最终发信 MIME：存储较少，但无法证明重试内容、精确大小和导出内容一致，不采用。

## 后果

### 正面影响

1. 每个正文、附件和修复代数都有可对账身份、大小和哈希。
2. KV 与 R2 的差异集中在对象适配器和一致性等待，不进入邮箱业务规则。
3. 对象损坏会先撤销可见性，修复完成后恢复，不会向用户提供半封邮件。
4. 最终发信 MIME 与发送快照强关联，重试不能悄悄改变内容。
5. 备份、恢复、导出和对象清理可以共用同一对象清单。

### 成本与限制

1. 每个对象代数增加一行 D1 登记，附件多的邮件会产生更多记录。
2. 最终提交与修复需要在 D1 中协调对象附着、当前代数和邮件完整性状态。
3. 草稿附件固化到已发送邮件会增加对象写入量，但避免长期跨所有者共享。
4. 所有邮箱与下载查询都必须包含完整性状态和权限条件。
5. 真实 KV 多地区一致性和大对象校验仍需在 Cloudflare 环境验证。

## 验证方式

1. 同一逻辑部件同一代数不能重复登记，同一时刻只能有一个当前代数。
2. 预期大小或 SHA-256 与实际内容不一致时，对象不能进入当前使用状态。
3. R2 对象验证后可以继续，KV 对象必须经过等待一致性与再次校验。
4. 没有当前原始 MIME 的收信邮件、没有当前最终 MIME 的发信邮件不能标为就绪。
5. 附件数量与当前活动普通附件对象数量不一致时，邮件不能标为就绪。
6. 对象损坏后完整性状态不再就绪；更高代数校验并切换后才能恢复。
7. 发送操作引用的最终 MIME 大小和 SHA-256 必须与冻结负载完全一致。
8. 对象键、不可信文件名和错误摘要中不出现正文、邮箱地址或密钥。
