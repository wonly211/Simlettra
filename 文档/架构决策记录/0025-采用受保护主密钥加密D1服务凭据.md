# 0025 采用受保护主密钥加密 D1 服务凭据

## 状态

已接受

- 提议与接受日期：2026-08-11
- 依据：[需求变更-0001：域外发信服务故障切换与密钥管理](../需求/变更记录/0001-域外发信服务故障切换与密钥管理.md)、[第五批数据模型确认清单](../数据模型/第五批数据模型确认清单.md)的数据-82、数据-85
- 取代关系：取代 [0021 以供应商尝试和不可变事件维护域外发信状态](0021-以供应商尝试和不可变事件维护域外发信状态.md) 中“服务密钥只保存受保护配置引用、不进入 D1”的部分结论；`0021` 其余发送尝试和事件结论继续有效

> 后续取代：[0049 采用可信管理员可见变量和 Cloudflare 连接 GitHub 部署](0049-采用可信管理员可见变量和Cloudflare连接GitHub部署.md)于 2026-08-14 接受，取代本记录中配置主密钥只能作为不可回看 Secret 和旧变量名的结论。D1 动态凭据认证加密、管理员明文管理和日志边界继续有效。

## 背景

每套 Simlettra 只有一名系统管理员。该管理员需要在网页中维护多个域名、多家站外发信服务以及用户通知通道所需的动态凭据。若每新增一个密钥都要求管理员修改 Cloudflare 部署变量，配置过程会变得分散、难以核对，也无法通过网页完成日常管理。

直接把明文密钥写入 D1 又会让数据库副本、逻辑备份和排错导出变成明文凭据副本。用户接受的简化方向是：管理员正常管理密钥，但 D1 只保存加密后的值。

## 决定

1. Cloudflare 受保护部署配置只保存一把或一组版本化的配置加密主密钥，例如 `CONFIG_KEY`，不再为每个 Provider 单独保存服务密钥。它与用于初始化和管理员恢复的 `init_key` 完全分离，二者不得互相兼任。
2. 系统管理员可以在网页中查看、复制、创建、替换、删除和测试发信服务密钥与回调凭据；普通用户没有这些能力。
3. Worker 使用 Web Crypto 的 `AES-GCM` 加密动态凭据。每条密文使用独立随机 96 位随机值；D1 保存密文、随机值、算法标识、主密钥版本和必要非敏感配置，不保存明文。
4. 通知端点的敏感值使用同一机制加密保存。邮件正文、附件、密码、会话令牌和完整回调不使用此配置库作为存放位置。
5. 管理员读取明文时，服务端先验证其是当前系统管理员，再在当前请求中短暂解密；明文不得进入日志、审计详情、Queue 消息、错误响应、浏览器长期存储或普通导出。
6. 配置加密主密钥不随 D1 逻辑备份导出。完整恢复需要部署者准备与备份密文兼容的主密钥；密钥轮换应保留旧版本直到相关密文全部重新加密或被删除。
7. 服务配置的公开参数和加密凭据版本不可原地修改。管理员修改凭据或连接参数时建立新配置版本；旧版本保留给已经冻结且尚未完成的发送路线，直到被安全清理。

## 备选方案

1. 每家 Provider 的密钥都只放 Cloudflare 部署变量：保护边界清晰，但日常管理需要反复离开网页和编辑部署配置，不采用。
2. 在 D1 明文保存密钥：实现最少，但备份与数据库读取会直接泄露可用凭据，不采用。
3. 不让系统管理员再次查看已保存密钥：减少展示次数，但与单一受信任管理员负责完整配置的产品取向不符，不采用。
4. 为每名用户的通知端点建立独立部署变量：部署变量数量不可控，普通用户无法自助配置，不采用。

## 后果

### 正面

1. 管理员可以在产品内统一维护多家发信服务和动态通知端点。
2. D1 数据库、逻辑备份和故障副本不直接包含可用明文密钥。
3. 密钥轮换与发送配置版本能够保留可追踪历史。

### 成本与限制

1. 部署者必须安全保存配置加密主密钥；遗失兼容主密钥会使相应密文无法读取。
2. Worker 需要实现加密、解密、密钥版本和重新加密流程，并为其建立契约测试。
3. 当前系统管理员查看密钥仍是有意提供的产品能力；这不是面向不可信管理员的隔离。

## 验证方式

1. 同一明文使用不同随机值加密后得到不同密文，解密后保持一致。
2. 错误主密钥、随机值、算法或密钥版本不能解密并得到明确错误。
3. 普通用户不能读取、修改或测试服务凭据；当前系统管理员可以完成上述操作。
4. D1 逻辑备份、审计记录、任务消息和普通日志中不出现明文凭据。
5. 使用兼容主密钥恢复备份后，服务凭据可用；缺少兼容主密钥时恢复检查明确失败，不伪装为完整恢复。
