# 0026 采用域名级优先发信路线与安全故障切换

## 背景

用户要求每个域名可配置一个默认 Outbound Mail Provider 和多个备用 Provider，在默认服务无法发信时自动切换。Cloudflare Email Sending、Resend 和 SMTP2GO 的容量、幂等能力和故障语义不同；若把任何失败都当作可切换，网络请求已到达供应商但响应丢失时，备用服务可能造成重复投递。

原方案让一次发送操作冻结单一供应商，不能满足故障切换。新方案必须同时保留两项承诺：管理员可预先配置备用服务，且 Simlettra 自己控制的操作不得向同一收件人重复发送。

## 决定

1. 每个发件域名拥有版本化的发信路线。每个路线按优先顺序包含一个默认服务和零个或多个备用服务；路线和服务配置均使用不可变版本。
2. 发送操作接受时冻结整条路线、每个服务配置版本、顺序、Provider 类型和适用大小规则。后续路线调整只影响新操作；旧操作不得临时使用后来新增的服务。
3. 对每名站外收件人独立选择路线中优先且兼容最终 MIME、收件条件和当前状态的服务。不同收件人可以在同一封邮件中使用不同服务，整封邮件结果仍由逐收件人状态汇总。
4. 发送前要求每名站外收件人至少有一家冻结服务可接受最终完整负载。Cloudflare 普通外部收件人的 5 MiB 限制继续适用；若它不兼容而后续 Resend 或 SMTP2GO 兼容，可直接选择后者，不把默认服务的较小限制强加给所有候选服务。
5. 只有在适配器能明确证明当前服务尚未接受某个收件人，且失败属于服务不可用、服务限制不兼容、服务端临时拒绝或配置被停用时，才可为该收件人尝试路线中的下一家服务。
6. 地址格式错误、全局大小超限、发件权限失效和其他本地确定性错误不切换。请求已发出但响应丢失、连接中断等结果未知情形不切换，也不自动重发；保持 `unknown` 等待回调或人工再次发送。
7. 每次实际提交继续在外部调用前登记尝试。尝试保存选中的路线位置、配置版本、选择类型、切换原因和收件人关系；供应商事件仍按 Provider 加事件编号去重并遵循终态不倒退规则。
8. 配置被管理员紧急停用时，尚未提交的收件人可在冻结路线的后续兼容服务中继续；没有后续兼容服务则暂停或失败，并给出明确原因。

## 备选方案

1. 一个域名只允许一份服务配置：简单但不满足用户要求，不采用。
2. 发生任何异常都切换备用：表面成功率高，但可能重复发送，不采用。
3. 遇到大小限制仍要求用户手动更换默认服务：规则容易解释，但无法发挥已配置备用服务的作用，不采用。
4. 整封邮件只允许使用同一家服务：实现较少，但一名收件人的限制会阻断其他兼容收件人，不采用。

## 后果

### 正面

1. 单家 Provider 临时不可用或容量不兼容时，发送可自动继续。
2. 管理员能为不同域名设置送达、成本或容量不同的优先路线。
3. 逐收件人的 Provider、切换原因和最终状态可被准确解释。

### 成本与限制

1. 数据模型需要记录路线版本、冻结快照和每名收件人的路线进度。
2. 用户可能看到同一封邮件的不同收件人使用不同 Provider；界面必须清楚显示实际结果。
3. 结果未知仍需要等待或人工判断，不能承诺所有失败都自动恢复。
4. 每次 Provider 更新限制或错误语义时，适配器契约测试需要重新运行。

## 验证方式

1. 同一域名可保存默认和多个备用服务，并保持稳定顺序。
2. Provider 明确拒绝且未接受时，只把受影响收件人切换至下一家兼容服务。
3. 请求超时且无法判断接受结果时，不创建下一家服务的尝试。
4. 默认 Cloudflare 不支持 10 MB、备用 Resend 支持时，可接受该邮件并选择 Resend；若任何收件人没有兼容服务，则整次发送不开始。
5. 多收件人使用不同 Provider 时，状态、事件和失败不会互相覆盖。
6. 修改路线后，已接受操作仍只使用冻结的旧路线；停用当前服务只允许按该旧路线继续。
