# 0034 不在应用内重复验证邮件域名所有权

## 状态

已接受

- 提议与接受日期：2026-08-11
- 需求依据：[需求变更-0005：应用不重复验证邮件域名所有权](../需求/变更记录/0005-应用不重复验证邮件域名所有权.md)
- 影响模块：系统与初始化、域名与地址、运行状态

## 背景

Simlettra 的收信依赖部署者在 Cloudflare Email Routing 中建立规则，站外发信依赖管理员提供已经申请的 Resend 或 SMTP2GO 配置。系统只有一名可信管理员，不存在需要由产品防范管理员添加陌生域名的多租户平台边界。

在这种部署模型中，应用自行生成 DNS TXT 挑战只能重复证明外部平台已经要求部署者具备的配置能力。它还会增加数据库状态、DNS 查询、失败处理、初始化页面和维护文档，却不能证明邮件路由或 Provider 当前确实可用。

## 决定

1. Simlettra 信任当前唯一系统管理员提交的邮件域名，不执行额外的域名所有权验证。
2. 域名模块只负责规范化、系统内唯一性、启用、暂停、删除约束、全域收信规则和关联配置。
3. `mail_domains` 只使用 `active`、`paused` 和 `deleting` 状态，不保存验证挑战和验证完成时间。
4. 初始化事务直接创建处于 `active` 状态的首个域名，并同时创建唯一管理员、管理员主邮箱和系统单例。
5. Cloudflare Email Routing、Resend 和 SMTP2GO 的可用性通过各自的配置测试与运行健康状态观察，不转化成域名所有权状态。
6. 配置测试失败时显示可操作的诊断信息，但不自动删除域名，也不伪装成所有权验证失败。

## 备选方案

1. 使用 DNS TXT 挑战验证所有权：重复外部平台职责，增加初始化和状态维护，不采用。
2. 使用 Cloudflare API 令牌读取 Zone：要求额外高权限凭据，并把产品绑定到账号级资源管理，不采用。
3. 只有成功收信后才激活域名：会让初始化依赖外部邮件投递，并混淆域名配置与邮件运行状态，不采用。

## 后果

### 正面

1. 初始化步骤更少，更符合自部署系统由所有者直接管理的边界。
2. 不需要 DNS 查询依赖、验证挑战表、过期任务或轮询页面。
3. 域名状态只表达 Simlettra 自己能够控制的生命周期。

### 负面

1. 管理员可以输入尚未完成外部邮件路由或 Provider 配置的域名。
2. 域名处于启用状态不代表收信和站外发信已经可用，管理界面必须分别显示实际运行状态。

## 验证方式

1. 初始化和添加域名不产生 DNS 请求或验证挑战数据。
2. 非法域名和规范化后重复的域名被拒绝。
3. 合法且未重复的域名可以直接创建为 `active`。
4. 未配置 Cloudflare Email Routing 或 Outbound Mail Provider 时，域名仍存在，但对应健康检查清楚显示未配置或不可用。
5. 暂停、恢复和删除域名仍遵守地址、邮件和发信配置的关联约束。
