# 0035 采用 ASCII 邮箱前缀与 IDNA 域名规范化

## 状态

已接受

- 提议与接受日期：2026-08-11
- 需求依据：[需求变更-0006：确定首发邮箱地址字符规则](../需求/变更记录/0006-确定首发邮箱地址字符规则.md)
- 关联决定：[0014 分离账号、地址身份与地址占用](0014-分离账号地址身份与地址占用.md)

## 背景

邮箱地址创建后不可修改，并且同一地址文字释放后可能由新的地址身份重新使用。因此规范化算法是长期数据契约，必须在首份正式迁移和管理员主邮箱创建前确定。

完整 RFC 邮箱前缀允许引号和多种特殊字符，国际化邮箱又依赖 SMTPUTF8 支持。首发需要同时兼容 Cloudflare Email Routing、Resend、SMTP2GO、浏览器表单、搜索和地址唯一性，优先选择容易解释和长期维护的共同范围。

## 决定

1. 邮箱前缀只允许 `[a-z0-9._-]`，输入先转换为小写。
2. 前缀长度为 1 至 64 个字符，首尾必须是字母或数字，不能出现连续两个点。
3. 首发不支持非 ASCII 邮箱前缀和其他特殊字符，也不把加号解释为子地址标签。
4. 域名输入使用 URL 平台的 IDNA 处理转换为小写 ASCII Punycode；转换失败、包含端口、路径、空标签或不合法标签时拒绝。
5. 规范地址由规范前缀、`@` 和规范域名直接组成，显示地址也使用小写规范前缀，避免形成只有大小写不同的不可变显示身份。
6. 初始化、用户创建、别名、组织共享地址、全域认领和主地址迁移共享同一个地址值对象，不各自实现正则表达式。
7. 数据库唯一约束是并发下的最终防线，应用校验负责在写入前返回可理解的简体中文错误。

## 备选方案

1. 实现完整 RFC 5322 邮箱前缀：允许范围更广，但引号、转义和第三方服务兼容性显著增加测试成本，首发不采用。
2. 首发支持 SMTPUTF8 国际化前缀：对中文用户更完整，但收信和两家发信服务的共同边界尚不足以形成可靠承诺，不采用。
3. 只允许字母和数字：最简单，但会无理由排除常见的点、下划线和连字符，不采用。
4. 保留用户输入的邮箱前缀大小写：显示更自由，但不可变显示身份与不区分大小写唯一性容易产生误解，不采用。

## 后果

### 正面

1. 地址输入、比较、登录和 Provider 配置使用同一稳定格式。
2. 避免不同模块对大小写、特殊字符和国际化前缀作出不同解释。
3. 国际化域名仍可使用，内部存储和外部调用统一使用 Punycode。

### 负面

1. 需要引号、加号或中文邮箱前缀的用户无法在首发创建相应地址。
2. 以后放宽字符范围需要验证现有唯一性、路由和发信服务兼容性，并建立显式迁移。

## 验证方式

1. 合法前缀、边界长度和国际化域名得到稳定规范地址。
2. 大写输入统一转为小写，仅大小写不同的地址产生相同规范值。
3. 空白、连续点、首尾分隔符、加号、引号和中文前缀被拒绝。
4. 初始化与以后所有地址创建入口对同一输入产生完全相同的结果。
5. D1 唯一约束拒绝并发创建相同规范地址。
