# ADR-0037：以全局地址策略和权威任务释放保留别名

## 状态

已接受

- 决定日期：2026-08-12
- 依据：需求 `4.08`、`4.10`、`11.08`、数据-08、数据-09、数据-72 至数据-75、数据-102
- 关联决定：ADR `0003`、`0014`、`0024`、`0031`、`0035`、`0036`

## 背景

系统管理员需要设置邮箱前缀最短长度、禁止文字、保留名称和个人别名保留期。策略收紧只能影响以后创建的地址，不能让已有主地址或别名突然失效。个人别名删除后则要立即停止收发，但在 0 至 30 天的可选期限内继续占用原地址文字，到期后可靠释放。

地址身份、当前占用和历史归属已经分离。异步任务架构也已经确定 D1 保存权威任务，Cloudflare Queue 只负责唤醒，定时任务扫描并补投遗漏工作。本切片应复用这些边界。

## 决定

1. 使用单例 `address_policy_settings` 保存邮箱前缀最短长度和个人别名保留天数；默认分别为 1 和 0，管理员可以设置为 1 至 64 和 0 至 30。
2. 使用 `address_policy_terms` 保存两类规范化文字：`blocked_substring` 表示前缀中不得包含的文字，`reserved_name` 表示不得精确使用的完整前缀。
3. 管理员一次提交完整策略；设置、文字集合和成功审计在同一个 D1 原子批次中替换。策略使用递增版本防止两个管理页面互相覆盖。
4. 所有新建主地址、个人别名和以后新增的组织地址都必须使用同一策略校验。数据库插入触发器作为绕过应用和并发情况下的最后保护。
5. 已存在地址不因最短长度提高或新增禁止文字、保留名称而停用、改名或失去收发权限。
6. 删除个人别名时冻结当时策略的版本和保留天数。保留天数为 0 时立即删除 `address_claims`；大于 0 时把占用改为 `reserved` 并设置精确到期时间。
7. 保留期内，历史地址身份和已经结束的地址归属继续存在，任何用户或组织都不能重新占用相同文字。
8. 正式引入已经接受的统一 `background_tasks` 权威任务表。别名进入保留期时建立稳定的 `alias_release` 任务；Queue 消息只含任务编号和版本，不含邮箱地址、邮件内容或密钥。
9. Queue 消费者以租约和递增令牌领取任务，释放到期地址后把任务标记成功；重复消息不能重复释放。定时任务按小时扫描到期或遗漏任务并重新投递。
10. 如果 Queue 暂时不可用，别名删除仍以 D1 原子批次成功；地址继续安全保留，定时补投后再释放，不会提前被抢占。

## 备选方案

### 把策略字段放入 `system_instances`

字段数量暂时较少，但地址规则属于地址模块，未来组织地址、全域认领和主地址迁移都会依赖它；把策略混入系统身份表会扩大模块耦合，不采用。

### 把禁止文字和保留名称保存为 JSON

写入简单，但数据库无法对单项建立唯一约束，也难以在触发器中可靠验证，备份和迁移时也不易逐项检查，不采用。

### 只用每小时定时扫描 `address_claims`

可以完成释放，但与已经接受的统一任务架构不一致，也无法为以后邮件解析、对象清理和重试提供同一运行状态，不采用。

### 删除别名时等待保留期结束再结束归属

会让用户删除后仍可能继续收发或使用该地址，违反“先停收停发，再冻结地址文字”的已确认行为，不采用。

## 后果

1. 管理员可以理解并集中管理地址创建规则，普通用户创建时得到具体拒绝原因。
2. 删除响应需要明确返回是否立即释放以及预计释放时间；网页二次确认内容随当前策略变化。
3. 部署配置需要正式声明一个 Queue 和每小时 Cron，但仍由同一个 Worker 生产、消费和维护。
4. 后续组织地址、主地址迁移和全域认领必须复用地址策略服务和占用释放任务。
5. `background_tasks` 是共享基础结构，后续任务类型不得另建不兼容的私有任务表。

## 验证方式

1. 验证默认策略为最短 1、无禁止文字、无保留名称、别名立即释放。
2. 验证策略调整只影响新地址，已有地址继续可用。
3. 验证最短长度、包含禁止文字和精确保留名称在应用与数据库边界都被拒绝。
4. 验证保留期为 0 时立即释放，大于 0 时地址不能重新创建且删除响应显示到期时间。
5. 验证重复 Queue 消息只完成一次释放，未到期任务不会提前释放，定时扫描可以补投遗漏任务。
6. 验证策略修改、别名删除、地址占用变化、任务建立和审计任一步失败时整体回滚。
