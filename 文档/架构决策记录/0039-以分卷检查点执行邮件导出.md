# 0039 以分卷检查点执行邮件导出

## 状态

已接受

- 提议与接受日期：2026-08-12
- 依据：[第六批数据模型确认清单](../数据模型/第六批数据模型确认清单.md)中的数据-122
- 关联决定：[0033 以不可变记录和可验证清单完成审计、备份与迁移](0033-以不可变记录和可验证清单完成审计备份与迁移.md)

## 背景

用户需要导出自己的个人邮件，或由组织创建者导出组织邮件。邮件可能包含附件，导出结果还要能被其他邮件软件读取。Simlettra 首发以 Cloudflare Workers Free 为运行基线，因此不能在一次 Worker 请求或一次 Queue consumer 执行中把整个邮箱读入内存，也不能让一个超大导出任务长时间占用单次执行额度。

## 决定

1. 创建导出时只在 D1 中建立冻结清单，使用单条 `INSERT ... SELECT` 生成项目编号和顺序；Worker 不把全部邮件项目加载到 JavaScript 内存。
2. 导出输出为多个 ZIP 分卷。每个分卷按约 20,000,000 个源邮件字节组织，并包含每封邮件的 `.eml` 和简体中文 `导出清单.md`。
3. 每次 `generate_mail_export` 后台任务最多生成一个分卷。已写入的项目和制品是检查点，下一分卷通过新的 D1 权威后台任务继续；Queue 消息发送失败时由 Cron 依据任务账本补投。
4. 分卷写入对象存储并完成 D1 登记后才允许最终激活。只有所有冻结项目写入完成，导出运行才标记为成功。
5. 邮件原始 MIME 可能包含当前下载者无权看到的密送地址时，改用结构化数据重建邮件，并在邮件头标记重建来源。
6. ZIP 使用不压缩模式生成。邮件附件通常已经压缩，降低 Workers Free CPU 消耗比再次压缩更重要；对象大小仍必须通过平台容量预留和存储后校验。
7. 导出制品默认保留七天，导出记录不引用邮件、邮箱条目或组织外键，以免阻塞正常邮件永久删除。导出制品计入 KV/R2 平台资源用量，但不计入用户和组织逻辑邮件配额。

## 备选方案

1. 一次查询全部项目并在单次 Queue 任务中生成全部分卷：实现简单，但大邮箱会产生过大的 D1 返回结果、JavaScript 内存和单次执行时间，不采用。
2. 每个导出建立独立任务系统：可以单独调度，但会重复租约、重试、对账和 Cron 补投逻辑，不采用。
3. 先生成一个完整 ZIP 再提供下载：容易超过对象单项限制，也无法在中断后从中间继续，不采用。

## 后果

### 正面

1. 大邮箱导出不需要一次性把所有邮件正文和附件放入 Worker 内存。
2. Queue consumer 在每次执行后释放资源，失败可以从已完成分卷继续。
3. D1 中的冻结项目、项目状态、分卷和对象摘要可以相互对账。

### 负面

1. 用户可能得到多个下载分卷，网页需要显示分卷状态。
2. 导出完成时间取决于 Queue 和 Cron 的调度，不能承诺单次请求立即完成。
3. 真实 Workers Free 的 Queue CPU、内存、KV 单对象和 R2 对象边界仍必须远程验证。

## 验证方式

1. 创建个人导出和组织导出时，检查冻结数量、权限边界和项目唯一性。
2. 下载 ZIP 后验证 `.eml`、中文清单、文件哈希和密送地址不泄露。
3. 模拟对象损坏，确认当前任务安全重试且不产生重复分卷。
4. 模拟多分卷任务，确认每次任务最多写入一卷，下一任务可由 Queue 或 Cron 继续，最后才标记成功。
5. 过期或主动删除后确认对象实际清理，且不阻塞邮件和用户删除。
6. 在真实 Workers Free、KV 和 R2 绑定下复核内存、CPU、单对象大小和长任务行为。
