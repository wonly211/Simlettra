# 0044 以 D1 账本聚合运行健康并记录定时维护心跳

## 状态

已接受

- 决定日期：2026-08-13

## 背景

需求 `2.08` 与首发验收项 `验收-27` 要求唯一系统管理员能够判断收信、发信、存储和定时任务是否正常，同时运行信息不能泄露邮件正文。正式工程已经分别为收信、发信、资源用量和后台任务建立 D1 权威账本，但这些证据分散在不同模块，管理员不能快速判断哪些情况需要处理。

定时维护此前只执行补投、过期清理和资源刷新，没有保存整次运行的开始、成功或失败证据。仅依靠 Worker 日志无法区分“尚未运行”“正在运行”“运行失败”和“日志已经过期”，也不适合作为网页健康状态的长期事实来源。

## 决定

1. 健康状态只读聚合现有 D1 权威账本，不复制邮件正文、附件、邮箱地址明文、服务密钥或普通运行日志。
2. 管理员网页统一显示收信、发信、存储和定时维护四类摘要，状态只使用“正常”“需检查”“尚无记录”和“未配置”。整体状态只用于快速提示，不取代四类明细。
3. 收信依据操作阶段、最近可见时间、停滞操作和需人工处理结果判断；发信依据 Provider 与域名路线、逐收件人状态、结果未知和最近服务未接受判断。正常退信等业务结果不直接视为系统故障。
4. 存储复用 D1 与当前 KV/R2 的最新免费资源快照和阈值；缺少快照与快照不可用必须明确区分。
5. 新增 `scheduled_maintenance_runs`，每次 Cron 开始时写入“运行中”，全部步骤完成后写入“成功”；失败时保存受限步骤名、安全错误代码和简体中文摘要。状态只能从“运行中”前进到“成功”或“失败”。
6. 超过 15 分钟仍未完成的收发操作或维护运行视为停滞；最近一次定时维护超过两小时没有运行证据时保守提示“需检查”。这些数值是当前运维判定参数，不是邮件数据保留期。
7. 健康接口只允许当前唯一系统管理员读取。打开或刷新健康页不主动探测外部 Provider、通知服务或 Cloudflare API，避免产生外部副作用和额外额度消耗。
8. 健康状态用于定位方向，不承诺替代 Cloudflare 平台监控、Provider 控制台或真实端到端探测。

## 备选方案

1. 只展示 Cloudflare 与 Provider 在线探测：能发现部分外部连接问题，但每次打开页面都会产生外部请求，且无法证明内部收发、对象提交和后台任务状态，不采用。
2. 把所有模块健康结果周期性复制到一张汇总表：查询简单，但需要维护另一套易过期的派生状态和刷新任务，当前规模没有必要，不采用。
3. 只依赖 Worker 日志：无需新增表，但日志保留期、查询权限和结构不适合作为网页长期事实，且难以证明 Cron 是否从未运行，不采用。
4. 引入独立监控 Worker 或 Durable Objects：可以扩展实时能力，但违反单 Worker 与 Workers Free 首发基线，不采用。

## 后果

### 正面影响

1. 管理员可以在一个页面判断四类核心运行路径是否需要处理。
2. 聚合查询复用已有权威事实，不新增邮件内容副本，也不让健康页产生外部提交。
3. 定时维护具备可验证的开始、结束和失败步骤证据，Cron 缺失或停滞不再只能依赖日志猜测。
4. 普通用户、前端隐藏和管理员角色之外的账号都不能绕过服务端权限边界。

### 成本与限制

1. 健康结论是账本推断，不是对真实外部服务的在线探测；Provider 账号、Cloudflare 指标和通知通道仍需分别联调。
2. 固定时间窗口可能在极慢任务或时钟异常时产生保守告警，后续调整需要结合真实 Workers Free 运行证据。
3. 新部署在首次 Cron 运行、首次收信或尚未配置站外发信前会显示“尚无记录”或“未配置”，不能误称故障。
4. 升级与回退仍需独立版本说明、数据检查和远程演练；健康页本身不完成这些发布流程。

## 验证方式

1. 正式迁移建立受约束的 `scheduled_maintenance_runs`，并在迁移后通过外键检查。
2. 普通用户读取健康接口返回 `403`，当前唯一系统管理员可以读取四类摘要。
3. 空系统、正常证据、停滞收信、结果未知发信、资源停止线、失败 Cron、需人工处理任务和逾期任务均有高保真测试。
4. 正式定时维护处理器成功与失败时分别保存完成时间或安全错误信息，已经结束的运行不能倒退。
5. 桌面和 `390 × 844` 手机浏览器分别检查状态标签、长摘要、时间、刷新操作、横向溢出和控制台错误。
6. 在真实 Cloudflare Free 环境执行至少两次每小时 Cron，并核对页面结论与 D1、KV/R2、Queue 和 Provider 实际状态。
