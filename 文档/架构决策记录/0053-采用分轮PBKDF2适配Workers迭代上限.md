# 0053 采用分轮 PBKDF2 适配 Workers 迭代上限

## 状态

已接受

- 提议日期：2026-08-14
- 接受日期：2026-08-14
- 取代记录：[0011 采用平台原生密码哈希和可撤销不透明会话](0011-采用平台原生密码哈希和可撤销不透明会话.md)

## 背景

远程 Cloudflare Workers 首次初始化时，`POST /api/initialization/complete` 在管理员密码哈希阶段失败。真实运行日志显示，Workers Web Crypto 拒绝单次 PBKDF2 超过 100,000 次迭代，而原决定使用单次 900,000 次迭代。

原决定的安全目标仍然有效：密码必须使用平台原生的慢速 PBKDF2-HMAC-SHA-256，默认总计算量为 900,000 次，且不能因为平台单次调用上限而静默降低安全强度。

## 决定

1. 密码记录格式升级为 `format_version = 2`，算法标识为 `PBKDF2-HMAC-SHA-256-CHAINED`。
2. 总迭代次数仍保存为 `900000`，并继续满足数据库的 `iterations >= 600000` 约束。
3. 派生过程固定分为 9 轮，每轮调用 Workers Web Crypto PBKDF2-HMAC-SHA-256 `100000` 次；每轮使用原始 16 字节盐与四字节轮次编号组成的独立盐，上一轮 32 字节结果作为下一轮输入，最终结果仍为 32 字节。
4. 所有单次 Web Crypto 调用不得超过 `100000` 次。新建密码、登录验证、临时密码、管理员恢复和改密统一使用同一派生实现。
5. `format_version = 1` 且算法为单次 `PBKDF2-HMAC-SHA-256` 的旧记录不在 Workers 上尝试验证，验证结果为失败。由于无法从哈希反推出明文，不能自动转换；这类账号必须通过已确认的管理员重置或 `init_key` 恢复流程设置新密码。
6. 不新增数据库迁移。现有密码字段已经能够保存新版本的算法标识、总迭代次数、盐和结果；版本差异由验证逻辑处理。

## 备选方案

1. 直接把单次迭代降低为 `100000`：实现最简单，但会把已接受的总计算强度降低到原方案的九分之一，拒绝采用。
2. 使用 Wasm 或纯 TypeScript 的 Argon2id：需要引入新的核心密码实现、增加包体和运行风险，当前不符合可靠和易维护优先的路线。
3. 继续使用单次 `900000` 次 PBKDF2：在真实 Workers 环境无法运行，拒绝采用。

## 后果

### 正面

- 保留原定 `900000` 次总计算量，同时满足 Workers 单次 `100000` 次的运行上限。
- 不增加部署密钥、数据库字段或新的密码服务依赖。
- 所有密码相关流程继续共享一套版本化记录和验证规则。

### 负面

- 每次密码派生需要 9 次 Web Crypto 调用，调用开销略高于单次派生。
- 已按旧格式写入的密码记录不能在 Workers 上直接兼容验证，需要重置密码。
- 仍需在真实 Cloudflare Free 环境复核初始化、登录、改密和并发限速的 CPU 与时间表现。

## 验证方式

1. 单元测试验证新记录的版本、算法、总迭代次数、随机盐、32 字节结果、正确密码、错误密码和旧格式拒绝。
2. Worker HTTP 集成测试验证初始化可以原子建立管理员，并写入新密码记录。
3. 在真实 Cloudflare Workers Free 部署中重新执行初始化，确认不再出现 `NotSupportedError`，并检查初始化失败时不留下半套数据。
4. 发布前继续执行登录、改密、临时密码、管理员恢复和限速回归测试。
