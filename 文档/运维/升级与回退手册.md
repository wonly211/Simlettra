# 升级与回退手册

## 适用范围

本手册用于系统所有者升级自行部署的单 Worker Simlettra。它把升级分为准备、演练、备份、迁移、部署、数据检查和必要时回退七个阶段。任何远程步骤都必须先确认当前操作的是目标 Cloudflare 账号和资源。

本手册不要求系统所有者编写 SQL，但执行命令前仍应完整阅读对应版本说明。版本说明与本手册冲突时先停止升级，不要自行猜测。

## 升级前准备

1. 阅读 `文档/发布/` 中与目标迁移版本对应的升级说明，确认行为、配置、数据和已知限制。
2. 在管理员“运行健康状态”页面确认收信、发信、存储和定时维护没有无法解释的“需检查”。已有告警必须先记录原因。
3. 确认当前使用 `D1 + KV` 还是 `D1 + R2`，并记录当前 Worker、D1、KV/R2 和 Queue 资源。
4. 确认受保护部署配置中的 `init_key`、配置加密主密钥和外部服务凭据能够重新配置。不要把明文写入项目、命令历史或普通日志。
5. 保留可重新部署的上一版本源码或构建来源。没有上一版本就不能执行代码回退。
6. 选择低使用时段，通知当前用户升级窗口。备份完成后到切换完成前应尽量避免继续收发邮件。

## 本地演练

在新版本项目根目录运行：

```powershell
pnpm test:upgrade-rollback
pnpm check
```

第一条命令从迁移 `0023` 重建代表性数据，依次应用 `0024` 和 `0025` 并建立独立回退目标。第二条命令执行完整代码、类型、测试、备份恢复、旧系统迁移、升级回退、性能、网页控件可访问性和安全构建门槛。任一命令失败都应停止远程升级。

## 建立升级前备份

1. 在管理员网页创建完整备份，等待状态成功。
2. 下载清单和全部分卷，记录网页显示的清单 SHA-256。
3. 在本地校验并生成加密容器：

```powershell
node tools/本地备份恢复.mjs validate --manifest 清单.json --parts 分卷 --manifest-sha256 清单摘要
node tools/本地备份恢复.mjs pack --manifest 清单.json --parts 分卷 --output 加密备份
```

4. 确认清单中的迁移版本等于升级前实际版本、存储模式正确，且配置加密密钥版本能够另行提供。
5. 加密容器和密码分开保存。没有校验成功的完整本地备份，不执行远程迁移。

## 执行升级

1. 再次确认 `wrangler.jsonc` 指向正确的远程 D1、Queue 和 KV/R2 资源。
2. 按[0025 升级说明](../发布/0025升级说明.md)规定的顺序执行迁移。当前版本使用先迁移、后部署：

```powershell
pnpm db:migrate:remote
pnpm deploy
```

3. 迁移或部署失败时立即停止，不重复执行不清楚后果的命令。远程迁移工具会通过 D1 文件导入逐个执行迁移，并跳过已经记入 `d1_migrations` 账本的连续版本；仍需先查看错误并确认账本没有异常。

## 升级后数据检查

使用管理员页面和只读 SQL 完成以下检查：

```powershell
wrangler d1 execute DB --remote --config wrangler.jsonc --command "SELECT id, name, applied_at FROM d1_migrations ORDER BY id DESC LIMIT 5"
wrangler d1 execute DB --remote --config wrangler.jsonc --command "PRAGMA foreign_key_check"
wrangler d1 execute DB --remote --config wrangler.jsonc --command "SELECT COUNT(*) AS user_count FROM users"
wrangler d1 execute DB --remote --config wrangler.jsonc --command "SELECT COUNT(*) AS domain_count FROM mail_domains"
wrangler d1 execute DB --remote --config wrangler.jsonc --command "SELECT COUNT(*) AS message_count FROM messages"
wrangler d1 execute DB --remote --config wrangler.jsonc --command "SELECT task_status, COUNT(*) AS task_count FROM background_tasks GROUP BY task_status ORDER BY task_status"
```

检查要求：

1. 最新迁移名称与版本说明一致。
2. `PRAGMA foreign_key_check` 返回零行。
3. 用户、域名和邮件数量与升级前记录相符；升级期间的新数据必须能够解释。
4. 后台任务没有持续增加的 `needs_attention` 或逾期项目。
5. 管理员可以登录，普通用户仍不能读取他人邮件；收件箱、邮件详情、写信和永久删除至少各做一次非破坏性检查。
6. 运行健康状态的四类摘要与实际配置相符，页面和 Worker 日志没有正文、附件或密钥。

## 如何选择回退方式

### 只回退 Worker 代码

仅在以下条件全部满足时使用：

1. 版本说明明确标记迁移与上一版本代码兼容。
2. 外键、数量和关键流程检查全部通过。
3. 问题只存在于新 Worker 行为，不涉及数据损坏或对象缺失。

重新部署保留的上一版本 Worker。不要删除已经应用的迁移，也不要手工删除新表。当前 `0023` 到 `0025` 升级包含 `0024` 表重建，没有承诺旧代码可直接配合升级后的 D1 使用，因此默认不采用只回退 Worker 代码；应按下节从升级前备份恢复到全新资源。

### 从备份恢复到全新资源

出现以下任一情况时使用：

1. 版本说明没有承诺旧代码兼容。
2. 外键、数量、对象引用或搜索重建检查失败。
3. 迁移改写了旧代码依赖的数据，或者无法判断是否已经损坏。
4. 代码回退后仍不能正常读写。

处理顺序：

1. 停止失败升级资源继续接收写入，不在原资源上执行逆向 SQL。
2. 创建与备份迁移版本、存储模式一致的全新空白 D1 与空白 KV/R2。
3. 按[本地工具说明](../../tools/README.md)执行 `plan`、`apply` 和 `finalize`，任何阶段失败都废弃目标后从空白资源重来。
4. 清单哈希、表行数、对象哈希、外键、对象引用和搜索重建六项全部成功后，为目标 Worker 配置必要密钥。
5. 把 Worker 绑定切换到恢复后的 D1、KV/R2 和对应 Queue，再部署上一版本 Worker。
6. 重新执行本手册的升级后检查。确认稳定前保留失败升级资源，不急于删除。

## 当前限制

1. 本地演练不能代替真实 Cloudflare Free 的 D1、KV/R2、Queue 和 Worker 绑定切换。
2. D1、对象存储、搜索和外部服务不具备一次跨资源原子回退。
3. 升级前备份之后产生的新邮件和设置不在该恢复点中；正式演练必须评估维护窗口内允许的数据差异。
4. 当前没有产品内“一键升级”或“一键回退”按钮，所有破坏性远程步骤都由系统所有者明确执行。
