# 澄笺基本排错指南

## 文档状态

- 状态：当前，已纳入首次 Cloudflare Git 真实部署故障
- 建立日期：2026-08-13
- 适用版本：`0.1.0-dev.0`，最新正式迁移为 `0025-补齐早期内部投递容量拒绝事实.sql`
- 适用对象：按照[首次部署与初始化指南](../部署/首次部署与初始化指南.md)操作的系统所有者

## 排错原则

遇到问题时先停止重复操作，再按发生阶段查找原因。尤其不要连续点击“发送”、反复执行远程迁移、删除资源或重新初始化。

可以记录：

- 发生时间和所在时区；
- 正在执行的步骤；
- 无敏感信息的错误代码和错误摘要；
- 使用 R2 还是 KV；
- Worker、D1、R2/KV 和 Queue 的资源名称；
- 最新迁移文件名和应用版本；
- 问题能否稳定复现。

不能记录或发送：

- `INIT_KEY`、配置加密主密钥或第三方服务密钥；
- 登录密码、临时密码、验证码、会话 Cookie 或 CSRF 令牌；
- 完整邮件正文、原始 MIME 或附件内容；
- 含有上述信息的截图、录屏、终端历史或日志。

## 一、先确认账号和版本

在项目目录执行：

```powershell
node --version
pnpm --version
pnpm exec wrangler --version
pnpm exec wrangler whoami
```

当前工程要求 Node.js `22.13.0` 或更高、pnpm `11.x`，并锁定 Wrangler `4.120.1`。`whoami` 显示的账号必须是实际持有目标资源的账号。

### 提示找不到 `node`

Node.js 没有安装，或安装后尚未重新打开终端。安装符合要求的 Node.js 后关闭所有 PowerShell 窗口并重新打开，再执行 `node --version`。

### 提示找不到 `pnpm`

pnpm 没有安装或没有进入系统路径。安装 pnpm `11` 后重新打开终端。不要因为方便改用另一个包管理器生成新的锁文件。

### Wrangler 登录到错误账号

停止创建、迁移和部署。先退出错误账号，再运行 `pnpm exec wrangler login`；只有 `whoami` 正确后才能继续。

## 二、依赖或本地检查失败

先执行：

```powershell
pnpm install
pnpm check
```

常见原因：

| 现象 | 先检查 | 不要做 |
| --- | --- | --- |
| 依赖下载失败 | 网络、代理、磁盘空间和系统时间 | 删除锁文件或随意更换依赖版本 |
| 格式或代码规则失败 | 是否修改过代码或配置 | 关闭检查后继续部署 |
| 类型检查失败 | Node/pnpm 版本和依赖是否完整 | 使用旧构建产物部署 |
| 测试失败 | 记录第一个失败文件和错误摘要 | 反复运行直到偶然通过后忽略 |
| 备份、迁移或性能自检很久 | 等待当前命令完成；旧系统迁移自检本来就较耗时 | 同时启动多个 `pnpm check` |

`pnpm check` 仍在运行时不要关闭终端，也不要再次启动同一命令。失败后保留第一处错误，它通常比随后出现的连锁错误更有价值。

## 三、资源创建或配置失败

### 提示资源已经存在

自动部署会按完整名称复用资源，这是正常行为。先确认资源名分别是 `simlettra-<Worker项目名称>-meta`、`simlettra-<Worker项目名称>-raw` 和 `simlettra-<Worker项目名称>-tasks`。如果同名资源来源不明或 D1 已有其他系统数据，停止部署并换用新的 Worker 项目名称，不要手工覆盖或删除。

### 提示资源不存在或无权限

确认：

1. Cloudflare Git 构建属于正确账号；
2. `SIMLETTRA_STORAGE_MODE` 是 `r2` 或 `kv`；
3. Cloudflare 实际 Worker 项目名称只包含小写字母、数字和连字符，且不超过 47 个字符；
4. Workers Builds 有权列出和创建 D1、R2/KV 与 Queue；
5. 当前账号的相应 Free 资源功能已经可用，没有付费或权限提示阻止创建。

普通 Cloudflare Git 部署不需要填写 D1、KV、R2 或 Queue 的编号和名称，也不要改动绑定名 `DB`、`MAIL_OBJECTS_R2`、`MAIL_OBJECTS_KV` 或 `TASK_QUEUE`。

### 控制台提示会产生费用

立即停止。本项目按 Cloudflare Free 设计，不能在未确认影响时接受付费升级。保存不含账号编号和密钥的提示摘要，重新核对当前套餐和资源范围。

## 四、远程迁移失败

查看尚未应用的迁移：

### R2 模式

```powershell
pnpm exec wrangler d1 migrations list DB --remote --config wrangler.jsonc
```

### KV 模式

```powershell
pnpm exec wrangler d1 migrations list DB --remote --config wrangler.kv.jsonc
```

列表只显示尚未应用的迁移。全新数据库在部署前应按编号从 `0001` 到 `0022` 应用；不应跳号或手工把迁移标记为成功。

迁移失败时：

1. 不要重复修改同一个正式迁移文件；
2. 不要直接编辑远程迁移账本；
3. 确认目标 D1 是否真的是本次部署的空白或预期数据库；
4. 记录失败迁移编号和无敏感信息的错误摘要；
5. 若是首次空白测试部署，优先废弃失败目标并从新的空白资源重来；
6. 若目标已有真实数据，停止操作，先完成备份和影响分析。

## 五、部署失败或网页打不开

正式发布默认由 Cloudflare 连接 GitHub 部署。先打开 Worker 的“构建”记录，确认两条命令是：

```text
构建命令：pnpm run build
部署命令：npx wrangler deploy
```

然后核对 `SIMLETTRA_STORAGE_MODE` 和 Cloudflare 实际 Worker 项目名称。构建日志应显示正在创建或复用 `meta` D1、`raw` KV/R2 与 `tasks` Queue。提示“目标 D1 不是当前迁移版本”时，不要重试覆盖；先按升级手册完成备份和迁移。

### 提示 D1 编号 `00000000-0000-0000-0000-000000000000` 不存在

这是旧公开部署快照在 Cloudflare 默认命令下使用占位配置造成的历史错误。更新到包含 ADR 0052 的最新公开仓库后，只保留 `SIMLETTRA_STORAGE_MODE` 构建变量并重新部署；新构建会自动创建或复用命名资源。旧失败可能留下 `simlettra-mail` R2 存储桶和 `simlettra-tasks` Queue，新规则不会复用它们；确认它们为空且不再需要后再删除。

### 全新 D1 提示“已有数据但没有正式迁移账本”

2026-08-14 的第二次真实 Cloudflare 构建证明新建 D1 会出现 Cloudflare 保留表 `_cf_KV`。公开部署提交 `a1b58d0` 已修复该误判，只忽略精确保留表 `_cf_KV`，并继续把其他未知表视为需要人工检查的数据。更新到该提交后直接重试，构建会复用已经创建的 D1、KV/R2 与 Queue，不需要删除资源。若日志列出的表不止 `_cf_KV`，不要绕过保护，先确认目标 D1 是否属于其他系统或失败迁移。

以下 Wrangler 命令只适用于本地高级部署与真实验收。

先确认执行的是：

```powershell
pnpm deploy:r2
```

或：

```powershell
pnpm deploy:kv
```

不要直接对源 `wrangler.jsonc` 执行 `wrangler deploy`。项目使用 Cloudflare Vite 插件，部署目标是安全构建后生成的最终配置。

### 部署预检提示静态资源目录缺失

通常是直接部署了源配置。重新使用项目提供的 `pnpm deploy:r2` 或 `pnpm deploy:kv`。

### Worker 地址返回空白页或 404

确认部署输出没有失败，且最终配置同时包含 Worker 代码和静态资源。尝试浏览器无痕窗口，排除旧缓存；仍失败时记录请求时间、状态码和 Worker 名称。

### 网页能打开但接口报错

这通常表示静态资源已部署，但 D1、KV/R2、Queue、迁移或密钥绑定不完整。按“资源创建”“远程迁移”和“初始化”三节逐项检查。

## 六、初始化失败

### 提示“部署配置中的初始化密钥缺失或长度不足”

`INIT_KEY` 没有设置到当前 Worker，或者少于 16 个字符。在 Cloudflare Worker 的“设置 → 变量和机密”中检查管理员可查看的 `INIT_KEY` 文本变量，修正后重新部署当前版本。不要改成保存后不可回看的 Secret，也不要放入 GitHub 构建变量。

### 提示“初始化密钥不正确”

确认输入的是当前 Worker 的 `INIT_KEY`，不是登录密码或配置加密主密钥。连续失败五次会限制 15 分钟；触发后等待，不要换浏览器绕过。

### 提示“系统已经完成初始化”

这是保护行为。初始化只能执行一次，直接回到登录页。不要为了重做向导而清空已有数据库。

### 邮箱前缀或域名无效

邮箱前缀只使用小写英文字母、数字、点、下划线和连字符，首尾为字母或数字；域名只填 `example.com`，不要包含协议、端口、路径或 `@`。

### 密码被拒绝

密码需要 15 至 128 个字符，不能是常见、简单重复或明显包含账号信息的内容。不要把满足规则的真实密码发给别人帮助排错。

### 初始化中途失败

刷新系统状态。正式初始化使用 D1 原子批次，失败不应留下半套数据；如果页面既不能继续初始化也不能正常登录，停止操作并记录时间和错误代码，不要手工补写数据库。

## 七、收不到邮件

按以下顺序检查：

1. Cloudflare Email Routing 已为正确域名启用；
2. 路由动作是 **Send to a Worker**，目标是当前部署的 Worker，规则状态为启用；
3. 澄笺中的域名、地址和用户都没有暂停或禁用；
4. 收件地址已经创建，或该域名已启用全域收信；
5. 来信没有命中发件地址、发件域名、主题或正文拒收规则；
6. Queue consumer 能够处理任务；
7. 存储没有达到预警停止线或逻辑配额；
8. 管理员“运行健康”中的收信、存储和定时维护状态没有显示“需检查”。

邮件只有在原始 MIME、正文和附件全部保存并校验后才会显示。Email Routing 已收到但收件箱暂时没有邮件时，不要立刻重复投递多封相同邮件；先查看 Queue 和健康状态。

接近 20 MB 的邮件在真实 Workers Free 中仍待正式验收。小邮件成功而大邮件失败时，应记录原始总字节数、处理阶段和安全错误代码，不能私自降低产品限制或切换付费方案。

## 八、邮件发不出去

先区分收件人：

- 全部是本系统地址：站内直投不需要 Resend 或 SMTP2GO；
- 含站外地址：必须为发件域名配置启用的 Provider 和路线。

检查：

1. 发件地址属于当前用户，或当前用户获准使用组织地址；
2. 域名有启用的默认 Provider；
3. Provider 凭据和回调凭据填写正确；
4. `CONFIG_KEY` 存在且仍是加密这些凭据时使用的主密钥；
5. 单封邮件没有超过 20,000,000 字节，也没有超过实际 Provider 的更小限制；
6. 用户每日配额和域名月度配额还有余量；
7. 发送与存储健康状态没有“需检查”。

如果状态是“结果未知”，不要反复点击发送，也不要手工切换 Provider。系统会在不能确定服务是否已经接受邮件时停止自动重发，以避免同一收件人收到重复邮件。

## 九、通知或自动转发失败

通知和自动转发失败不会删除原始来信。确认订阅或转发规则仍启用、外部邮箱已经验证、通道凭据正确、目标地址可达，并查看最近一次安全错误摘要。

排错时不要把通知内容改成真实敏感邮件，也不要把完整响应正文写入日志。先使用虚构主题和正文的测试邮件。

## 十、存储或配额显示异常

管理员资源页面会区分 Cloudflare 官方指标和 Simlettra 本地估算，并显示更新时间。官方指标缺失或过期时，系统会更保守，不会把未知当作仍有空间。

检查：

1. 当前模式是 R2 还是 KV；
2. Cloudflare 只读配置是否存在且验证成功；
3. 快照更新时间和数据来源；
4. 账号总量、当前数据库或命名空间/存储桶两个口径；
5. 用户或组织逻辑配额是否同时耗尽；
6. 是否已经达到预警线或停止线。

达到停止线后，新增收信、草稿附件和已发送副本会停止增长，但阅读、导出、备份和永久删除仍应可用。不要通过修改 D1 数值绕过保护。

## 十一、定时维护显示“需检查”

当前配置每小时运行一次 Cron。首次部署尚未运行时可能显示“尚无记录”；超过预期时间仍无心跳，或最近一次运行失败，才需要检查。

确认最终部署配置包含 `0 * * * *`，Cloudflare 控制台中 Worker 的 Cron Trigger 存在，并查看安全错误代码和失败步骤。不要在日志中加入邮件正文来辅助定位。

## 十二、安全查看实时日志

只有在确有需要时短时间查看 Worker 日志。当前代码设计不主动记录正文、附件、密码或密钥，但真实发布前仍需要人工审计。

R2 模式的最终配置位于 `dist/simlettra/wrangler.json`，KV 模式位于 `dist/simlettra_kv/wrangler.json`。使用日志时：

1. 先用虚构邮件复现；
2. 只记录状态码、安全错误代码、任务类型和时间；
3. 不截取请求头、Cookie、密钥或完整请求体；
4. 复现完成后立即停止日志会话；
5. 发现敏感信息时立即停止分享，按泄露事件处理并更换相关凭据。

## 十三、什么时候必须停止

出现以下任一情况，不要继续尝试：

- 账号、资源或部署目标与计划不一致；
- Cloudflare 提示将产生未预期费用；
- 迁移失败后目标数据库状态不明确；
- 邮件可能重复发送，但 Provider 是否接受无法确认；
- 已成功接收的邮件正文或附件疑似丢失；
- 普通用户能够读取无权访问的个人或组织邮件；
- 日志、截图或终端泄露了密钥、密码、令牌、正文或附件；
- 完整恢复、版本回退或旧系统迁移的对账失败；
- 接近 20 MB 邮件在 Workers Free 上无法稳定完成。

这些情况需要先保存脱敏证据、限制影响范围，再分析原因。不要用生产邮箱继续试错。

## 十四、排错记录模板

```text
发生时间与时区：
项目版本与最新迁移：
存储方式：D1 + R2 / D1 + KV
发生阶段：安装 / 资源 / 迁移 / 部署 / 初始化 / 收信 / 发信 / 通知 / 存储 / 定时维护
操作前状态：
执行的命令或页面操作（不得包含密钥）：
安全错误代码或状态码：
预期结果：
实际结果：
是否可重复：
已经停止的后续操作：
```

提交记录前再检查一次，确认没有真实地址、完整主题或正文、附件名中的敏感信息、账号编号、密钥和令牌。
