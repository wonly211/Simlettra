# 真实 Cloudflare Free 远程验收运行手册

## 文档状态

- 状态：当前；R2 模式已完成资源、迁移、部署、双密钥和初始化鉴权，后续阶段待执行
- 建立日期：2026-08-13
- 适用版本：迁移 `0025-补齐早期内部投递容量拒绝事实.sql`
- 对应证据模板：[真实远程验收证据模板](../验收/真实远程验收证据模板.md)
- 首次执行记录：[2026 年 8 月 13 日 R2 首次部署记录](../验收/2026年8月13日-R2首次部署记录.md)
- 适用对象：能够登录自有 Cloudflare 账号的系统所有者

## 目的

本手册用于补齐本地测试不能证明的真实 Cloudflare Free 能力，包括两种存储部署、接近 20 MB 收信、Queue、Cron、外部发信与通知、免费资源指标、备份恢复、升级回退、性能、日志安全和真实用户流程。

手册不会自动操作生产资源。所有命令必须先确认 Cloudflare 账号、资源名、配置文件和目标环境；不确定时立即停止。

## 总体原则

1. `D1 + R2` 与 `D1 + KV` 使用两套完全独立的验收资源，不共用 D1、Queue、地址或邮件数据。
2. 先用测试域名、测试 Provider 和测试通知账号验收，不把现有生产邮箱直接接入开发版。
3. 每阶段完成后立即填写证据模板；失败时先保存无敏感信息的错误代码、时间和影响，再停止后续阶段。
4. 任何文档、截图、终端输出和日志都不得包含 `init_key`、配置加密主密钥、Cloudflare Token、Provider 密钥、回调密码、会话 Cookie、完整邮件正文或附件内容。
5. 未通过接近 20 MB Workers Free 验证时，不得静默降低产品上限、切换 Paid 或宣称首发可用；必须重新提交产品方案。

## 阶段零：本地门槛

在连接远程账号前执行：

```powershell
pnpm check
pnpm test:security
```

两条命令任一失败都停止。记录版本、最新迁移、56 个测试文件与 234 项测试结果，以及备份恢复、旧系统迁移、升级回退、早期逻辑配额迁移、性能和网页控件可访问性自检结果。

## 阶段一：准备独立资源

### R2 模式

```powershell
pnpm exec wrangler d1 create simlettra --location apac
pnpm exec wrangler r2 bucket create simlettra-mail --location apac
pnpm exec wrangler queues create simlettra-tasks
```

把 D1 返回的 `database_id` 写入 `wrangler.jsonc`。若资源采用其他名称，同时修改配置中的 `database_name`、`bucket_name` 和 Queue 名称；绑定名 `DB`、`MAIL_OBJECTS_R2`、`TASK_QUEUE` 不得改变。

### KV 模式

```powershell
pnpm exec wrangler d1 create simlettra-kv --location apac
pnpm exec wrangler kv namespace create simlettra-mail-kv
pnpm exec wrangler queues create simlettra-kv-tasks
```

把 D1 返回的 `database_id` 和 KV 返回的 `id` 写入 `wrangler.kv.jsonc`。绑定名 `DB`、`MAIL_OBJECTS_KV`、`TASK_QUEUE` 不得改变。

`apac` 只是面向中国时区验收的默认位置提示，不是数据驻留承诺；部署者可以按实际用户位置选择 Wrangler 4.120.1 支持的其他区域。

### 运行时变量准备

部署前分别生成 `INIT_KEY` 与 `CONFIG_KEY`。`INIT_KEY` 至少 16 个字符；`CONFIG_KEY` 是独立生成的 32 字节随机 Base64 值，不得复用 `init_key`。唯一系统管理员直接负责两者的安全，实际 Worker 创建后在 Cloudflare 控制台以可查看的文本变量保存，完整步骤见[首次部署与初始化指南](../部署/首次部署与初始化指南.md)。

### 阶段停止条件

- 命令显示的账号、资源名或位置与计划不符。
- D1、KV、R2 或 Queue 不是 Cloudflare Free 可用资源，或控制台提示即将产生费用。
- 配置中仍存在全零占位编号。
- 密钥曾进入 GitHub、构建变量、命令参数、屏幕录制或普通日志。

## 阶段二：迁移、构建与部署

### R2 模式

```powershell
pnpm db:migrate:remote
pnpm deploy:r2
```

### KV 模式

```powershell
pnpm db:migrate:remote:kv
pnpm deploy:kv
```

两种部署命令都会重新执行统一质量门槛，再用对应 Wrangler 配置完成安全生产构建。R2 和 KV 生成的最终部署配置分别位于 `dist/simlettra/wrangler.json` 与 `dist/simlettra_kv/wrangler.json`。

部署后在实际 Worker 的“设置 → 变量和机密”中，把 `INIT_KEY` 与 `CONFIG_KEY` 添加为唯一管理员可查看的文本变量，然后重新部署当前版本。不要使用保存后不可回看的 Secret，也不要把值放进 GitHub 构建变量。随后打开 Worker URL，通过 `init_key` 完成网页初始化。分别记录：唯一管理员、首个域名、管理员主邮箱、禁止重复初始化、桌面和手机视口结果。不要在验收记录中抄写密码和密钥。

### 阶段停止条件

- 远程迁移不是从 `0001` 顺序执行到 `0025`，或出现失败但原因不清楚。
- 部署绑定缺少 D1、当前 KV/R2、Queue 或静态资源。
- 网页初始化留下半套数据、允许第二次初始化或域名被错误要求 DNS 所有权验证。
- Worker 控制台显示 Paid 专属能力或产生费用风险。

## 阶段三：收信、Queue 与 20 MB 门槛

1. 在 Cloudflare Email Routing 中把测试域名来信路由到当前 Worker。
2. 依次投递纯文本、HTML、普通附件、重复来源事件和失败重试样本。
3. 按[多地址收信事件语义核验](../验证/Cloudflare多地址收信事件语义核验.md)分别投递“同一用户主地址与别名”“不同用户”“个人与组织”“可见后迟到”和“Queue 故障”样本；记录收信操作、物理邮件、冻结路由、实际投递、邮箱条目、对象和逻辑用量数量。
4. 验证邮件只在原始 MIME、正文和附件全部校验后可见，重复投递只保存一次；官方没有保证多地址事件的调用数量和原始字节一致性，必须以本次真实证据判断。
5. 验证暂停域名、地址、用户、禁用用户和四类拒收规则；恢复后只接收新到邮件。
6. 启用全域收信，验证查看授权、未知地址、并发认领和历史来信迁入。
7. 使用 19,900,000 字节附近的单附件、多附件和纯文本 RFC 822 样本，观察 Email Handler、Queue consumer、D1、KV/R2、重试次数、CPU、内存和最终完整性；至少一个样本包含多个本地地址。
8. 分别在 KV 与 R2 模式重复执行关键样本。

20 MB 按 20,000,000 个原始邮件字节执行。样本内容使用虚构地址和无敏感信息的重复文本或随机字节。

### 阶段停止条件

- 已成功送达 Worker 的邮件静默消失、出现半封可见邮件或附件缺失。
- 接近 20 MB 样本在 Workers Free 中超出 CPU、内存、消息或重试边界。
- 重试产生重复邮件，或 KV 一致性等待不能最终收口。
- 同一原始邮件的多地址事件缺少任一路由，或因平台改写原始字节而形成多封物理邮件。
- 并发认领产生多个地址归属或越权读取。

## 阶段四：域外发信与回调

1. 为测试域名分别准备 Resend 和 SMTP2GO 测试配置，互换默认与备用顺序。
2. 实测两家当前账号对最终 MIME 和附件的单封大小限制；Simlettra 必须采用自身 20 MB 与当前 Provider 限制中的较小值。
3. 验证站内、站外和混合收件人；混合发送只产生一个已发送条目。
4. 验证逐收件人状态、Provider 名称、明确未接受后的备用切换和结果未知后停止自动动作。
5. 验证 Resend Svix 与 SMTP2GO HTTPS Basic Auth 回调；重复、乱序、过期和伪造事件不能改坏状态。
6. 模拟响应丢失和超时；Resend 使用相同幂等键，SMTP2GO 结果未知时不能自动重发。

### 阶段停止条件

- 同一收件人收到重复邮件。
- 结果未知后自动切换或重发。
- 无效回调被接受，或 Provider 密钥出现在普通用户界面与日志。
- 实际大小限制与产品判断不一致。

## 阶段五：通知、转发和资源状态

1. 使用 ntfy、Gotify、WxPusher、Telegram 和 Bark 的测试目标各发送一次真实通知。
2. 验证通知包含发件人、收件人、主题和完整安全正文，不包含附件；网络失败不影响原始来信。
3. 验证外部邮箱验证码、全部个人来信转发、指定地址转发、防重和防环路。
4. 配置 Cloudflare 只读指标访问，核对 D1、当前 KV/R2 的账号与当前资源双口径、更新时间、数据来源和本地估算降级。
5. 让 Cron 至少运行三个小时，确认定时维护心跳、Queue 补投和健康摘要与实际账本一致。
6. 观察页面每 60 秒自动刷新、后台暂停、网络恢复和失败退避产生的 Worker 请求及 D1 读取成本。

### 阶段停止条件

- 通知或转发失败导致原邮件丢失、隐藏或重复。
- 通知发送附件、未净化脚本内容或越权组织邮件。
- 资源指标缺少统计口径却被显示为精确值。
- Cron 未运行、自动刷新成本接近免费额度上限或健康页泄露敏感内容。

## 阶段六：备份、恢复、升级与迁移

1. 在每种存储模式中生成包含 D1 与当前对象的完整备份，下载、校验并生成加密本地容器。
2. 为每种模式新建空白 D1、空白 KV/R2 与独立 Queue，按[升级与回退手册](升级与回退手册.md)执行完整恢复和六项检查。
3. 从迁移 `0023` 的隔离资源依次升级到 `0025`，按[0025 升级说明](../发布/0025升级说明.md)检查迁移账本、行数、外键、配额、内部投递、搜索、健康状态和邀请码约束。
4. 在隔离资源中分别演练兼容代码回退，以及从升级前备份恢复到全新资源并切换绑定。
5. 使用真实旧系统数据副本完成只读快照、独立演练、重复执行、七类对账和失败报告；不得直接读取唯一生产副本。

### 阶段停止条件

- 备份无法校验、无法加密或无法恢复到空白资源。
- 任一恢复检查失败却仍显示成功。
- 在原生产 D1 上尝试逆向 SQL 或覆盖式恢复。
- 迁移工具写入旧系统来源，或真实数据对账不一致。

## 阶段七：性能、浏览器与安全

1. 在隔离环境建立 50 名测试用户和累计 100,000 封测试邮件，10 名用户同时执行列表、详情、搜索、回复和发送。
2. 记录浏览器从操作开始到可交互的完整时间，不只记录 D1 查询；常用列表和详情第 95 百分位应低于 2 秒。
3. 在当前主流 Chrome、Edge、Firefox 和 Safari 验证电脑流程；在 `390 × 844` 或真实手机浏览器验证读信、搜索、回复、写信和基础设置。
4. 使用[发布前安全人工检查表](../验收/发布前安全人工检查表.md)逐项复核真实部署，并审查 Worker、Queue、Cron、Provider 和通知日志不含密码、密钥、令牌、邀请码、正文或附件。
5. 由非程序员依据简体中文文档从空白资源完成部署、初始化、基本排错和多人共享收发邮件。

### 阶段停止条件

- 第 95 百分位超过 2 秒且无法解释为测试端设备问题。
- 关键流程在任一目标浏览器不可完成，或手机存在遮挡、横向溢出和不可操作控件。
- 发现越权、脚本执行、令牌泄露、重复发信或敏感日志。
- 非程序员必须修改源码、猜测配置或依赖口头指导才能完成。

## 完成判断

只有两个存储模式的必需阶段全部通过、失败均已处理、证据模板没有空白必填项，并由系统所有者确认真实资源与费用边界后，才可以把相应首发验收项更新为“通过”。任何单一模式、本地结果或截图都不能替代另一模式与完整流程。
