# 澄笺首次部署与初始化指南

## 文档状态

- 状态：当前，首次 Cloudflare Git 真实构建故障已经修复，待重新部署和非程序员验收
- 更新日期：2026-08-14
- 适用版本：`0.1.0-dev.0`，最新正式迁移为 `0025-补齐早期内部投递容量拒绝事实.sql`
- 适用对象：拥有自己的 Cloudflare 账号和邮件域名，但不以编程为日常工作的部署者
- 高级路径：[真实 Cloudflare Free 远程验收运行手册](../运维/真实Cloudflare-Free远程验收运行手册.md)

## 先读这一页

正式发布后的默认部署方式是：在 Cloudflare 的“创建 Worker”页面连接 Simlettra GitHub 仓库。Cloudflare 会从 GitHub 读取代码、运行项目检查并部署 Worker。普通部署者不需要在自己的电脑上安装 Node.js、pnpm 或 Wrangler。

当前版本仍是开发版，请先使用测试域名和独立测试资源，不要直接接管正在使用的生产邮箱。完成本指南后会得到一个单 Worker 网页应用、一份 D1、一个 R2 或 KV 邮件对象存储、一个 Queue，以及唯一系统管理员和管理员主邮箱。

## 一、准备项目代码

1. 当前测试可以使用[公开部署测试仓库](https://github.com/wonly211/Simlettra)，正式发布后应选择带正式版本标识的可信版本，并按需要派生到自己的仓库。
2. 不要把别人已经填写过的资源编号、账号信息或密钥带进自己的仓库。
3. 首次测试建议保持仓库为私有；无论仓库是否私有，都不能提交真实密钥。

公开部署测试仓库已经建立 `main` 分支和首个可追溯提交，但当前仍没有正式版本标签，也尚未完成 Cloudflare 真实 Git 连接和首发验收。不能把测试分支或开发快照当成已经验收的生产版本。

## 二、选择存储方式

| 选择 | 适合情况 | 默认逻辑配额 | 部署自动准备 |
| --- | --- | --- | --- |
| **D1 + R2（推荐）** | 希望保存更多邮件和附件 | 每名用户和每个组织各 1,000,000,000 字节 | D1、R2、Queue |
| **D1 + KV** | 邮件量很小，明确希望使用 KV | 每名用户和每个组织各 100,000,000 字节 | D1、KV、Queue |

选择后不能在一套已初始化系统中直接切换。本指南建议第一次使用 R2。创建资源时以 Cloudflare 控制台当天显示的 Free 套餐提示为准，出现付费提示时停止。

## 三、确认 Cloudflare 资源权限

普通部署者不需要手工创建 D1、R2、KV 或 Queue，也不需要复制资源编号。请先确认当前 Cloudflare 账号可以使用：

1. Workers；
2. D1；
3. 当前选择的 R2 或 KV；
4. Queues。

Cloudflare Git 构建会使用实际 Worker 项目名称自动创建或复用：

- `simlettra-<Worker项目名称>-meta`：D1；
- `simlettra-<Worker项目名称>-raw`：R2 存储桶或 KV 命名空间；
- `simlettra-<Worker项目名称>-tasks`：Queue。

同名资源已存在时会复用，不会创建第二份。首次测试应选择一个没有旧 Simlettra 数据的 Worker 项目名称；出现付费提示时停止，不要继续启用付费方案。

## 四、连接 GitHub 创建 Worker

1. 打开 Cloudflare 的 **Workers 和 Pages**。
2. 选择 **创建应用** 或 **创建 Worker**。
3. 选择从 Git 仓库导入，授权 Cloudflare 访问你的 GitHub 仓库。
4. 选择 Simlettra 仓库和要部署的分支。
5. 保持 Cloudflare 自动填写的默认命令：

```text
构建命令：pnpm run build
部署命令：npx wrangler deploy
```

6. 根目录使用仓库根目录，生产分支选择你的正式分支。
7. 在“构建变量”中只添加存储模式：

| 名称 | R2 模式 | KV 模式 |
| --- | --- | --- |
| `SIMLETTRA_STORAGE_MODE` | `r2` | `kv` |

Cloudflare 会自动把实际 Worker 项目名称交给 Wrangler。`SIMLETTRA_WORKER_NAME` 只用于本地或自定义流水线，不需要在 Workers Builds 中填写。真正的 `INIT_KEY` 与 `CONFIG_KEY` 也不填在这里。

## 五、首次构建与数据库迁移

确认配置后开始部署。默认构建与部署命令会：

1. 读取实际 Worker 项目名称；
2. 按 `meta`、`raw`、`tasks` 名称查找或创建 D1、KV/R2 和 Queue；
3. 取得真实 D1 或 KV 编号并生成一次性部署配置；
4. 生成当前存储模式的 Cloudflare 类型，并检查 Vue 与 Worker TypeScript；
5. 检查目标 D1；
6. D1 完全空白时，从 `0001` 到当前版本自动应用全部正式迁移；
7. 安全构建网页和 Worker，把真实资源配置写入构建产物；
8. 由默认 `npx wrangler deploy` 部署已经检查过的产物。

资源创建与后续迁移、构建不是一个原子操作。后续步骤失败时已创建资源会保留，重新部署将按完整名称复用，不会自动删除或创建随机副本。

不要把构建命令留空。`pnpm run deploy:github` 只保留给本地或自定义流水线，不需要填入 Cloudflare Git 连接页面。

公开部署仓库不包含内部完整测试集。完整自动化、备份恢复、旧系统迁移、升级回退、性能、安全与双模式部署检查在开发仓库中执行，不由每次 Cloudflare 自动部署重复运行。

如果目标 D1 已有数据但迁移版本不是当前版本，部署会主动停止。不要删除检查或强行部署；已有系统必须先按[升级与回退手册](../运维/升级与回退手册.md)完成备份、迁移和数据检查。

## 六、设置两把管理员可见变量

首次代码部署成功后，打开刚创建的 Worker，进入 **设置 → 变量和机密**。添加两项**文本变量**，不要选择保存后不可回看的 Secret：

| 名称 | 用途 | 要求 |
| --- | --- | --- |
| `INIT_KEY` | 首次初始化和管理员忘记密码恢复 | 至少 16 个字符的随机值 |
| `CONFIG_KEY` | 加密 D1 中动态 Provider、通知、资源 Token 和邀请码副本 | 32 个随机字节的 Base64 编码 |

唯一系统管理员直接对这两项安全负责，可以在 Cloudflare 控制台查看、复制和修改。项目不会额外使用 DPAPI 或其他机制阻止管理员查看。

两把值必须不同。它们不能进入 GitHub、构建变量、截图、公开文档或普通日志。`CONFIG_KEY` 丢失后，D1 中已经加密的动态凭据将无法解密，需要重新填写相关配置。

保存变量后重新部署当前 Worker，使运行实例读取变量。仓库配置使用 `keep_vars: true`，以后 GitHub 自动部署会保留管理员在 Cloudflare 控制台填写的变量。

## 七、完成网页初始化

打开 Worker 地址。未初始化系统会显示三步向导。

1. 输入 `INIT_KEY` 完成部署鉴权。
2. 填写管理员显示名称、邮箱前缀、邮件域名、登录密码和时区。
3. 确认完整主邮箱、存储方式和时区后完成初始化。

邮箱前缀只使用小写英文字母、数字、点、下划线和连字符，首尾必须是字母或数字，不能包含连续两个点。邮件域名只填写 `example.com` 形式。Simlettra 信任系统管理员填写的域名，不执行 DNS TXT 所有权验证。

初始化完成后使用主邮箱地址和登录密码登录；`INIT_KEY` 不是日常登录密码。

## 八、配置 Email Routing

对每个需要收信的域名，在 Cloudflare Email Routing 中建立发往当前 Worker 的规则：

1. 确认该域名已启用 Email Routing；
2. 建立地址或全域规则；
3. 动作选择发送到 Worker；
4. 选择当前 Simlettra Worker；
5. 启用规则并用虚构内容的小型邮件测试。

## 九、完成首次自检

- [ ] Worker 地址能打开简体中文网页；
- [ ] 第二次打开不再出现初始化向导；
- [ ] 管理员能用主邮箱和密码登录；
- [ ] 设置页显示正确的 R2 或 KV 模式；
- [ ] 运行健康页显示收信、发信、存储和定时维护四类摘要；
- [ ] 小型纯文本测试邮件经过 Queue 后出现在收件箱；
- [ ] GitHub、构建日志和 Worker 日志中没有密钥、密码、正文或附件；
- [ ] 手机浏览器可以登录、读信和打开基础设置。

## 十、后续更新

GitHub 正式分支出现新提交时，Cloudflare 会自动执行同一部署命令。若新版本不含 D1 迁移，或目标 D1 已经与代码处于同一迁移版本，更新可以继续。若包含尚未应用的迁移，自动部署会停止，管理员先按版本说明和升级手册处理数据库，再重新部署。

本地 Wrangler CLI 继续用于开发、远程迁移、备份恢复、升级演练和高级排错。普通部署者不需要为了日常自动更新长期维护本地 CLI 环境。
