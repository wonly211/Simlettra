# 需求变更-0001：域外发信服务故障切换与密钥管理

## 状态

已接受；Provider 范围已由[需求变更-0004](0004-首发移除CloudflareEmailSending.md)取代，其余结论继续生效

> 后续取代：[需求变更-0011](0011-确定可信管理员密钥与GitHub部署规则.md)取代“配置主密钥只能作为不可回看的受保护 Secret”的解释和旧变量名；D1 动态凭据加密、管理员明文管理和故障切换结论继续有效。

- 提议与接受日期：2026-08-11
- 适用基线：[需求基线-0001](../需求基线.md)
- 影响需求：`2.06`、`10.06`，以及与其相关的发信、通知、转发、备份和验收边界

## 背景

原需求将所有服务密钥限定为 Cloudflare 受保护部署配置，并只要求不同域名能够选择不同的站外发信服务。用户在第五批数据模型确认前明确要求：

1. 系统管理员可以在网页中完整管理发信服务密钥；
2. 密钥可以加密后保存到 D1，不必为每一家服务单独维护部署变量；
3. 每个域名可以设置默认 Outbound Mail Provider 和多个备用 Provider；
4. 默认服务无法安全发信时，系统应自动切换到备用服务。

同时，用户明确要求其余已确认结论保持不变，特别是系统管理员不能通过产品界面读取或代删普通用户个人邮件的边界不变。

## 取代的旧结论

| 原编号 | 原结论 | 新结论 |
| --- | --- | --- |
| `2.06` | 密钥等敏感信息使用受保护部署配置 | 受保护部署配置只保存一把配置加密主密钥；系统管理员可在网页中管理服务密钥，Worker 加密后将密文保存到 D1。普通用户不能访问服务密钥。 |
| `10.06` | 不同域名可以配置不同站外发信服务 | 每个域名可以配置一条有优先顺序的发信路线，包含一个默认服务和零个或多个备用服务。对每名站外收件人，只有在能够证明当前服务尚未接受邮件且失败可能由服务切换解决时，才自动尝试下一家服务。 |

## 当前有效行为

1. 当前系统管理员可查看、复制、替换、删除和测试 Cloudflare Email Sending、Resend 与 SMTP2GO 的服务密钥和回调凭据。
2. D1 仅保存经认证加密后的密文、随机值、加密主密钥版本和必要配置元数据；明文密钥不进入数据库、日志、审计记录、Queue 消息或备份清单。
3. 加密主密钥以独立的 `CONFIG_KEY` 保存在 Cloudflare 受保护部署配置中，不能使用 `init_key` 兼任。它不随 D1 逻辑备份导出；恢复时必须提供与备份密文兼容的主密钥，或使用单独的密钥恢复步骤。
4. 域名发信路线及其服务顺序在发送被接受时冻结。随后调整路线只影响新发送；已接受邮件只在其冻结路线中切换，不能使用后来新增的服务。
5. 请求已发出但响应丢失、连接中断等“是否已被服务接受”无法判断的情形，保持“结果未知”，不得自动切换，避免重复投递。
6. 邮件大小按每名站外收件人的冻结路线判断：只要每名收件人存在至少一家可接受最终负载的服务，整次发送才可开始；实际优先选择路线中靠前且兼容的服务。

## 影响与后续工作

1. 本变更本身不增加或删除需求数量，生效时仍为 159 项有效需求；后续总数以[需求基线](../需求基线.md)中的当前统计为准。
2. 第五批数据模型将建立加密配置、域名发信路线、冻结路线快照和逐收件人服务切换记录。
3. 架构决策记录将新建替代性决定，明确取代 ADR `0010` 与 `0021` 中关于单一供应商快照和密钥仅存部署引用的部分结论；旧记录保留历史事实和双向链接。
4. 发布前必须新增多供应商大小边界、明确未接受后的切换、结果未知不切换、密钥加密与备份恢复的自动化验证。

## 不改变的结论

1. 只有当前系统管理员可以管理服务设置；普通用户不能访问服务密钥。
2. 系统管理员不能通过产品界面读取普通用户个人邮件正文，也不能代替用户永久删除单封个人邮件。
3. 密码仍只保存慢速哈希；会话令牌、邮件正文、附件、完整回调和密钥仍不进入普通日志或 Queue 消息。
4. 本变更生效时 Cloudflare Email Sending、Resend 和 SMTP2GO 是首发支持的三种站外发信服务；该 Provider 范围已经由需求变更-0004 取代，当前首发只支持 Resend 和 SMTP2GO。
