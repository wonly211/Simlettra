# 需求变更-0002：资源用量与域名月度发件配额

## 状态

已接受；资源容量解释已由[需求变更-0003](0003-以Cloudflare免费额度作为产品资源上限.md)取代，其余结论继续生效

- 提议与接受日期：2026-08-11
- 适用基线：[需求基线-0001](../需求基线.md)
- 新增需求：`2.10`、`7.16`
- 技术核验：[Cloudflare 资源用量接口核验](../../验证/Cloudflare资源用量接口核验.md)

## 背景

用户在确认第六批数据模型时明确要求：系统管理员能够查看资源使用情况，例如 D1、KV 或 R2 的已用容量与总容量，以及每个域名当月已发件数量与每月配额。

现有需求 `2.08` 只要求管理员判断收信、发信、存储和定时任务是否健康，`11.13` 只要求查看并设置用户和组织的存储配额；两者都没有完整覆盖 Cloudflare 平台资源用量和域名月度发件配额，因此需要增加两项独立需求。

## 新增需求

| 编号 | 当前有效行为 | 范围 | 状态 |
| --- | --- | --- | --- |
| `2.10` | 管理员可以查看 D1 与当前使用的 KV 或 R2 的资源使用情况，包括已用容量、平台实际提供的硬上限或套餐包含量、数据来源和最后更新时间；无法取得精确平台指标时必须明确标注估算或暂不可用 | 首发应有 | 已确认 |
| `7.16` | 管理员可以查看每个域名当月已发件数量和每月配额，并为域名设置月度发件配额；具体计数单位、月份边界和失败回退规则在数据模型中确认 | 首发应有 | 已确认 |

## 显示边界

以下内容记录本变更生效时的原始结论，已由需求变更-0003 取代，不再作为当前实现依据。

1. “已用容量”是当前测得或估算的使用量。
2. “硬上限”是平台明确不允许超过的容量限制。
3. “套餐包含量”是免费或已付套餐包含的用量，超过后可能计费，但不一定停止服务。
4. “无固定总容量”表示平台没有给该资源设置固定总容量，不能把免费包含量当作总容量。
5. 平台精确指标、Simlettra 自有账本估算值和暂不可用状态必须清楚区分，并显示最后更新时间。

## 影响与后续工作

1. 本变更新增两项“首发应有”需求，有效需求总数由 159 项增加到 161 项，“首发应有”由 24 项增加到 26 项。
2. 第六批数据模型补充 `数据-129` 至 `数据-132`，用于确认资源快照、容量类型、域名月度配额和计数账本。
3. 具体计数单位、自然月边界、预留与释放规则仍需用户批量确认，不能从本变更的高层行为直接推定。
4. 架构和实现阶段需要验证 Cloudflare 指标接口的权限、刷新延迟、失败降级和免费额度消耗。
5. 首发验收必须同时覆盖 Cloudflare 平台资源总览、用户和组织存储配额、用户每日发件配额以及域名月度发件配额。

## 不改变的结论

1. 系统仍只有一名系统管理员，资源和配额管理只属于该管理员。
2. 管理员资源总览不提供普通用户个人邮件正文或附件内容。
3. 用户和组织存储配额仍按数据-108 至数据-112 的已确认规则计算。
4. 用户每日发件配额仍按数据-113 的已确认滚动 24 小时规则计算；域名月度配额是另一条独立限制。
5. D1、KV 和 R2 的实际限制及计费规则以 Cloudflare 当前官方资料为准，不在需求文档中伪造固定总容量。
