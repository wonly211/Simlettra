# 需求变更-0003：以 Cloudflare 免费额度作为产品资源上限

## 状态

已接受，当前生效

- 提议与接受日期：2026-08-11
- 适用基线：[需求基线-0001](../需求基线.md)
- 影响需求：`2.09`、`2.10`
- 取代结论：[需求变更-0002](0002-资源用量与域名月度发件配额.md)中的资源容量显示边界
- 技术核验：[Cloudflare 资源用量接口核验](../../验证/Cloudflare资源用量接口核验.md)

## 背景

用户澄清，Simlettra 的设计初衷是利用 Cloudflare 免费资源搭建小型邮件系统。因此，对 D1、KV 和 R2 而言，“上限”不是平台允许使用的最大付费容量，而是 Cloudflare 当前免费额度的上限。

此前需求变更-0002 将平台硬上限、免费包含量和付费扩展能力分开显示。这种表达符合 Cloudflare 的平台事实，却不符合 Simlettra 的产品目标，因为它会让管理员误以为免费额度用完后仍可以自然进入付费容量。

## 当前有效行为

1. D1、KV 和 R2 的 Cloudflare 免费额度就是 Simlettra 的产品资源总容量。
2. 管理员界面统一显示“已用免费额度、免费额度上限、剩余额度、统计范围、数据来源和最后更新时间”。
3. 即使 Cloudflare 技术上允许超出免费额度并按量计费，Simlettra 也不把该付费容量显示为可用空间。
4. 接收邮件、保存草稿或附件、建立已发送副本以及其他会增加存储的操作，在执行前必须检查预计增量；预计越过免费额度时停止操作并明确说明原因。
5. 达到资源上限不会删除现有数据，也不阻止登录、阅读、导出、备份或永久删除；释放空间后恢复可增加存储的操作。
6. 免费额度可能属于整个 Cloudflare 账号而不是单个 Worker、数据库、命名空间或存储桶。管理员界面必须说明统计范围，并在能够取得账号级指标时计入同一账号中其他项目的资源占用。
7. 无法取得精确账号级指标时，系统必须明确标注估算，并采用保守策略；不得因为看不到其他项目的占用就宣称一定不会产生费用。
8. 免费额度数值属于可能变化的平台事实，每次发布前复核，不把过期数字永久写成不可修改的产品常量。

## 对当前免费额度的解释

1. D1 采用 Free 计划的单数据库和账号总存储限制，实际可用上限取两者及账号剩余额度中的较小值。
2. KV 采用 Free 计划的账号和命名空间存储限制，实际可用上限取两者及账号剩余额度中的较小值。
3. R2 将标准存储的账号级月度免费存储额度作为 Simlettra 的产品容量上限；即使 R2 存储桶本身没有固定硬上限，也不允许 Simlettra 自动进入付费存储。
4. 管理员可以为用户、组织或系统设置更低的配额和预警值，但不能通过普通产品设置把上限提高到 Cloudflare 免费额度之外。

## 影响与后续工作

1. 本变更不增加或删除需求，当前仍为 161 项有效需求。
2. 第六批数据模型的 `数据-129` 和 `数据-130` 需要使用免费额度总量、账号已用量、Simlettra 已用量、剩余额度和统计时间，不再设计“无固定总容量”产品状态。
3. 资源总览需要优先使用 Cloudflare 账号级只读指标；Simlettra 自有账本作为对账和降级依据。
4. D1、KV 和 R2 的配额拦截必须与已有容量预留、失败释放、垃圾箱和永久清理规则衔接。
5. 免费资源影响已经单独收口：ADR `0029` 规定 Workers Free 是首发核心运行基线，ADR `0030` 取代完整 20 MB 直接以 Workers Paid 为生产基线的结论；Cloudflare Email Sending 已由需求变更-0004 明确移出首发。

## 不改变的结论

1. 仍只提供 `D1 + KV` 和 `D1 + R2` 两种存储方式。
2. 用户和组织存储配额、用户每日发件配额及域名月度发件配额继续分别存在。
3. 管理员可以查看资源使用情况，普通用户不能管理 Cloudflare 指标凭据。
4. 达到免费额度时不得静默丢弃已经成功送达系统的邮件；收信入口必须在接受前完成可用容量判断或提供可恢复处理。
