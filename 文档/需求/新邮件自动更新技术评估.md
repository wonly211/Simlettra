# 新邮件自动更新技术评估

## 文档状态

- 对应需求：`6.13`
- 状态：已接受
- 评估日期：2026-08-09
- 接受日期：2026-08-09
- 实现日期：2026-08-13
- 适用约束：单 Cloudflare Worker，仅使用 `D1 + KV` 或 `D1 + R2`，按免费额度规模设计

## 要解决的问题

用户打开 Simlettra 页面时，希望新邮件能够自动出现，不需要频繁手动刷新。同时，该功能不能明显挤占 Cloudflare 免费额度，影响正常收信、读信和发信。

## 当前平台额度

以下数字来自评估日期当天的 Cloudflare 官方文档，未来可能变化，开发和发布前必须再次核对：

- Workers 免费方案每天共有 100,000 次请求额度。
- D1 免费方案每天包含 5,000,000 行读取和 100,000 行写入。
- KV 免费方案每天包含 100,000 次读取，但 `D1 + R2` 部署方式没有 KV 可供统一使用。
- Durable Objects 可用于协调 WebSocket 连接，但会增加新的平台组件、请求额度和部署复杂度。

- [Cloudflare Workers 限制](https://developers.cloudflare.com/workers/platform/limits/)

- [Cloudflare Workers KV 价格与免费额度](https://developers.cloudflare.com/workers/platform/pricing/)
- [Cloudflare Durable Objects 概览](https://developers.cloudflare.com/durable-objects/)

## 方案比较

| 方案                         | 用户感受                 | 免费额度影响              | 与已确认约束的关系               | 结论           |
| ---------------------------- | ------------------------ | ------------------------- | -------------------------------- | -------------- |
| 仅手动刷新                   | 不会自动出现新邮件       | 最低                      | 完全符合                         | 可用但体验较弱 |
| 节制轮询                     | 通常在一分钟内看到新邮件 | 可控制                    | 不增加部署组件                   | 推荐           |
| 高频轮询                     | 数秒至数十秒看到新邮件   | 容易占满 Workers 请求额度 | 不增加组件，但不符合免费额度目标 | 不推荐         |
| WebSocket 与 Durable Objects | 接近实时                 | 需要额外额度和组件        | 实际形成第三种部署依赖           | 不采用         |

## 请求量估算

下表只计算自动检查请求，不包含登录、读信、发信和管理操作：

| 使用情况                   | 检查间隔 | 每日自动请求量                            |
| -------------------------- | -------- | ----------------------------------------- |
| 1 个页面全天打开           | 60 秒    | 1,440 次                                  |
| 10 个页面每天各打开 8 小时 | 60 秒    | 4,800 次                                  |
| 30 个页面每天各打开 8 小时 | 60 秒    | 14,400 次                                 |
| 30 个页面全天打开          | 60 秒    | 43,200 次                                 |
| 30 个页面全天打开          | 30 秒    | 86,400 次                                 |
| 30 个页面全天打开          | 15 秒    | 172,800 次，超过 Workers 每日免费请求额度 |

由此可见，请求次数比 D1 行读取更容易先达到免费额度。自动检查必须低频，并在页面不可见时暂停。

## 推荐方案

建议首发保留新邮件自动更新，并采用节制轮询：

1. 页面可见且用户仍在使用时，每 60 秒检查一次。
2. 用户重新切回页面、网络恢复或完成登录时立即检查一次。
3. 页面进入后台后停止定时检查，重新可见时再恢复。
4. 连续失败时逐步延长间隔，避免故障期间反复请求。
5. 始终保留手动刷新。
6. 自动检查只查询“上次检查后是否有变化”所需的最少数据，不重复加载完整邮件列表。
7. 管理员可以关闭自动更新；首发不提供低于 60 秒的检查间隔。

该方案不引入 Durable Objects，不改变已经确认的两种部署方式，并能在典型个人、家庭和小团队使用中为正常操作保留较多免费请求额度。

## 已接受决定

用户已接受推荐方案，将节制轮询纳入首发：

1. 页面可见且用户仍在使用时，每 60 秒检查一次。
2. 用户重新切回页面、网络恢复或完成登录时立即检查一次。
3. 页面进入后台后停止定时检查，重新可见时再恢复。
4. 连续失败时逐步延长间隔。
5. 始终保留手动刷新。
6. 不提供低于 60 秒的检查间隔。
7. 不引入 Durable Objects，不改变已经确认的两种部署方式。

“首发只保留手动刷新”的备选方案未被采用。

## 实现状态

第二十八批纵向切片已经完成本地代码、自动化和质量门槛：

1. 页面可见且在线时每 60 秒检查；登录、切回页面和恢复在线后立即检查。
2. 页面后台、浏览器离线、用户登出或组件卸载时取消定时检查。
3. 连续失败依次退避到 2 分钟、5 分钟和 10 分钟，成功后恢复 60 秒。
4. 自动刷新使用静默模式，不清空当前勾选、提示或正在阅读的邮件；手动刷新保持不变。
5. 不新增 D1 迁移、Durable Objects、WebSocket 或其他 Cloudflare 组件。

当前实现静默重新请求当前筛选条件下的完整首屏列表，没有实现早期建议中的独立轻量变化探测端点。复用现有列表契约减少了新的授权、搜索和会话一致性风险，但 D1 读取成本高于最小化建议，需在真实 Workers Free 环境验证后再决定是否优化。

“管理员可以关闭自动更新”没有进入最终需求 `6.13`，因此不是已接受产品行为，也没有实现。早期推荐方案中的该文字仅作为历史建议保留，不得用来判断当前产品能力。

自动刷新调度器 4 项测试及全量 53 个测试文件、217 项测试已经通过；桌面与手机浏览器的页面可见性、离线恢复和不干扰当前操作仍待验收。详细记录见[第二十八批网页新邮件自动更新](../开发/第二十八批网页新邮件自动更新.md)。
