## 旧系统整体形态

旧系统是一个部署在 Cloudflare Workers 上的自有域名邮箱网页应用：

- 网页端使用 Vue 3、Vite、Pinia 和 Element Plus。
- 服务端使用 Cloudflare Worker、Hono 和 Drizzle ORM。
- D1 保存用户、邮箱地址、邮件元数据、权限和设置。
- KV 或 R2 保存邮件正文、附件和内嵌图片。
- Cloudflare Email Routing 将收到的邮件交给 Worker。
- 外发邮件可使用 Cloudflare Email Service 或按域名配置的 Resend。
- 定时任务用于恢复未完成的收信记录和重置每日发件计数。

这些是旧系统的技术事实，不构成新系统的技术约束。

## 初始化与部署

旧系统提供以下能力：

- 检查 D1 与 KV 或 R2 是否绑定。
- 在首次使用时建立数据表、默认设置、默认角色和权限。
- 检测旧版邮件存储结构。
- 对检测到的旧版存储执行需要明确确认的格式化。
- 使用 KV 或 R2 两种对象存储模式部署。
- 通过单个 Worker 同时提供网页、接口、附件访问、收信和定时任务。

## 用户与登录

旧系统提供以下能力：

- 用户注册、登录和退出。
- 注册可由全局设置控制，并可要求注册码。
- 首次初始化时建立管理员身份。
- 用户可以修改自己的密码和删除自己的账户。
- 管理员可以添加、禁用、启用、改密、调整身份和永久删除用户。
- 系统记录注册与近期活动的 IP、浏览器、系统和设备信息。
- 登录后使用最长三十天的令牌会话。

## 角色与权限

旧系统包含可配置角色和细粒度权限：

- 角色可限制邮箱地址数量。
- 角色可限制允许使用的域名。
- 角色可禁止发信、只允许站内发信，或限制每日及累计发件数量。
- 角色可按发件人或域名限制收信。
- 管理员可以建立、修改、删除角色并设置默认角色。
- 权限覆盖邮箱地址、邮件删除、邮件发送、用户管理、全站邮件、系统设置和注册码管理。

## 域名与邮箱地址

旧系统提供以下能力：

- 一个实例配置一个或多个收信域名。
- 每个用户拥有一个与登录账号相同的主邮箱地址。
- 在系统设置允许时，用户可以添加多个别名邮箱地址。
- 邮箱地址在整个实例中不区分大小写且保持唯一。
- 用户可以修改地址显示名称，但不能修改地址本身。
- 用户可以软删除自己的别名，不能删除主邮箱地址。
- 用户可置顶别名，并按自定义顺序、最近来信、字母或未读数排序。
- 用户可指定一个邮箱入口显示其全部个人来信。
- 管理员可以限制地址前缀最短长度和禁止包含的文字。
- 删除仍有关联邮箱地址的域名时会显示风险确认。

## 全域收信

旧系统实现了面向未创建地址的全域收信：

- 管理员可以按域名开启或关闭全域收信。
- 管理员可以把某个域名的未分配来信交给一个或多个用户查看。
- 被分配用户各自拥有独立的已读和删除状态。
- 用户可以把某封未分配来信的收件地址认领为自己的别名。
- 认领后，同一地址的历史未分配邮件和附件会一起转入该用户。

这属于“多人查看未分配来信”，旧系统没有通用的组织、团队或共享邮箱模型。

## 收信

旧系统提供以下能力：

- 接收配置域名下已有邮箱地址的邮件。
- 解析纯文本、HTML、收件人、抄送、密送、主题、邮件标识、回复关系和附件。
- 保存普通附件和正文中的内嵌图片。
- 按主题、正文、发件邮箱或发件域名拒收邮件。
- 全局暂停收信。
- 对无对应地址且未开启全域收信的邮件直接拒收。
- 可将符合规则的来信转发到 Telegram 或一个或多个外部邮箱。
- 收信过程中先写入“保存中”状态，定时任务会恢复异常中断的记录。

## 阅读与整理

旧系统提供以下能力：

- 按邮箱地址查看收件箱。
- 查看全部个人来信。
- 查看邮件正文和附件。
- 标记已读。
- 添加或取消星标，并查看星标邮件。
- 按新旧时间方向连续加载邮件。
- 软删除个人邮件。
- 管理员可搜索全站邮件，并执行单封永久删除或按条件批量删除。
- 网页端通过轮询获取新邮件。

未发现完整的归档、标签、垃圾箱恢复或面向普通用户的全文搜索闭环。

## 写信与发信

旧系统提供以下能力：

- 从用户拥有的邮箱地址选择发件地址。
- 编辑纯文本和 HTML 正文。
- 向一个或多个收件人发送邮件。
- 添加普通附件和内嵌图片，普通附件与内嵌图片各限制十个。
- 回复邮件并写入邮件回复关系标识。
- 站内收件人直接在本系统内收到邮件。
- 站外收件人通过 Cloudflare Email Service 或 Resend 投递。
- 保存已发送邮件并记录成功、延迟、退信、投诉和失败等状态。
- 使用 Resend 回调更新投递状态。
- 按角色限制发件范围和数量。

旧系统的数据结构能够保存抄送和密送信息，但当前发信接口主要接收一个收件人数组，是否存在完整的抄送、密送发信界面需要在后续深入盘点时验证。

## 草稿与最近联系人

旧网页端使用浏览器本地数据库保存草稿和附件，使用浏览器本地状态保存最近联系人：

- 草稿不会自动跨浏览器或跨设备同步。
- 清理浏览器数据可能导致草稿丢失。
- 这些本地数据难以通过服务端迁移工具完整迁移。

## 系统设置与外部连接

旧系统的系统设置包括：

- 注册、收信、发信、添加邮箱和多邮箱模式开关。
- 网站标题、自动刷新和登录页域名显示。
- 收信域名和 Worker 自定义域名。
- Resend 令牌按域名配置。
- Telegram 机器人通知。
- 外部邮箱转发。
- 按地址规则转发。
- 无收件人邮件处理。
- 地址前缀限制和邮件黑名单。

## 删除与数据形态

旧系统同时存在软删除和永久删除：

- 普通用户删除邮箱地址或邮件时主要写入删除标记。
- 管理员删除用户、用户邮箱地址或全站邮件时可永久删除关联数据。
- 邮件正文和附件与 D1 元数据分开保存，需要跨存储清理。
- 未发现面向用户的备份、导出、恢复和完整迁移流程。

## 已有测试证据

旧 Worker 目录存在七个 Vitest 测试文件，覆盖：

- 基础接口与收信入口
- 部署脚本
- 品牌名称
- 页面导航和重定向
- 邮件正文访问权限
- 邮件正文对象存储
- 工具链约束

这些测试可以帮助识别旧行为，但不能证明旧系统全部功能正确，也不能直接作为新系统验收标准。

## 对新需求定义的提醒

盘点显示，新项目至少需要明确回答以下问题：

1. 产品究竟是个人邮箱工具、多人共享邮箱，还是两者兼顾。
2. 是否继续限定为 Cloudflare 部署，还是把平台选择留给架构阶段。
3. 主邮箱、别名、全域收信和共享邮箱之间是什么关系。
4. 系统管理员是否可以读取普通用户邮件。
5. 草稿、最近联系人和用户设置是否需要跨设备同步。
6. 删除是进入垃圾箱、延迟清除，还是立即永久删除。
7. 是否迁移旧用户、邮件正文、附件、设置和密码。
8. 外部发信、转发、Telegram 等连接是否属于首发范围。
9. 搜索、会话归并、归档和垃圾邮件处理做到什么程度。
10. 如何定义可接受的容量、可靠性、备份和恢复目标。
