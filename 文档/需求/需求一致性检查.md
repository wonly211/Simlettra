# 澄笺 | Simlettra 需求一致性检查

## 文档状态

- 阶段：需求定义收口
- 状态：检查完成，已纳入需求变更-0001 至需求变更-0012
- 检查日期：2026-08-11
- 检查范围：十二个已确认需求模块
- 正式需求基线：`需求基线-0001` 已接受并生效

## 检查目的

本文档检查不同需求模块放在一起后是否互相矛盾、是否缺少关键结果，以及质量要求能否被实际验收。这里不会用技术实现替用户决定产品行为。

检查结果是：现有需求没有必须推翻重做的直接冲突。八项原始跨模块边界、域外发信路线变更以及管理员资源用量与域名月度配额变更均已确认，并已纳入正式生效的 `需求基线-0001`。

## 已确认不存在冲突的事项

以下事项已经能够由现有需求共同解释，不需要重新确认：

1. 收信与发信的默认邮件总大小均为 20 MB；Cloudflare 或发信服务限制更小时，采用更小的限制。
2. 个人邮件可以由本人永久删除；组织邮件适用更具体的组织规则，普通成员只能改变自己的整理状态，只有组织创建者能删除组织原始邮件。
3. 首发不提供浏览器通知，与通过 ntfy、Gotify、WxPusher、Telegram 或 Bark 发送外部通知并不冲突，两者是不同渠道。
4. 系统管理员不能通过产品界面读取普通用户邮件正文，但完整备份必然包含邮件数据。备份属于基础设施管理能力，必须加密保存，且不得在日志中泄露正文。
5. 删除组织时立即停用组织地址，并保留七天供创建者恢复；这已经补全组织删除的数据保留规则。
6. 本地完整备份始终覆盖 D1 和当前实际采用的 KV 或 R2，与两种部署方式保持一致。
7. 每个域名配置默认与备用发信服务，并不放宽“不得重复投递”的边界：只有能证明前一家未接受的失败才切换；结果未知继续等待事件或人工处理。
8. 用户和组织存储配额是产品内部容量规则；D1、KV/R2 免费额度是整套 Simlettra 的平台资源上限；域名月度发件配额又是发信治理规则。三类数字用途不同，分别展示不会造成冲突。
9. Cloudflare 平台可能允许某些资源超过免费额度后继续付费使用，但 Simlettra 不采用该付费容量。产品界面把免费额度显示为总容量，达到上限后停止增加存储，不把平台的付费扩展能力暴露成可用空间。
10. Cloudflare Email Routing 和域外发信 Provider 已经承担各自的外部配置与许可检查；Simlettra 信任唯一系统管理员添加的域名，只检查格式、系统内唯一性和运行配置，不重复建立域名所有权验证流程。
10. 移除 Cloudflare Email Sending 不影响 Cloudflare Email Routing 收信，也不改变域名默认与备用路线、逐收件人状态、明确未接受后切换和结果未知不重发等通用发信规则；首发 Provider 集合只剩 Resend 与 SMTP2GO。

## 已确认的基线收口项

| 编号 | 需要补齐的边界 | 推荐结论 | 状态 |
| --- | --- | --- | --- |
| 基线-01 | 禁用用户或暂停域名、地址、用户收信后，新邮件如何处理 | 新邮件立即拒收，不保存也不建立隐藏队列；条件恢复后只接收此后到达的邮件，并尽可能让外部发件方获得拒收结果 | 已确认 |
| 基线-02 | 用户注销的七天冷静期内能做什么 | 申请注销后立即退出全部正常会话，地址停止收发；七天内只允许用户通过密码进入注销恢复页面并取消注销；取消后恢复正常使用，期满后永久删除个人数据 | 已确认 |
| 基线-03 | 唯一系统管理员能否注销、被禁用或转让身份 | 系统必须始终保留一名管理员；当前管理员必须先把管理员身份转让给另一名已启用用户，才能注销自己，且不能禁用当前唯一管理员 | 已确认 |
| 基线-04 | 组织创建者注销账号前如何处理组织 | 创建者必须先把仍有成员的组织交给现有成员；只有创建者一人的组织必须先删除或取消注销；普通组织成员进入待注销状态后立即失去组织访问权，最终删除时移出组织，历史操作保留必要署名 | 已确认 |
| 基线-05 | 认领全域收信中的未分配地址会产生什么结果 | 被认领地址成为认领者的个人别名，占用个人别名配额并遵守命名规则；只有获准自行创建别名的用户可以认领；多人同时认领时以第一个成功者为准 | 已确认 |
| 基线-06 | 一封邮件同时包含系统内和站外收件人时如何发送 | 一次发送操作自动拆分投递：系统内收件人直接投递，站外收件人通过对应域名的发信网关投递；用户仍看到一封已发送邮件，并能查看各收件人的投递结果 | 已确认 |
| 基线-07 | “通常在 2 秒内可操作”按什么规模验收 | 该数字是性能验收基准，不是使用上限；首发以 50 名已启用用户、10 人同时操作和系统内累计 100,000 封测试邮件作为基准场景，实际可保存数据量仍受邮件大小和 Cloudflare 配额影响 | 已确认 |
| 基线-08 | “重试不会产生重复邮件”的责任边界 | Simlettra 发起和控制的重试不得对同一收件人重复投递；外部发信服务或收件方在成功接收后自行产生的重复邮件不属于 Simlettra 能够保证的范围 | 已确认 |
| 基线-09 | 默认发信服务不可用时如何切换备用服务 | 每个域名冻结默认与备用服务路线；仅在能明确证明当前服务未接受邮件且备用服务兼容负载和收件条件时切换。结果未知不得自动切换 | 已确认 |

## 留到架构阶段验证的事项

以下内容不改变产品行为，不需要现在由用户选择，但架构方案必须逐项验证并记录证据：

1. 两种存储方式是否都能满足 20 MB 邮件、完整性写入、搜索、永久删除和本地备份要求。
2. 每种域外发信服务实际能够提供哪些投递状态和回调能力。
3. 单 Worker 部署下，收信、网页请求、定时任务和外部回调之间如何隔离故障。
4. Cloudflare 免费额度下，自动检查新邮件、正文搜索、备份和迁移的可承受成本。
5. 浏览器支持范围如何转换成可重复执行的兼容性测试。
6. Cloudflare 官方接口能够提供哪些 D1、KV 和 R2 账号级精确用量指标，指标刷新延迟、授权范围、共享账号中的其他资源占用和接口失败时的保守阻断口径。

## 检查结论

八项原始基线收口内容及基线-09 已确认，最终一致性检查通过。需求变更-0001 至需求变更-0012 均已生效；高层产品需求不存在遗留的待确认事项。资源指标与域名月度配额的数据口径已由第六批数据模型的数据-129 至数据-132 确认；Workers Free 已由 ADR `0029` 确认为首发核心运行基线，20 MB 邮件解析则以 ADR `0030` 规定的真实 Free 环境验证作为上线门槛；新用户个人别名默认额度由需求变更 `0007` 确认为 20，新用户组织创建默认额度由需求变更 `0008` 确认为 5；用户与组织逻辑存储默认额度由需求变更 `0009` 确认为 KV 模式 100,000,000 字节、R2 模式 1,000,000,000 字节；账号邀请码注册的次数、有效期、域名、显示、失效、限速和组织边界由需求变更 `0010` 确认；可信管理员密钥边界与 Cloudflare 连接 GitHub 默认部署方式由需求变更 `0011` 确认；D1 与 KV/R2 的自动创建和命名规则由需求变更 `0012` 确认。本次变更不增减有效需求数量。
