## 一句话结论

推荐使用 Drizzle 作为普通 D1 表的 TypeScript 查询与结构描述工具，最终 SQL 迁移只由 Wrangler 账本应用；FTS5、PRAGMA、批处理和平台指标保留原生 D1 能力。Prisma 虽能运行，但 D1 适配器仍为 Preview，代表性 Worker 的 gzip 包体约为 Drizzle 的 32 倍。D1 物理导出不能处理 FTS5，因此完整备份应导出权威普通表，恢复后重建派生搜索索引。

## 候选比较

### 原生 D1

原生 API 完整保留参数化 SQL、结果元数据、原子 `batch()`、Sessions、FTS5 和 PRAGMA，依赖最少。但如果所有普通查询都手写 SQL，字段名、返回类型、组合筛选和结构变更会产生大量人工同步工作。旧系统的运行时自动建表也说明，缺少明确迁移边界很容易把结构管理混入正常请求。

结论：保留为平台能力和特殊查询通道，不作为所有普通查询的唯一方式。

### Drizzle

1. TypeScript 表结构成功生成可读 SQL，中文迁移名称、外键、检查约束和索引都得到保留。
2. 新增字段只生成一条清晰的 `ALTER TABLE`，已有行获得预期默认值。
3. 与手写 FTS5 迁移、Wrangler 迁移账本和原生 D1 查询能够共存。
4. 代表性 Worker 干运行上传 198.75 KiB，gzip 后 38.52 KiB，不需要 `nodejs_compat`。
5. 组合查询与原生 D1 返回一致，Drizzle `batch()` 在失败时保持 D1 原子回滚语义。

结论：推荐作为普通表的结构描述和查询层，但不接管生产迁移应用，也不隐藏 D1 特有能力。

### Prisma

1. Prisma 7.9.1 与 D1 adapter 可以成功生成客户端、类型检查、打包并执行权限范围查询。
2. `@prisma/adapter-d1` 自身 README 仍明确标记为 Preview。
3. 代表性 Worker 上传 3,934.35 KiB，gzip 后 1,242.30 KiB，约为 Drizzle gzip 包体的 32.25 倍。
4. 需要 `nodejs_compat` 和生成客户端；FTS5、迁移 PRAGMA、D1 结果元数据及平台 Sessions 仍需绕开 Prisma 抽象。

结论：功能可以工作，但首发的运行时、生成代码和兼容边界明显更多，不符合单 Worker 与易维护优先原则。

### Kysely

Kysely 核心维护活跃且查询风格接近 SQL，但没有内置 Cloudflare D1 dialect。采用它需要自建适配或依赖第三方 `kysely-d1`，会把核心数据访问建立在额外维护边界上。

结论：不进入首发候选。

## 已接受的迁移工作流

1. Drizzle TypeScript 表结构描述当前普通表，并由 Drizzle Kit生成迁移草案。
2. 迁移草案必须人工审查，检查数据损失、默认值、外键、索引、D1 限制和预计耗时；审查后作为只增不改的 SQL 文件进入 `migrations/`。
3. FTS5、PRAGMA、数据回填、表重建和其他 SQLite 特有操作使用手写 SQL 迁移，继续放在同一编号序列中。
4. 本地使用 `wrangler d1 migrations apply`；远程生产依据 [ADR 0048](../架构决策记录/0048-远程迁移使用D1文件导入并沿用Wrangler账本.md) 使用 D1 文件导入通道，并继续沿用唯一 `d1_migrations` 账本。不使用 `drizzle-kit push`、Prisma Migrate 或运行时自动建表。
5. 每次升级先在数据副本演练，记录数量、外键、索引、对象引用和业务状态检查结果。
6. 生产迁移前建立本地完整备份并记录 D1 Time Travel 书签；迁移后立即执行自动检查。
7. 单个迁移失败时依靠 D1 原子回滚并停止发布。迁移已成功但新版应用失败时，优先发布兼容旧结构的应用或修复性前向迁移；需要恢复数据时使用 Time Travel 或本地备份。
8. 已应用迁移不可改写、删除、重排或复用编号；修复必须新增迁移。

## 已接受的数据访问边界

1. Drizzle、原生 D1 和 SQL 只能出现在各业务模块的内部存储适配器中。
2. 业务规则只能调用模块公开的存储接口，不接收 Drizzle 表对象、查询构造器、D1 行或 SQL 字符串。
3. 普通增删改查优先使用 Drizzle，便于类型检查和组合条件维护。
4. FTS5、PRAGMA、D1 Sessions、结果 `meta`、大批量分块和工具未覆盖的语句使用原生 D1。
5. 所有动态值必须绑定参数；表名、列名和排序字段只从代码中的固定白名单选择。
6. 列表默认使用稳定键集分页，不使用深 `OFFSET` 作为主要翻页方式。
7. 大批量 `IN`、插入或更新每批最多使用 90 个业务参数，为其他条件和未来字段保留 D1 的 100 参数边界余量。

## FTS5 对备份的影响

D1 的物理 SQL 导出当前会拒绝包含虚拟表的数据库。官方临时方案是先删除虚拟表、导出后再重建，但这会让搜索暂时不可用，并增加生产备份步骤的破坏性。

Simlettra 已经确定 FTS5 是可重建派生数据，因此采用以下定义：

1. “完整 D1 备份”指完整保存所有权威普通表、迁移版本、数量、引用和校验信息，不要求保存 FTS5 物理页和影子表。
2. 生产备份使用带版本清单的逻辑格式，按表流式写出 NDJSON 或等价记录文件，不能一次把全部数据装入 Worker 内存。
3. 备份中明确列出被排除的派生表、对象存储清单、模式版本、表数量和校验值。
4. 恢复时先建立与备份兼容的结构，按外键顺序导入权威数据，完成数量和引用检查后从正文对象重建 FTS5。
5. Time Travel 用于保留窗口内的快速同库恢复，本地逻辑备份用于跨时间、跨数据库和灾难恢复，两者不能互相替代。

## 仍需远程复核

2026-08-13 已在两个短命或生产远程 D1 中完成以下验证：空库顺序应用全部 25 个正式迁移、重复执行跳过已应用版本、`PRAGMA foreign_key_check` 零行，以及故意失败的文件导入不留下探针表或迁移账本记录。生产 D1 已从 `0001` 完整迁移到 `0025`。

1. 记录并实际执行一次 Time Travel 书签恢复，确认当前账号保留窗口。
2. 在 100,000 封邮件规模下验证逻辑备份的分页、流式文件、恢复时间和校验成本。
3. 验证 Sessions API 在多地区读副本中的一致性和书签传播。
4. 验证 D1 远程导出对 FTS5 的限制是否与本地一致；即使将来平台解除限制，权威数据与派生索引的备份边界仍保持不变。
