# 澄笺 | Simlettra D1 数据库工具与迁移验证计划

## 文档状态

- 状态：当前
- 建立日期：2026-08-10
- 最近更新：2026-08-10
- 验证编号：验证-06
- 依据：`需求基线-0001`、已接受的架构决策记录 `0001` 至 `0011`
- 目的：确定 D1 表结构、查询代码和版本迁移分别由什么工具管理，并验证升级失败、重复执行、全文搜索与本地恢复流程

## 已确认约束

1. D1 是用户、权限、地址、组织、邮件元数据、状态、任务、审计和可重建搜索索引的权威来源。
2. 数据库只能通过版本化迁移改变，不得在普通请求中自动建表或隐式升级。
3. 复杂查询必须在服务端执行邮箱所有权或组织成员资格限制，不能先取回全部数据再由前端过滤。
4. 邮件接收、发送、删除和恢复需要明确事务、幂等、补偿或重放策略。
5. 搜索使用内容空 FTS5 表和应用生成词元，不能要求数据库工具完全抽象 SQLite 特有能力。
6. 升级需要版本说明、升级步骤、数据检查和回退说明；发布前必须演练备份恢复和版本回退。
7. 旧系统运行时自动执行 `CREATE TABLE IF NOT EXISTS` 的模式只作为反例，不进入新系统。

## 官方能力基线

核验日期均为 2026-08-10。

1. D1 Worker API 提供参数化预处理语句、`batch()` 和 Sessions API。
2. D1 `batch()` 中的语句按顺序执行，并作为一个事务提交；任一语句失败时整批回滚。
3. Wrangler D1 migrations 按顺序逐个应用 SQL 文件；单个迁移失败时回滚该迁移并停止后续迁移。
4. D1 迁移不提供传统的向下迁移命令。生产回退应优先使用修复性前向迁移；需要恢复数据时使用升级前导出、Time Travel 或完整备份。
5. D1 Time Travel 自动保留历史：免费计划 7 天，付费计划 30 天；可以在迁移前记录书签并恢复到该位置。
6. D1 每条查询最多 100 个绑定参数，SQL 语句最大 100 KB，单行或 BLOB 最大 2 MB；批量操作必须分块。
7. D1 始终启用外键约束；修改存在外键关系的表时可以在迁移开头使用 `PRAGMA defer_foreign_keys = on`，并在完成后执行外键检查。
8. Cloudflare 文档提供 Drizzle ORM 与 Prisma 的 D1 使用路径；Wrangler 迁移目录也支持匹配子目录中的迁移文件。

## 候选方案

| 候选 | 迁移方式 | 查询方式 | 主要优点 | 主要风险 |
| --- | --- | --- | --- | --- |
| 原生 D1 | 手写 Wrangler SQL 迁移 | `prepare().bind()`、`batch()`、Sessions | 依赖最少，完整保留 D1 和 SQLite 能力 | 行类型、字段名和组合查询容易靠人工维护，重复样板较多 |
| Drizzle | Drizzle TypeScript 表结构生成迁移草案，Wrangler 负责应用；特殊能力使用自定义 SQL | Drizzle 查询构造器，必要时使用参数化 `sql` 和原生 D1 | TypeScript 类型直接关联表结构，接近 SQL，Cloudflare D1 适配成熟 | 生成迁移仍需人工审查；FTS5、PRAGMA 和复杂恢复不能完全交给 ORM |
| Prisma | Prisma Schema 与 Prisma Migrate，D1 driver adapter | Prisma Client，必要时原始查询 | 数据模型集中、开发工具完整 | 代码生成和运行时更重；D1 适配仍有额外兼容边界；SQLite 特有能力需要绕过抽象 |
| Kysely | 需要自建或采用第三方 D1 dialect | Kysely 查询构造器 | 查询类型表达清晰、接近 SQL | Kysely 核心没有内置 D1 dialect，第三方适配器维护与长期兼容风险更高，不进入运行原型 |

## 原型范围

### 代表性结构

1. 用户、邮箱地址、物理邮件、个人邮箱条目和个人状态。
2. 地址唯一约束、外键、状态检查、常用列表索引和键集分页索引。
3. 内容空 FTS5 搜索表，由应用显式写入和删除。
4. 第二版迁移增加摘要字段并完成已有数据回填。

这些表只用于验证工具能力，不是正式数据模型。

### 查询场景

1. 根据当前用户、邮箱范围、收件箱状态、未读和附件条件组合查询。
2. 使用 `(received_at, id)` 键集分页，避免深分页依赖大偏移量。
3. 创建物理邮件与个人条目时使用原子批处理，唯一约束失败不得留下半条数据。
4. FTS5 搜索通过参数化原始 SQL 执行，恶意关键词不能改变查询结构。
5. 超过 100 个绑定参数的批量操作按不超过 90 个业务参数分块。
6. 原生 D1 与候选工具对相同输入返回一致结果。

### 迁移场景

1. 从空数据库按顺序应用全部迁移。
2. 第二次应用时不重复执行已经记录的迁移。
3. 故意失败的迁移不会留下部分表、部分数据或迁移记录。
4. 迁移后执行 `foreign_key_check`、表列检查、索引检查和关键数据数量对账。
5. 明确复现“含 FTS5 虚拟表时 D1 物理导出失败”，改用权威普通表逻辑备份，在新的本地 D1 恢复后重建搜索索引并重新对账。
6. Drizzle 生成的普通表迁移、手写 FTS5 迁移和 Wrangler 迁移账本能够共存。

### 构建与维护

1. Drizzle 与 Prisma 候选均完成类型检查和 Worker 干运行打包。
2. 记录运行时包体、依赖数量、生成文件和必要兼容标志。
3. 检查每个候选能否把业务模块限制在公开存储接口内，不把 ORM 对象泄漏到业务规则。

## 判定原则

1. 数据正确、迁移可审查和恢复路径优先于少写几行代码。
2. 数据库工具不得成为 D1、FTS5、外键检查、Time Travel 或 Wrangler 迁移的替代品。
3. 正式数据库只能有一套迁移账本和一个生产应用入口。
4. 如果工具生成的 SQL 无法稳定审查、重复应用或与 FTS5 共存，则不采用其迁移方案。
5. 若两个工具都能工作，优先选择运行时更轻、SQL 更透明、Cloudflare 边界更少的方案。
6. 本地恢复只能证明流程和对账逻辑，不能替代真实 D1 Time Travel 演练。

## 本地验证结论

1. 11 组自动验证全部通过，详细证据见[D1 数据库工具与迁移验证结果](D1数据库工具与迁移验证结果.md)。
2. Drizzle 与原生 D1 的组合列表结果一致，生成迁移、手写 FTS5 SQL 和 Wrangler 迁移账本可以共存。
3. Prisma D1 适配器可以运行，但仍为 Preview；同一代表性 Worker 的 gzip 包体约为 Drizzle 的 32 倍。
4. D1 物理导出明确拒绝包含 FTS5 虚拟表的数据库；权威普通表逻辑备份能够恢复并重建搜索索引。
5. 方案已分别记录为 ADR `0012` 和 `0013`；第七批架构已经确认，两项 ADR 状态均为“已接受”。

## 输出和通过条件

1. 建立可重复运行的数据库工具与迁移原型。
2. 所有查询、事务、迁移失败、重复执行、导出恢复和外键场景具有自动验证证据。
3. 给出原生 D1、Drizzle、Prisma 和 Kysely 的明确取舍，不以“都可以”结束。
4. 建立状态为“提议中”的架构决策记录和第七批批量确认清单。
5. 用户接受前，不建立正式工程骨架，不把候选 ORM 写成生产依赖。
