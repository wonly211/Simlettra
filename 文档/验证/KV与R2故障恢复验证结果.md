## 给非程序员的结论

本轮验证回答了一个核心问题：数据库和邮件文件不可能在同一瞬间一起写完，如果其中一步失败，Simlettra 怎样避免出现半封邮件或删不干净的数据。

结果如下：

1. `D1 + R2` 和 `D1 + KV` 使用同一套恢复流程都能完成本地故障测试。
2. 接收过程中无论已经写入 0、1、2 还是 4 个对象，邮件都不会提前出现在收件箱。
3. 最后一次 D1 可见提交故意失败时，整个事务回滚，没有留下邮箱条目或一半完成的可见状态。
4. D1 已经提交、但调用方误以为失败时，重复执行三次仍只有一封邮件、一个邮箱条目和四个对象。
5. 正文或附件对象缺失、哈希不符时，系统能撤下邮件，使用原始 MIME 和新对象键重建，再恢复可见。
6. 原始 MIME 丢失时不能凭空恢复；系统会撤下邮件并标记损坏，而不是继续显示不完整内容或静默忽略。
7. 永久删除开始后，用户立即不能访问邮件；即使后台在还剩 4、3 或 0 个对象时中断，重试仍能最终清空对象和 D1 内容引用。
8. KV 的全球传播延迟无法由本地单进程真实复现。本轮只证明“等待一致性再显示”的状态机有效，仍需真实 Cloudflare 多地区验证。

因此，已接受的“D1 权威状态 + KV/R2 不可变对象”方向获得了本地证据支持，但 KV 模式必须接受更保守的可见延迟，不能假装具备 R2 的强一致性。

## 数据模型原型

每次接收使用一个稳定操作编号，并在 D1 中保存：

1. `operations`：接收或删除操作的权威状态。
2. `messages`：物理邮件及其“准备中、等待一致性、可见、修复中、待删除、损坏”等状态。
3. `object_registry`：每个对象的角色、唯一键、代数、预期大小、SHA-256 和当前状态。
4. `mailbox_entries`：只有最终提交时才建立的可见邮箱条目。
5. `tasks`：可以由 Queue 或定时任务再次唤醒的权威任务记录。
6. `audit_events`：只记录状态类别和错误代码，不记录正文、附件或密钥。

一封合成邮件具有四个对象：原始 MIME、纯文本正文、HTML 正文和一个附件。对象键包含操作编号、角色与代数；对象损坏时创建下一代新键，不覆盖旧键。

## 场景对账

共运行 31 个完整场景：R2 15 个，KV 16 个。KV 比 R2 多一个“跨地区暂不可见”的模拟场景。

### 接收故障

每种存储模式均运行以下五个中断点：

| 中断点 | 中断时实际对象数 | 中断时可见邮箱条目 | 恢复后对象登记 | 恢复后实际对象 | 恢复后可见邮箱条目 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 接收意图刚建立 | 0 | 0 | 4 | 4 | 1 |
| 原始对象写入意图已建立 | 0 | 0 | 4 | 4 | 1 |
| 原始对象已写入 | 1 | 0 | 4 | 4 | 1 |
| 第一个衍生对象已写入 | 2 | 0 | 4 | 4 | 1 |
| 最终可见 D1 批次回滚 | 4 | 0 | 4 | 4 | 1 |

两种存储模式的结果一致。恢复后重复执行三次，邮件、邮箱条目和对象键数量均未增加。

### 提交后结果未知

原型在 D1 已完成最终可见事务后故意返回失败。调用方重试时能够从 D1 发现操作已经完成，不重复创建邮件、邮箱条目或对象。该场景验证了“调用失败”不能简单等同于“提交没有发生”。

### KV 一致性等待

KV 正常写完四个对象后，原型模拟另一地区暂时读取不到新对象：

1. D1 邮件保持“等待一致性”，邮箱条目为 0。
2. 用户内容接口返回不可访问，不泄露内部对象键。
3. 重试仍不可见时继续等待，不覆盖同一个 KV 键。
4. 模拟传播完成并重新校验后，才通过 D1 事务建立唯一邮箱条目。

本场景证明状态机可以处理传播延迟，但没有证明真实 KV 会在某个固定时间全球一致。

### 对象完整性

每种模式均验证：

| 异常 | 修复前对账 | 处理 | 修复后 |
| --- | --- | --- | --- |
| 纯文本对象缺失 | 缺失 1 个 | 撤下邮件，以第 2 代新键从原始 MIME 重建 | 登记与实际对象均为 4，健康 |
| HTML 对象哈希不符 | 损坏 1 个 | 撤下邮件，删除损坏对象，以第 2 代新键重建 | 登记与实际对象均为 4，健康 |
| 无 D1 引用的对象 | 孤立 1 个 | 对账列出并幂等清理 | 无孤立对象，健康 |
| 原始 MIME 缺失 | 缺失 1 个 | 撤下邮件并标记“原始对象丢失” | 保持损坏状态，等待备份恢复或人工处理 |

原型没有通过覆盖同一键修复损坏对象。新一代对象使用新键，避免 KV 缓存旧值，也使修复过程能够回滚和对账。

### 永久删除

每种模式均运行四个中断点：

| 中断点 | 中断时剩余实际对象 | 用户是否仍可访问 | 重试后结果 |
| --- | ---: | --- | --- |
| D1 已撤销访问，尚未删对象 | 4 | 否 | 完整删除 |
| 第一个对象已删除 | 3 | 否 | 完整删除 |
| 全部对象已删，最终 D1 批次回滚 | 0 | 否 | 完整删除 |
| 最终 D1 清理已提交，但调用方收到失败 | 0 | 否 | 重试保持完整删除 |

完成后，邮件行、邮箱条目、对象登记和实际对象均为 0；只保留不含邮件内容的操作防重记录、任务结果和必要审计事件。

## 架构影响

1. 每封物理邮件的每种对象使用唯一不可变键，不在不同邮件之间做内容去重共享。
2. D1 为每个对象保存写入意图、角色、代数、大小和 SHA-256；对象存储不承担权威引用计数。
3. 只有全部活动对象通过校验后，才在一个 D1 `batch()` 中建立邮箱条目并改为可见。
4. R2 在写入校验后可以立即提交可见；KV 进入一致性等待，至少经过后续任务重新校验，仍不可用时继续等待并告警。
5. 已可见邮件发现衍生对象缺失或损坏时，应立即撤下可见条目并使用新一代对象键重建；原始 MIME 丢失时标记损坏，不伪造恢复成功。
6. 永久删除应先在 D1 撤销全部访问，再执行可重试对象清理；只有对账为零后才显示“永久删除完成”。
7. 孤立对象不能发现后立即删除，需要保护期和至少两次独立对账，避免清理正在进行但尚未完成登记的写入。

## 仍需完成

1. 在真实 Cloudflare 账号跨至少两个地区验证 KV 新建、读取、删除和负查询缓存。
2. 验证 R2 条件写入、校验和、列举分页及并发删除。
3. 使用真实 Queue 重复投递和定时扫描验证同一任务的并发抢占。
4. 在接近目标规模时测量全量对象对账的 D1 读取、KV/R2 列举操作和完成时间。
5. 后续备份验证必须证明原始 MIME 和 D1 对象登记可以共同恢复，并能重新生成衍生对象与搜索索引。
