## 给非程序员的结论

三家服务不能简单共用一个“20 MB”数字。Simlettra 必须先看当前域名选择了哪家发信服务，再采用自身上限和供应商上限中的较小值。

| 当前发信方式 | 用户实际可发送的单封邮件总大小 |
| --- | ---: |
| Cloudflare Email Sending，普通外部收件人 | 5,242,880 字节，即 5 MiB |
| Cloudflare Email Sending，全部收件人均为 Email Routing 已验证目标 | 20,000,000 字节 |
| Resend | 20,000,000 字节 |
| SMTP2GO API | 20,000,000 字节 |

因此，选择 Cloudflare Email Sending 向普通外部邮箱发信时，会明显早于产品默认的 20 MB 达到上限。界面必须在发送前说明当前实际限制，不能等上传和发送完成后才由供应商报错。

## 大小计算结论

1. Simlettra 自身上限为 `20,000,000` 个字节，不把 `20 MB` 解释为 `20 MiB`。
2. 判断对象是最终 RFC 822 MIME 或供应商适配器将要提交的等价完整邮件负载，不是附件原文件大小之和。
3. 邮件头、地址、主题、纯文本、HTML、MIME 边界、内嵌资源、附件和 Base64 膨胀都计入总大小。
4. 实际上限为 `min(Simlettra 上限, 供应商上限, 当前收件人条件上限)`。
5. 最终检查在 Queue consumer 调用供应商前执行；前端显示的估算不能代替服务端检查。
6. 刚好等于有效上限时允许提交，多一个字节时返回本地错误，供应商接受次数必须为零。

## 统一状态结论

每个站外收件人独立保存：等待提交、提交中、已提交、延迟、已送达、退信、失败和结果未知。

1. 同一封邮件发给多个站外收件人时，一个收件人退信不能覆盖其他收件人的已送达状态。
2. 垃圾投诉保存为独立风险标记，不覆盖“已送达”。
3. 打开和点击事件不作为可靠的已读状态。
4. 供应商事件按供应商事件编号去重；较早到达的“已提交”或“延迟”不能让终态倒退。

## 重试结论

1. 能明确证明请求尚未被供应商接受时，三家服务都可以使用同一 Simlettra 操作编号重试。
2. Resend 已接受但响应丢失时，在 24 小时内使用同一 `Idempotency-Key` 重试。
3. Cloudflare Email Sending 和 SMTP2GO 没有已核实的发送幂等键；响应丢失后进入“结果未知”，禁止自动重新发送。
4. 后续供应商事件可以消解部分“结果未知”。SMTP2GO 适配器应发送 `X-Simlettra-Operation-ID` 等自定义邮件头，以便事件与本地操作关联。
5. 超过 Resend 的 24 小时幂等窗口后仍无结果，不自动重发，由用户或管理员查看说明后决定是否创建一次新的发送。

## 回调与事件结论

1. Cloudflare Event Subscriptions 由同一 Worker 的 Queue consumer 接收，不建立同等权限的公共 HTTP 回调地址。
2. Resend 必须使用原始请求体、`svix-id`、`svix-timestamp` 和 `svix-signature` 验签，并限制允许的时间偏差。
3. SMTP2GO 使用专用 HTTPS Basic Auth 凭据，并按 Webhook 事件编号去重；凭据不能放进查询参数。
4. 鉴权失败、事件重复或事件时间较早时，都不能改变现有投递结果。

## 验证边界

本轮没有证明以下事项：

1. 真实账号的套餐、日配额、域名审核、地区可用性、费用和实际送达率。
2. 供应商将 `20,000,000` 字节邮件真实接受后的网络耗时和超时行为。
3. Cloudflare Queue、Resend Webhook 和 SMTP2GO Webhook 在真实公网环境中的重试时序。
4. 供应商以后调整限制时的自动发现能力；生产实现必须把能力值集中在适配器中，并在升级说明中复核。
5. SMTP2GO Webhook 的 Basic Auth 是可配置保护，不是事件级数字签名；仍需依赖 HTTPS、强随机凭据、限速和事件去重。
