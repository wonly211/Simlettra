# 澄笺 | Simlettra 三种域外发信服务验证计划

## 文档状态

- 状态：当前
- 建立日期：2026-08-10
- 对应总计划：`验证-04`
- 执行状态：历史验证已完成；Provider 范围已由 ADR `0028` 取代
- 目的：验证 Cloudflare Email Sending、Resend 和 SMTP2GO 能否通过统一域外发信网关执行大小检查、幂等提交、结果未知处理、回调鉴权和投递状态映射

> 当前用途：只保留 2026-08-10 三家 Provider 原型的历史证据。首发当前只支持 Resend 和 SMTP2GO，新的验证范围见[两种域外发信服务验证计划](两种域外发信服务验证计划.md)。本计划中的 Cloudflare Email Sending 项目不得作为当前实现依据。

## 已确认需求

1. 每个发信域名可以单独选择域外发信服务。
2. Simlettra 单封邮件总大小上限为 20,000,000 个最终 MIME 字节。
3. Outbound Mail Provider 限制更小时，实际允许大小取更小值。
4. 用户可以看到发送中、已提交、已送达、延迟、退信和失败等供应商能够提供的状态。
5. 临时失败可以重试，但 Simlettra 控制的重试不能向同一收件人重复投递。
6. 供应商回调或事件必须验证来源，重复事件不能重复改变业务结果。

## 大小判定

1. 先生成最终将被发送或等价提交的 RFC 822 MIME 字节。
2. 主题、地址、邮件头、纯文本、HTML、内嵌资源、附件边界和 Base64 膨胀全部计入总大小。
3. 实际上限为：Simlettra 上限、当前供应商上限、当前收件人条件产生的供应商上限三者中的最小值。
4. 在 Queue consumer 调用供应商之前再次检查，不能只依赖写信页面估算。
5. 刚好等于上限允许提交；多一个字节必须在本地拒绝，不能消耗供应商额度后才报错。

## 统一状态

每个站外收件人独立保存以下状态：

| 状态 | 含义 |
| --- | --- |
| `等待提交` | D1 已建立发信任务，尚未调用供应商 |
| `提交中` | 当前任务正在调用供应商 |
| `已提交` | 供应商明确接受，并返回可追踪编号或同等确认 |
| `延迟` | 供应商明确表示暂时未送达且仍可能继续尝试 |
| `已送达` | 收件服务器确认接受 |
| `退信` | 收件服务器最终拒绝或退回 |
| `失败` | 本地检查、供应商拒绝、鉴权或其他确定性错误 |
| `结果未知` | 请求可能已经被供应商接受，但 Simlettra 没有得到足够证据；不能盲目自动重发 |

垃圾投诉和打开、点击不改变核心投递状态；可以保存为独立风险或互动事件，但首发不向用户承诺准确的已读状态。

## 故障与幂等场景

1. 供应商调用前连接明确失败：可以按同一操作编号安全重试。
2. 供应商已经接受但响应丢失：
   - Resend 在 24 小时内使用同一幂等键重试，必须返回同一发送结果且只投递一次。
   - Cloudflare Email Sending 和 SMTP2GO 不自动重发，进入“结果未知”。
3. SMTP2GO 可以通过 Webhook 中的 `message-id` 或配置回传的 `X-Simlettra-Operation-ID` 解决部分结果未知状态。
4. Cloudflare 事件、Resend Webhook 和 SMTP2GO Webhook 重复三次，只能记录一个供应商事件并产生一次状态迁移。
5. 事件乱序到达时，已送达或退信等终态不能被更早的“已提交”或“延迟”覆盖。

## 回调鉴权

1. Cloudflare Event Subscriptions 只从绑定到同一 Worker 的 Queue consumer 入口接收，不开放伪装成 Queue 的公共 HTTP 接口。
2. Resend 使用原始请求体、`svix-id`、`svix-timestamp` 和 `svix-signature` 验证签名，并按事件编号防重放。
3. SMTP2GO 使用单独的 HTTPS Basic Auth 高强度凭据，不把密钥放在查询参数；同时按 Webhook `id` 去重，并配置回传 `X-Simlettra-Operation-ID`。
4. 任何鉴权失败、时间窗口不合理或重复事件都不能修改投递状态。

## 通过标准

1. 三种供应商在有效上限处允许发送，上限加一个字节在本地拒绝。
2. Cloudflare 普通外部地址有效上限为 5,242,880 字节；Resend 与 SMTP2GO 有效上限为 20,000,000 字节。
3. 同一 Resend 幂等键重复提交三次只产生一个供应商发送编号。
4. Cloudflare 与 SMTP2GO 发生“接受后响应丢失”时不自动创建第二次发送。
5. 明确未提交的临时故障恢复后只产生一次供应商发送。
6. 三家供应商事件均映射到统一的收件人状态；重复和乱序事件不造成状态倒退。
7. 无效 Resend 签名、过期时间戳、无效 SMTP2GO Basic Auth 和伪造 Cloudflare HTTP 事件全部被拒绝。
8. 原型不包含真实 API 密钥，不向真实收件人发送邮件。

## 不在本轮验证

1. 真实账号配额、实际送达率、垃圾邮件评分和供应商费用。
2. 真实 Cloudflare Queue、Resend 或 SMTP2GO 网络调用，需要部署者测试账号。
3. 邮件编辑器和附件上传界面。
4. 站内与站外混合收件人的完整用户流程。
